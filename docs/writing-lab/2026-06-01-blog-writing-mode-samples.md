# 블로그 글쓰기 모드 샘플

이 문서는 기존 글을 여러 글쓰기 모드로 바꿔 읽어보기 위한 실험 문서다. 실제 발행글을 바로 바꾸지 않고, 같은 원본을 서로 다른 목적의 글로 변환해 어떤 패턴을 스킬로 굳힐지 판단한다.

## 기준 원본

- 원본 글: `docs/blog/2026-05-31-frontmatter-validation.md`
- 주제: frontmatter validation으로 발행 사고 막기
- 원본 성격: 문제, 선택지, 구현, 검증을 균형 있게 설명하는 기술 딥다이브

원본의 핵심 내용은 다음과 같다.

- 마크다운 frontmatter는 사람이 손으로 쓰기 때문에 실수가 생긴다.
- Astro content collection schema만으로는 편집 정책까지 검증하기 어렵다.
- `validate:posts` 스크립트로 error와 warning을 나눠 발행 전 검증을 한다.
- source mode와 published mode를 나눠 초안 검증과 발행본 검증을 분리한다.

---

## 모드 1: 자기 학습형

### 제목

frontmatter validation을 이해하며 발행 사고를 막는 기준 세우기

### 샘플 본문

이 글은 `validate:posts` 스크립트를 만들었다는 결과 보고가 아니라, 내가 frontmatter validation을 어떻게 이해했는지 남기는 기록이다. 처음에는 frontmatter를 단순한 글 메타데이터로 봤다. 제목, 날짜, 태그, 요약, draft 여부를 적는 작은 설정 정도라고 생각했다.

하지만 글이 여러 프로젝트에서 들어오고, 그 글들이 하나의 블로그로 모이기 시작하면 frontmatter는 단순한 부가 정보가 아니게 된다. `project`가 틀리면 프로젝트 페이지와 연결되지 않고, `tags`가 흔들리면 태그 목록이 지저분해진다. `draft`가 잘못되면 아직 공개하지 않을 글이 발행될 수도 있다. 결국 frontmatter는 블로그의 데이터 계약에 가깝다.

내가 이해해야 했던 첫 번째 지점은 Astro content collection schema와 별도 validation script의 역할 차이다. schema는 데이터 형태를 지킨다. 예를 들어 `date`가 날짜인지, `type`이 허용된 값인지 같은 것을 확인한다. 반면 validation script는 편집 정책을 지킨다. 요약이 너무 짧거나 긴지, deep-dive 글에 `## 검증` 섹션이 있는지, tag가 닫힌 목록 안에 있는지 같은 기준은 스키마보다 정책에 가깝다.

두 번째로 이해해야 했던 지점은 error와 warning을 나누는 기준이다. 모든 문제를 error로 만들면 글쓰기가 불편해지고, 결국 검증을 끄고 싶어진다. 반대로 모든 문제를 warning으로 만들면 실제로 사이트를 깨뜨릴 문제도 통과한다. 그래서 기준은 "사이트 구조나 데이터 무결성을 깨뜨리는가"로 잡았다. 필수 frontmatter 누락, 허용되지 않은 project, 허용되지 않은 tag는 error다. 요약 길이나 섹션 누락은 warning이다.

이번 구현은 Codex에게 맡겼지만, 내가 검토한 핵심은 이 기준이 과하지 않은지였다. 발행을 막아야 하는 문제와 알려주기만 해도 되는 문제를 분리했는지, 로컬 source mode와 CI published mode가 섞이지 않는지, 새 프로젝트가 들어와도 검증 기준이 유지되는지를 봤다.

나중에 다시 볼 코드는 `scripts/validate-posts.mjs`, `src/content.config.ts`, `src/data/tags.json`, `posts.config.yml`이다. 이 네 파일을 같이 봐야 "스키마", "편집 정책", "닫힌 태그 목록", "프로젝트별 원본 경로"가 어떻게 연결되는지 이해할 수 있다.

다음에는 직접 작은 실패 케이스를 만들어보고 싶다. 허용되지 않은 tag를 넣었을 때 어떤 에러가 나는지, `draft: true` 글이 sync에서 빠지는지, source mode와 published mode의 검증 대상이 어떻게 달라지는지 직접 확인하면 이 구조를 내 언어로 더 잘 설명할 수 있을 것 같다.

### 이 모드의 장점

- AI가 구현한 작업이어도 사용자의 학습과 판단이 드러난다.
- "내가 무엇을 이해해야 하는가"가 앞에 있어서 공부 기록으로 좋다.
- 포트폴리오에서 과장 없이 정직하게 읽힌다.

### 이 모드의 한계

- 독자가 빠르게 해결책만 보고 싶을 때는 길게 느껴질 수 있다.
- 글쓴이의 학습 과정이 중심이라, 튜토리얼처럼 바로 따라 하기는 어렵다.

## 모드 2: 설명형

### 제목

마크다운 블로그에서 frontmatter validation이 필요한 이유

### 샘플 본문

마크다운 블로그에서 frontmatter는 글의 메타데이터를 담는다. 보통 제목, 날짜, 태그, 요약, 발행 여부 같은 값이 들어간다. 글이 적을 때는 이 값을 사람이 직접 확인해도 큰 문제가 없다. 하지만 글이 늘어나고, 여러 프로젝트의 글을 한 블로그로 모으기 시작하면 frontmatter 실수는 곧 사이트 구조의 문제로 이어진다.

예를 들어 `project` 값이 잘못되면 글이 어느 프로젝트에 속하는지 알 수 없다. `tags`에 오타가 있으면 같은 개념이 여러 태그로 쪼개진다. `draft` 값을 잘못 쓰면 공개하지 않아야 할 글이 발행될 수 있다. 따라서 frontmatter는 단순한 메모가 아니라, 블로그가 글을 분류하고 렌더링하기 위한 입력 데이터다.

검증은 두 층으로 나눌 수 있다. 첫 번째는 Astro content collection schema다. 이 schema는 frontmatter의 기본 형태를 확인한다. `type`이 허용된 값인지, `tags`가 배열인지, `draft`가 boolean인지 같은 검증은 schema가 잘 맡는다.

두 번째는 별도 validation script다. schema가 데이터 타입을 확인한다면, validation script는 편집 정책을 확인한다. 예를 들어 요약은 80자 이상 160자 이하인지, deep-dive 글에는 `## 검증` 섹션이 있는지, tag는 닫힌 목록에 있는 값만 쓰는지 같은 규칙이다. 이런 규칙은 기술적인 타입보다는 운영 정책에 가깝기 때문에 별도 스크립트로 두는 편이 관리하기 쉽다.

검증 결과는 error와 warning으로 나누는 것이 좋다. error는 발행을 막아야 하는 문제다. 필수 frontmatter 누락, 허용되지 않은 project, 허용되지 않은 tag, 같은 프로젝트 안의 slug 중복이 여기에 해당한다. warning은 알려주되 발행을 막지는 않는 문제다. 요약 길이, 권장 섹션 누락처럼 글 품질과 관련된 항목이 여기에 가깝다.

이 구분이 중요한 이유는 검증을 지속 가능하게 만들기 위해서다. 너무 많은 문제를 error로 만들면 글을 쓸 때마다 발행이 막혀 검증을 끄고 싶어진다. 반대로 너무 느슨하면 검증이 있어도 사고를 막지 못한다. 그래서 "사이트를 깨뜨리는가"와 "품질을 개선하는가"를 기준으로 나누는 것이 좋다.

여러 프로젝트의 글을 모으는 블로그라면 source mode와 published mode를 나누는 것도 중요하다. source mode는 각 프로젝트의 원본 글까지 검사한다. published mode는 블로그 저장소에 동기화된 발행본만 검사한다. CI에서는 로컬 컴퓨터의 다른 프로젝트 경로에 접근할 수 없으므로 published mode만 실행하는 편이 안전하다.

결국 frontmatter validation은 글쓰기의 번거로운 규칙이 아니라, 글이 많아져도 블로그 구조를 유지하기 위한 안전장치다.

### 이 모드의 장점

- 독자가 개념을 이해하기 쉽다.
- 글쓴이 개인의 맥락보다 일반화된 설명이 중심이라 공유하기 좋다.
- 튜토리얼이나 기술 설명 문서에 가깝다.

### 이 모드의 한계

- 사용자가 어떤 판단을 했는지는 덜 드러난다.
- 포트폴리오 관점에서는 개성이나 문제 해결 과정이 약해질 수 있다.

## 모드 3: 포트폴리오형

### 제목

발행 전 검증 계층을 분리해 마크다운 블로그의 데이터 품질 지키기

### 샘플 본문

여러 프로젝트의 개발 로그를 하나의 블로그로 모으기 위해서는 글을 단순 파일이 아니라 데이터로 다뤄야 했다. 특히 frontmatter는 글의 제목, 날짜, 프로젝트, 태그, 요약, 발행 여부를 담기 때문에 사이트 라우팅과 목록 구성에 직접 영향을 준다.

문제는 frontmatter가 사람이 손으로 작성하는 값이라는 점이다. 태그 오타, 잘못된 project 값, 비어 있는 summary, 같은 프로젝트 안의 slug 중복은 모두 작은 실수처럼 보이지만, 발행 후에는 잘못된 목록, 깨진 링크, 지저분한 태그 페이지로 드러난다.

처음 선택지는 Astro content collection schema에만 의존하는 것이었다. 하지만 schema는 타입과 필수값 검증에는 적합해도, 편집 정책을 표현하기에는 한계가 있었다. 예를 들어 "요약 길이는 80자에서 160자 사이", "deep-dive 글에는 검증 섹션이 있어야 함", "tag는 닫힌 목록에서만 선택" 같은 규칙은 별도 정책 검증에 가깝다.

그래서 검증 계층을 둘로 나눴다. `src/content.config.ts`는 데이터 형태를 검증하고, `scripts/validate-posts.mjs`는 발행 정책을 검증한다. validation script는 error와 warning을 분리한다. 사이트 구조를 깨뜨리는 문제는 error로 처리해 발행을 막고, 글 품질을 높이는 권장 사항은 warning으로 알려준다.

이 결정의 핵심은 검증의 지속 가능성이다. 모든 규칙을 error로 만들면 작성 경험이 나빠지고, 모든 규칙을 warning으로 만들면 사고를 막지 못한다. 따라서 project, tag, slug 중복처럼 데이터 무결성에 영향을 주는 항목만 발행 차단 기준으로 삼았다.

또한 원본 글 검증과 발행본 검증을 분리했다. 로컬에서는 `npm run validate:posts -- --source`로 각 프로젝트의 `docs/blog` 원본까지 검사할 수 있다. 반면 CI에서는 블로그 저장소 안에 동기화된 `src/content/blog`만 검사한다. GitHub Actions runner에는 로컬 프로젝트 경로가 없기 때문에, source mode를 CI에 넣지 않는 것이 더 안정적인 선택이었다.

결과적으로 이 구조는 글이 늘어나도 발행 전에 메타데이터 품질을 확인할 수 있게 만든다. 새 프로젝트가 추가되어도 `posts.config.yml`, `projects.json`, `tags.json`에 명시된 계약을 기준으로 검증된다. 블로그를 단순 정적 사이트가 아니라 여러 프로젝트 글의 발행 허브로 운영하기 위한 기반이 된 셈이다.

### 이 모드의 장점

- 문제, 제약, 결정, 검증이 선명해서 채용 담당자가 읽기 좋다.
- "왜 이렇게 설계했는가"가 중심이라 설계 역량이 드러난다.
- 구체 파일과 자동화 경계가 보여 실제 프로젝트 경험처럼 읽힌다.

### 이 모드의 한계

- 학습 과정과 개인적 이해는 상대적으로 덜 드러난다.
- 설명형보다 초심자 친화성은 낮다.

## 비교 결론

세 모드는 같은 사실을 다루지만 독자가 기대하는 정보가 다르다.

| 모드 | 주 독자 | 중심 질문 | 좋은 사용처 |
| --- | --- | --- | --- |
| 자기 학습형 | 글쓴이 자신, 성장 과정을 보는 독자 | 내가 무엇을 이해했고 다음에 무엇을 해볼 것인가 | AI 협업 기록, 학습 회고, dev-log 확장 |
| 설명형 | 같은 문제를 처음 만난 개발자 | 이 개념은 무엇이고 어떻게 적용하는가 | 튜토리얼, 개념 정리, 공유용 글 |
| 포트폴리오형 | 채용 담당자, 동료 개발자 | 어떤 문제를 보고 어떤 설계를 선택했는가 | 대표 글, 프로젝트 상세 링크, 이력서 보조 자료 |

## 스킬로 굳힐 후보 패턴

스킬은 글을 한 번에 "좋게" 쓰게 하는 도구가 아니라, 목적에 맞는 글의 관점을 고르게 하는 도구여야 한다.

### 입력

- 원본 마크다운 글 경로
- 원하는 모드: `self-learning`, `explainer`, `portfolio`, `dev-log`
- 글의 사실 관계를 보강하기 위해 참고할 코드 파일이나 PR 링크
- AI가 맡은 작업과 사용자가 판단한 작업의 구분

### 공통 원칙

- 원본의 사실 관계를 유지한다.
- 모르는 내용을 지어내지 않는다.
- AI가 구현한 부분을 숨기지 않는다.
- 사용자가 한 판단, 검토, QA, 방향 설정을 선명하게 분리한다.
- 발행본인 `src/content/blog`를 직접 고치지 않고 원본 `docs/blog`를 고친다.
- 리라이트 후에는 `sync:posts`, `validate:posts`, `test`, `build`로 확인한다.

### 모드별 출력 구조

#### `self-learning`

- 이 글에서 내가 이해해야 할 것
- 문제 상황
- 내가 내린 결정
- Codex에게 맡긴 구현
- 내가 검토한 기준
- 코드에서 다시 볼 지점
- 배운 점
- 다음에는 직접 해볼 것

#### `explainer`

- 배경
- 핵심 개념
- 왜 필요한가
- 선택지
- 구현 흐름
- 주의할 점
- 요약

#### `portfolio`

- 문제
- 제약
- 선택지
- 결정
- 구현 구조
- 트레이드오프
- 검증
- 결과와 다음 과제

#### `dev-log`

- 오늘 한 일
- 막힌 점
- 결정한 것
- 검증한 것
- 남은 질문
- 다음 단계

## 스킬 이름 후보

- `technical-blog-rewriter`
- `blog-learning-writer`
- `portfolio-blog-writer`

현재 목적에는 `technical-blog-rewriter`가 가장 넓고 좋다. 기존 글을 목적별 모드로 바꾸는 기능을 잘 드러내고, 새 글 작성에도 확장할 수 있다.
