# 글쓰기 가이드 (dev-log + 기술 글)

이 문서는 이 블로그에 실리는 모든 글의 단일 기준이다. sigak 저장소의
`docs/blog/WRITING_GUIDE.ko.md`를 블로그 생태계 전체(여러 프로젝트가 글의 출처가 되는 구조)에
맞게 각색한 것이다. 글의 작성·동기화·발행 절차는 `docs/content-publishing-workflow.md`를 따른다.

다루는 글 유형은 두 가지다.

1. **개발 로그(dev-log)** — 하루 작업을 기록하는 글
2. **기술 글(deep-dive)** — 특정 주제를 깊게 파는 글

모든 글은 한국어로 쓴다. 코드, 식별자, API 필드는 영어를 유지한다.

## 0. 황금 규칙 (어기지 말 것)

1. 그 세션에서 실제로 한 일과 검증한 사실만 쓴다.
2. 실행하지 않은 테스트를 통과했다고 쓰지 않는다. 검증 안 된 항목은 `미검증`으로 표기한다.
3. 숫자(테스트 수, latency, 코드 줄 수 등)를 지어내지 않는다.
4. 완료한 일과 남은 일을 분명히 구분한다.
5. 핵심 결정은 *왜* 했는지 이유를 쓴다.
6. 독자는 기술이 있지만 이 프로젝트 맥락은 모른다고 가정한다.
7. 한 글은 하나의 핵심 메시지에 집중한다.

## 1. 개발 로그(dev-log) 작성법

### 목적

dev-log는 "오늘 무엇을, 왜 했는가"를 기록한다. 커밋 나열이 아니라 그날의 작업을
이해할 수 있는 맥락과 결정을 담는다.

### 구조 (권장 순서, 전부 필수는 아님)

1. 제목: `YYYY-MM-DD 개발 로그: 핵심 주제`
2. 요약: 2~4문장으로 그날의 핵심 변화
3. 오늘 완료한 일: 실제로 끝낸 작업 (근거와 함께)
4. 설계 고민 / 트레이드오프: 왜 그렇게 했는지
5. 기술 포인트: 구현 세부, 코드 스니펫, 설정 예시
6. 검증: 실행한 명령과 결과 (검증 안 된 것은 `미검증`)
7. 다음 단계: 앞으로 할 일
8. 커밋 로그: 그날의 주요 커밋 (선택)

## 2. 기술 글(deep-dive) 작성법

### 주제 선정 기준 (2개 이상 충족 시 글로 만든다)

- 재사용 가능한 패턴이나 원칙을 담고 있는가
- 디버깅/트러블슈팅에서 일반화할 교훈이 있는가
- 설계 트레이드오프를 설명할 가치가 있는가
- 다른 프로젝트에도 적용할 수 있는가

### 구조 (권장)

문제 → 선택지 → 결정과 이유 → 검증 → 일반화한 교훈 순으로 쓴다.
글의 목표는 "이 결정을 다른 상황에도 적용할 수 있게" 만드는 것이다.

## 3. frontmatter

글 파일은 `npm run new:post`로 만들고, 아래 필드를 채운다(스키마는 `src/content.config.ts`에서 검증).

- `title`, `date`, `summary`: 필수
- `type`: `dev-log` | `deep-dive` | `debugging` | `architecture` | `performance` | `research`
- `project`: `posts.config.yml`에 등록된 프로젝트 키
- `tags`: 1개 이상
- `draft`: 작업 중 `true`, 발행 시 `false`

## 4. 발행 전 점검

작성 중에는 원본 글도 검증한다.

```bash
npm run validate:posts -- --source --project <project>
```

발행할 때는 원본 글에서 `draft: false`로 바꾼 뒤 발행본을 동기화하고 최종 검증한다.

```bash
npm run sync:posts
npm run validate:posts
npm run build
```

`--source` 검증은 `draft: true` 초안까지 검사한다. 기본 `validate:posts`는 `src/content/blog`에 동기화된 발행본만 검사한다.

## 5. 글 발행 후 학습 노트

설계나 검증을 다룬 글은 발행 후 `면접에서 설명할 수 있어야 할 질문`을 기준으로 개인 답변 노트를 만든다.

- 공개 글에는 질문과 코드에서 다시 볼 지점을 남긴다.
- 개인 답변은 `docs/interview-notes/private/`에 작성한다.
- 작성 방식은 `docs/interview-notes/README.md`와 `docs/interview-notes/templates/article-answer-note.md`를 따른다.

이 노트는 블로그 콘텐츠가 아니라 학습 도구다. 답을 바로 공개 문장으로 다듬기보다, 먼저 내가 어디까지 이해했는지 드러내는 데 집중한다.
