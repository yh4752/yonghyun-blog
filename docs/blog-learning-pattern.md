# 블로그 학습 패턴

이 문서는 `yonghyun-blog`와 `sigak` 글을 기반으로 정리한 학습형 기술 블로그 작성 패턴이다.

목표는 글을 대신 잘 써주는 것이 아니다. 구현 과정에서 생긴 설계 판단을 내가 다시 읽고 설명할 수 있게 만들고, 동시에 면접관이나 채용 담당자가 봤을 때 문제 인식과 검증 능력이 드러나게 만드는 것이다.

## 적용 대상

이 패턴은 아래 성격의 글에 적용한다.

- 설계 선택을 설명해야 하는 글
- 버그 개선, 성능 개선, 배포/검증 흐름처럼 판단 근거가 중요한 글
- 여러 기술 선택지 중 하나를 고른 이유가 있는 글
- 나중에 면접에서 "왜 그렇게 했나요?"라는 질문을 받을 수 있는 글

단순 작업 기록이나 작은 UI 수정처럼 깊은 판단이 없는 글에는 전체 구조를 억지로 적용하지 않는다.

## 글 범위 결정 기준

글을 고치기 전에 먼저 글의 크기를 정한다. 모든 글을 `dev-log`와 `deep-dive` 둘 중 하나로만 보면, 하루 기록은 과하게 무거워지고 중요한 판단은 단순 로그 안에 묻힐 수 있다.

| 형식 | 적합한 상황 | 작성 방식 |
| --- | --- | --- |
| `dev-log` | 하루 동안 여러 작업을 진행했고, 시간순 기록이 중요한 경우 | 완료한 일, 검증, 남은 일을 중심으로 짧게 정리한다 |
| `decision-note` | 하나의 설계 선택이나 도구 선택을 설명해야 하지만 full deep-dive까지는 아닌 경우 | 문제, 선택지, 결정, 트레이드오프, 검증만 압축해서 쓴다 |
| `learning-note` | 내가 잘 몰랐던 개념을 프로젝트 사례로 이해하는 것이 중심인 경우 | 첫 이해, 부족한 개념, 프로젝트 예시, 다시 볼 질문을 남긴다 |
| `deep-dive` | 하나의 큰 기술 문제를 깊게 설명하고 포트폴리오 가치가 큰 경우 | 문제, 제약, 선택지, 구현, 검증, 트레이드오프를 충분히 보여준다 |

하나의 dev-log에 독립 주제가 3개 이상 들어가면, dev-log는 요약으로 유지하고 별도 `decision-note`나 `deep-dive` 후보를 뽑는다.

## 공개 글의 공통 구조

공개 블로그 글은 독자가 프로젝트 맥락을 모른다고 가정하고 쓴다. 결과를 먼저 자랑하기보다, 어떤 문제를 봤고 어떤 기준으로 결정했는지 보여주는 것이 중요하다.

권장 구조는 아래 순서다.

1. **한 줄 요약**
   - 이 글에서 설명할 핵심 결정을 한 문장으로 적는다.
   - 예: "배포는 Vercel에 맡기고, 배포 전에 깨질 수 있는 지점은 GitHub Actions에서 먼저 막도록 역할을 나눴다."

2. **문제**
   - 왜 이 작업이 필요했는지 설명한다.
   - 단순히 "도구를 도입했다"가 아니라, 도구가 없을 때 어떤 위험이 있었는지 쓴다.
   - 예: frontmatter 실수, schema drift, 배포 전 검증 부재.

3. **제약**
   - 당시 선택을 제한한 조건을 적는다.
   - 예: GitHub Actions runner에는 로컬 Sigak 경로가 없다, Vercel이 이미 배포를 담당한다, H2는 PostgreSQL-specific DDL을 충분히 검증하지 못한다.

4. **선택지**
   - 최소 2개 이상의 선택지를 비교한다.
   - 장점만 쓰지 않고 한계도 같이 쓴다.
   - 표를 쓰면 포트폴리오 독자가 판단 과정을 빠르게 볼 수 있다.

5. **결정**
   - 어떤 방식을 선택했는지와 이유를 쓴다.
   - "익숙해서"보다 "이 프로젝트의 제약에서 무엇을 더 중요하게 봤는가"를 드러낸다.

6. **구현 구조**
   - 어떤 파일, 설정, 스크립트, 테스트가 결정을 구현하는지 연결한다.
   - 코드 전체를 설명하기보다, 다시 볼 파일과 역할을 짚는다.

7. **트레이드오프**
   - 얻은 점과 미룬 점을 모두 적는다.
   - 좋은 글은 "이게 정답이다"보다 "이 상황에서는 이 비용을 감수했다"에 가깝다.

8. **검증**
   - 실제로 실행한 명령과 확인한 결과를 적는다.
   - 실행하지 않은 검증은 `미검증`으로 남긴다.
   - 자동 테스트가 보장하지 못하는 시각 QA, 운영 QA도 분리해서 쓴다.

9. **내가 이해한 것**
   - 도구 사용법보다 이번 작업을 통해 이해한 개념을 정리한다.
   - 이 섹션은 나중에 글을 다시 읽을 때 학습 효과가 가장 크다.

10. **Codex에게 맡긴 것과 내가 검토한 것**
    - 구현을 AI에게 맡긴 경우 숨기지 않는다.
    - 대신 내가 검토한 기준, 선택 이유, 위험 판단을 명확히 적는다.
    - 포트폴리오에서 중요한 것은 "모든 문자를 직접 입력했는가"가 아니라 "설계를 이해하고 설명할 수 있는가"다.

11. **코드에서 다시 볼 지점**
    - 파일 목록을 표로 정리한다.
    - 파일명만 나열하지 말고, 각 파일에서 무엇을 확인해야 하는지 적는다.

12. **면접에서 설명할 수 있어야 할 질문**
    - 글을 내 것으로 만들기 위한 질문을 5~8개 남긴다.
    - 이 질문은 공개 글의 끝이자, 개인 답변 노트의 시작점이다.

## 개인 답변 노트의 공통 구조

개인 답변 노트는 공개 글이 아니다. 잘 쓴 문장보다, 내가 어디까지 이해했는지를 드러내는 것이 먼저다.

위치는 아래 규칙을 따른다.

```txt
docs/interview-notes/private/<project>/<post-slug>.md
```

권장 구조는 아래와 같다.

1. **첫 답변**
   - 정리되지 않은 말로 먼저 적는다.
   - "잘 모르겠다"도 그대로 남긴다.

2. **부족한 개념**
   - 첫 답변에서 빠진 개념을 정리한다.
   - 개념 정의만 쓰지 말고, 해당 프로젝트 사례와 연결한다.

3. **코드/문서 근거**
   - 답변을 뒷받침할 파일을 체크한다.
   - 근거가 없는 답변은 면접용 답변으로 굳히지 않는다.

4. **면접용 30-60초 답변**
   - 첫 답변과 부족한 개념을 바탕으로 자연스럽게 다시 쓴다.
   - 외운 문장처럼 보이지 않도록 프로젝트 맥락을 넣는다.

5. **꼬리 질문 대비**
   - 면접관이 바로 이어서 물을 수 있는 질문을 남긴다.
   - 모르는 부분은 다음 학습 항목으로 분리한다.

## 프로젝트가 달라져도 유지할 원칙

아래 원칙은 `yonghyun-blog`, `sigak`, 앞으로의 새 프로젝트에 공통으로 적용한다.

- 결과보다 문제 인식과 선택 이유를 먼저 쓴다.
- 도구 이름보다 그 도구가 맡은 책임을 설명한다.
- 내가 모르는 개념을 숨기지 않는다.
- 공개 글과 개인 학습 노트를 분리한다.
- 코드나 문서 근거가 없는 설명은 면접 답변으로 확정하지 않는다.
- 검증한 것과 검증하지 않은 것을 분리한다.
- AI가 도운 부분은 숨기지 않고, 내가 검토한 판단 기준을 남긴다.

## 프로젝트마다 바뀌는 값

패턴은 같아도 프로젝트별로 아래 값은 매번 달라진다.

| 항목 | 설명 |
| --- | --- |
| `project` | `posts.config.yml`과 `src/data/projects.json`에 등록된 project slug |
| 원본 글 경로 | 각 프로젝트의 `docs/blog` 안에 있는 원본 글 |
| 발행본 경로 | `src/content/blog/<project>/` 안에 동기화된 글 |
| 주요 파일 | 글에서 설명하는 설계를 실제로 구현한 코드, 설정, 테스트 |
| 검증 명령 | 프로젝트별로 실제 실행 가능한 테스트와 빌드 명령 |
| 도메인 용어 | Sigak의 `source of truth`, `projection store`처럼 프로젝트 고유 맥락 |
| 면접 질문 | 해당 글의 결정과 트레이드오프를 설명하기 위한 질문 |

## 글을 고칠 때의 판단 기준

기존 글을 이 패턴으로 고칠 때는 아래 순서로 본다.

1. **문제가 명확한가?**
   - "무엇을 했다"만 있고 "왜 필요했는가"가 없으면 문제 섹션을 보강한다.

2. **선택지가 보이는가?**
   - 하나의 결정만 적혀 있으면, 버린 선택지와 그 이유를 추가한다.

3. **검증이 실제 명령과 연결되는가?**
   - "확인했다"만 있고 명령이나 근거 파일이 없으면 검증 섹션을 보강한다.

4. **내가 이해한 것이 드러나는가?**
   - 도구 사용법만 있고 배운 개념이 없으면 `내가 이해한 것` 섹션을 추가한다.

5. **면접 질문으로 이어지는가?**
   - 글을 읽고도 "그래서 어떤 질문에 답할 수 있어야 하지?"가 남으면 질문 세트를 추가한다.

## 스킬로 만들 때의 입력과 출력

이 패턴은 이후 `technical-blog-learning-writer` 스킬의 기준이 된다.

### 입력

- `project`: 글이 속한 project slug
- `sourcePost`: 원본 글 경로
- `mode`: `learning` | `explanation` | `portfolio` | `hybrid`
- `goal`: 학습, 면접 대비, 포트폴리오 설득력 중 우선순위
- `knownGaps`: 내가 잘 모르는 개념이나 불안한 설명

### 출력

- 공개 블로그 글 개선안
- 문제/선택지/결정/검증/트레이드오프 보강 포인트
- `면접에서 설명할 수 있어야 할 질문`
- 개인 답변 노트 생성 안내
- 다음에 직접 실험하거나 복습할 항목
- 스킬 적용/개선 작업이라면 `docs/skill-dogfooding/`의 평가 기록

## 완료 기준

이 패턴이 잘 적용된 글은 아래 조건을 만족한다.

- 글만 읽어도 왜 그 작업을 했는지 알 수 있다.
- 선택하지 않은 방식과 그 이유가 보인다.
- 구현 파일과 검증 명령을 다시 찾아갈 수 있다.
- 트레이드오프가 적혀 있다.
- 내가 모르는 개념이 질문으로 남아 있다.
- 공개 글과 개인 답변 노트가 연결되어 있다.
- 면접에서 30-60초로 설명할 답변을 만들 수 있다.
