> 한 줄 요약: 글을 각 프로젝트 저장소에서 쓰고 블로그는 발행만 담당하게 만들어, 원본과 발행본이 갈라지지 않도록 했다.

## 배경과 문제

이 블로그를 만들면서 가장 먼저 정해야 했던 것은 "글을 어디에 쓰는가"였다. 나는 여러 프로젝트를 동시에 진행하고, 각 프로젝트는 개발하면서 dev-log를 남긴다. 예를 들어 sigak은 세션이 끝날 때마다 `docs/blog`에 그날의 개발 로그를 쓴다.

문제는 이 글들을 블로그로 가져오는 방식이다. 흔한 선택은 블로그 저장소 안에서 직접 글을 쓰는 것이다. 하지만 그러면 같은 글이 두 곳에 존재하게 된다. 프로젝트 저장소의 원본과 블로그의 사본이다. 둘 중 하나를 고치면 다른 하나가 뒤처지고, 시간이 지나면 어느 쪽이 진짜인지 알 수 없게 된다.

dev-log는 특히 이 문제에 취약하다. dev-log의 가치는 "그 세션에서 실제로 일어난 일을 정확히 기록한다"는 데 있는데, 사본을 따로 손대기 시작하면 그 정확성이 무너진다.

## 선택지와 결정

세 가지 방식을 두고 비교했다.

| 방식 | 글을 쓰는 곳 | 단점 |
| --- | --- | --- |
| 블로그에서 직접 작성 | 블로그 저장소 | 원본(프로젝트 dev-log)과 사본이 갈라짐 |
| 수동 복붙 | 프로젝트 → 블로그 | 매번 손으로 옮겨야 하고 누락·표류 발생 |
| one-way sync (선택) | 프로젝트 저장소 | sync 스크립트와 설정이 필요 |

결정은 one-way sync였다. 글의 원본은 항상 각 프로젝트 저장소의 `docs/blog`에 두고, 블로그 저장소의 `src/content/blog/<project>`는 **발행본**으로만 취급한다. 발행본은 절대 직접 수정하지 않는다. 고칠 게 있으면 원본을 고치고 다시 sync한다.

이 결정의 핵심 원칙은 하나다. **한 글에는 source of truth가 하나만 있어야 한다.**

이건 사실 sigak에서 이미 쓰던 사고방식이다. sigak은 PostgreSQL을 source of truth로 두고, Elasticsearch나 Qdrant 같은 검색 저장소는 언제든 다시 만들 수 있는 projection store로 본다. 블로그도 똑같다. 프로젝트의 `docs/blog`가 source of truth이고, 블로그의 발행본은 sync로 다시 만들 수 있는 projection이다. 깨지거나 갈라지면 그냥 다시 sync하면 된다.

## 구현

발행 흐름은 세 단계다.

```txt
프로젝트 docs/blog (원본, source of truth)
  -> npm run sync:posts (draft: false인 글만 복사)
  -> src/content/blog/<project> (발행본, projection)
  -> npm run validate:posts + npm run build (공개 가능 여부 검증)
```

설정은 `posts.config.yml` 한 곳에 모았다. 각 프로젝트의 원본 경로와 포함·제외 규칙을 적는다.

```yaml
sources:
  - project: sigak
    label: Sigak
    path: ${HOME}/my-projects/sigak/docs/blog
    include:
      - "*.md"
    exclude:
      - README.md
      - topic-queue.md
```

sync 스크립트는 이 설정을 읽어 `draft: false`인 글만 발행본으로 복사하고, 원본에서 사라졌거나 `draft: true`로 바뀐 글은 발행본에서 지운다. 즉 발행본은 항상 "현재 공개 대상 원본"의 거울이다.

URL은 프로젝트 slug를 포함하도록 `/blog/[project]/[slug]` 구조로 잡았다. 프로젝트가 늘어나도 파일명이나 slug가 충돌하지 않고, 프로젝트별 글 목록도 자연스럽게 만들어진다.

흥미로운 점은 이 블로그 자신도 하나의 프로젝트로 등록했다는 것이다. 지금 읽는 이 글이 그 증거다. 블로그를 글의 출처 프로젝트로 추가하니, 블로그 개발기도 다른 프로젝트의 dev-log와 똑같은 파이프라인을 탄다.

## 트레이드오프

얻은 것은 명확하다. 글의 출처가 하나로 고정되고, 발행본이 표류할 여지가 없다. 글쓰기는 코드 옆에서 그대로 이어가고, 블로그는 발행에만 집중한다.

미룬 것도 있다. sync가 단방향이라 발행본에서 급하게 오타를 고치는 식의 작업은 막혀 있다. 항상 원본을 거쳐야 한다. 약간 번거롭지만, 이 번거로움이 바로 "발행본을 손대지 마라"는 규칙을 강제하는 장치라 의도적으로 남겨뒀다. URL redirect map도 아직 만들지 않았다. 글이 많아지고 URL 변경 이력이 쌓이면 그때 검토할 일이다.

## 검증

이 글을 쓰면서 실제로 한 작업과 검증은 다음과 같다.

- `src/data/projects.json`에 `yonghyun-blog` 프로젝트를 추가했다.
- `posts.config.yml`의 `sources`에 `yonghyun-blog`를 추가했다(원본 경로 `docs/blog`).
- `npm run new:post -- --project yonghyun-blog --type deep-dive`로 이 글의 초안을 생성했다.

| 영역 | 실행한 명령 | 결과 |
| --- | --- | --- |
| 원본 초안 검증 | `npm run validate:posts -- --source --project yonghyun-blog` | 통과 |
| 발행본 검증 | `npm run validate:posts` | 기존 공개 글 6개 기준 통과 |
| Astro 빌드 | `npm run build` | 기존 공개 글 기준 통과 |

이 글은 아직 `draft: true`라 공개 페이지에는 포함되지 않는다.
