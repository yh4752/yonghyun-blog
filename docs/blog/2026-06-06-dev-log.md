# 2026-06-06 개발 로그: Blog Ops Dashboard를 Folder, Runner, Safe Mutations까지 다듬기

## 요약

오늘은 Blog Ops Dashboard를 v1.2 Folder/Smart View, v1.3 Controlled Runner, v1.4 Safe Mutations까지 이어서 구현했다.

핵심은 대시보드가 글 목록을 단순히 프로젝트별로 나열하는 화면에서, "글을 어떤 묶음으로 보고 어떤 운영 판단을 해야 하는지"를 도와주는 화면으로 한 단계 이동한 것이다.

사용자에게는 `Projects`보다 `Folders`라는 표현이 더 자연스러웠다. 실제 내부 데이터 계약은 여전히 `project`, `activeProject`, `data-project`, `--project`를 사용하지만, 화면에서는 Folder가 글을 묶고 발행 범위를 고르는 단위로 보이게 했다.

또한 Smart View를 추가했다. `All Writing`, `Dev Logs`, `Deep Dives`, `Needs Attention`, `Learning Queue`처럼 자주 쓰는 관점을 버튼으로 두고, 선택한 Folder 위에 겹쳐서 글을 필터링할 수 있게 했다.

이번 작업은 subagent-driven 방식으로 진행했다. 구현만 빠르게 끝내는 것이 아니라, Task별 구현 후 spec review와 code quality review를 반복했다. 덕분에 마지막에 중요한 안전성 문제를 하나 잡았다. Smart View로 깨끗한 글만 보고 있어도, Action Runner의 publish command는 Folder 전체를 대상으로 실행된다. 따라서 runner readiness는 현재 화면에 보이는 Smart View subset이 아니라 Folder 전체를 기준으로 계산해야 했다.

v1.3에서는 preview-only였던 Action Runner를 바로 full publish 실행기로 키우지 않고, `validate-source`와 `publish-dry-run` 두 action만 실행하는 Controlled Runner로 확장했다. 핵심은 "Dashboard에서 버튼을 눌러도 안전한가"를 먼저 검증하는 것이었다.

v1.4에서는 파일을 바꾸는 작업을 처음으로 Dashboard에 올렸다. 단, 바로 저장하지 않고 Safe Edit와 Folder create/delete 모두 preview, hash 검증, dirty state 차단, apply 전 재확인을 거치게 했다. 오늘의 큰 흐름은 "보기 좋은 운영 화면"에서 "실제로 조심스럽게 수정할 수 있는 운영 도구"로 이동한 것이다.

## 오늘 완료한 일

### 1. Folder 용어로 화면을 정리했다

기존 대시보드는 왼쪽 navigation을 `Projects`로 보여줬다. 내부적으로는 맞는 표현이다. 글의 frontmatter에도 `project: "sigak"`이나 `project: "yonghyun-blog"`가 들어간다.

하지만 사용자가 대시보드에서 기대하는 것은 내부 데이터 모델이 아니라 "이 글들이 어떤 묶음에 들어 있는가"다. 앞으로 `notes`, `study`, `life` 같은 비프로젝트성 묶음도 만들 수 있다면, 화면에서는 Folder라는 표현이 더 확장성이 좋다.

그래서 화면에는 다음처럼 보이게 했다.

```txt
Folders
- All Folders
- Sigak
- Yonghyun Blog
```

각 Folder에는 총 글 수, draft 수, pending sync 수를 함께 보여준다. 모바일에서는 이 정보가 길어질 수 있으므로 `text-overflow: ellipsis`, `max-width`, 2줄 구조를 추가했다.

다만 내부 변수까지 전부 `folder`로 바꾸지는 않았다. v1.2에서 내부 이름을 부분적으로 바꾸면 오히려 위험하다. command와 frontmatter 계약은 여전히 `project` 기준이다.

```txt
UI label: Folder
internal state: activeProject
button attribute: data-project
command: --project <slug>
```

이 경계를 유지하는 것이 이번 작업의 첫 번째 기준이었다.

### 2. Smart Views를 추가했다

Folder만으로는 글을 찾기 어렵다. 같은 Folder 안에서도 개발 로그만 보고 싶을 때가 있고, deep-dive만 보고 싶을 때가 있고, 문제가 있는 글만 보고 싶을 때가 있다.

그래서 Smart View를 추가했다.

```txt
All Writing
Dev Logs
Deep Dives
Needs Attention
Learning Queue
```

필터 순서는 아래처럼 정했다.

```txt
Folder -> Smart View -> Content/Learning tab filter
```

예를 들어 `Sigak` Folder에서 `Dev Logs` Smart View를 선택하면 Sigak 글 중 `type: "dev-log"`인 글만 보인다. 그 상태에서 `Learning Ops` 탭으로 가면 dev-log 글의 학습 상태만 볼 수 있다.

Smart View는 아직 단일 선택만 허용한다. 여러 조건을 조합하는 커스텀 뷰는 매력적이지만 v1.2 범위에는 넣지 않았다. 먼저 기본 view가 실제로 충분한지 사용하면서 확인하는 편이 더 안전하다고 봤다.

### 3. 빈 상태에서 잘못된 글이 선택되는 문제를 고쳤다

Smart View를 추가하면서 새로 드러난 문제가 있었다.

특정 Folder와 Smart View 조합에서 글이 0개가 될 수 있다. 예를 들어 `Yonghyun Blog + Needs Attention`은 현재 문제가 있는 글이 없으므로 rows는 비어야 한다.

그런데 기존 `selectedPost()`는 현재 필터 결과가 비어 있으면 전체 글의 첫 번째 글로 fallback했다. 그러면 화면에는 "조건에 맞는 글이 없습니다"가 나오면서 오른쪽 inspector에는 전혀 다른 글이 표시될 수 있다.

이건 운영 도구로서는 위험하다. 사용자가 현재 보고 있는 조건과 inspector가 가리키는 글이 다르면, 잘못된 next action이나 command suggestion을 믿을 수 있다.

그래서 `selectedPost()`는 현재 보이는 글 목록 안에서만 선택하도록 바꿨다. 현재 조합에 글이 없으면 `null`을 반환하고, inspector는 "선택한 글이 없습니다"를 보여준다.

### 4. Action Runner readiness를 Folder 기준으로 고정했다

최종 리뷰에서 가장 중요한 문제가 발견됐다.

처음에는 `operationState()`가 `baseFilteredPosts()`를 사용했다. 이 함수는 Folder뿐 아니라 Smart View까지 적용한 결과를 반환한다.

겉보기에는 자연스럽다. 현재 화면에 보이는 글 기준으로 상태를 계산하는 것처럼 보이기 때문이다.

하지만 Action Runner Preview의 command는 다르다.

```bash
npm run publish:posts -- --project sigak --dry-run
npm run publish:posts -- --project sigak
```

이 명령은 현재 Smart View에 보이는 글만 발행하지 않는다. 선택한 Folder, 즉 내부적으로는 project 전체를 대상으로 한다.

따라서 `Sigak + Dev Logs` 화면에서 dev-log 글들은 깨끗해 보여도, 같은 Sigak Folder 안의 다른 글에 invalid tag나 frontmatter 오류가 있으면 runner는 "준비 완료"라고 말하면 안 된다.

이 문제를 해결하기 위해 범위를 분리했다.

```js
function folderScopedPosts() {
  return allPosts().filter((post) => {
    return state.activeProject === "all" || post.project === state.activeProject;
  });
}

function baseFilteredPosts() {
  return folderScopedPosts().filter((post) => smartViewMatches(post, state.activeSmartView));
}
```

rows, metrics, filter count는 `baseFilteredPosts()`를 쓴다. 사용자가 현재 선택한 Smart View를 반영해야 하기 때문이다.

반면 Action Runner의 readiness는 `folderScopedPosts()`를 쓴다. preview command가 Folder 전체를 대상으로 하기 때문이다.

이 구분이 오늘 작업에서 가장 중요한 설계 포인트였다.

### 5. subagent-driven 방식으로 구현과 리뷰를 분리했다

이번 작업은 구현자 하나가 한 번에 끝낸 것이 아니라, 단계별로 subagent를 붙여서 진행했다.

흐름은 다음과 같았다.

```txt
Task 구현
-> spec compliance review
-> code quality review
-> 지적 사항 반영
-> 다음 Task 진행
```

실제로 리뷰 과정에서 잡힌 문제들이 있었다.

- 모바일 Folder row 테스트가 너무 느슨했다.
- Smart View 빈 결과에서 inspector가 엉뚱한 글을 보여줄 수 있었다.
- UI에 `project slug`라는 내부 용어가 노출되고 있었다.
- Action Runner readiness가 Smart View subset을 기준으로 계산되고 있었다.

이 문제들은 혼자 빠르게 구현했다면 놓쳤을 가능성이 높다. 특히 마지막 runner scope 문제는 테스트가 모두 통과한 뒤 최종 리뷰에서 잡혔다.

### 6. Controlled Runner v1.3을 추가했다

v1.2의 Action Runner는 preview-only였다. 사용자는 Dashboard에서 `publish:posts --dry-run`과 full publish command를 복사할 수 있었지만, 실제 실행은 터미널에서 해야 했다.

v1.3에서는 여기서 한 단계만 더 나아갔다. Dashboard에서 직접 실행할 수 있는 action을 만들되, 파일을 바꾸는 명령은 아직 넣지 않았다.

허용한 action은 두 개다.

```txt
validate-source
-> npm run validate:posts -- --source --project <project>

publish-dry-run
-> npm run publish:posts -- --project <project> --dry-run
```

반대로 아래 action은 의도적으로 제외했다.

```txt
sync:posts
full publish:posts
npm test
npm run build
frontmatter edit
commit / push / PR
```

이 결정의 기준은 단순했다. v1.3은 "Dashboard에서 안전하게 실행할 수 있는가"를 검증하는 단계이고, 파일을 바꾸는 기능은 v1.4 Safe Edit나 이후 단계에서 diff preview와 함께 다루는 것이 맞다.

그래서 브라우저는 서버에 command string을 보내지 않는다. 오직 `{ action, project }`만 보낸다.

```json
{
  "action": "validate-source",
  "project": "sigak"
}
```

서버는 이 값을 받아 allow-list에 있는 argv만 실행한다. 사용자가 브라우저에서 `npm test`, `rm -rf`, 임의 shell command를 넣을 수 있는 입력창은 없다.

### 7. runner API의 안전 경계를 만들었다

v1.3에서 추가한 API는 두 개다.

```txt
GET /api/runner/preflight?project=<project>
POST /api/runner/run
```

`preflight`는 선택한 Folder에서 실행 가능한 action과 warning을 알려준다. `All Folders` 상태에서는 실행하지 못하게 막는다. 이유는 Dashboard의 runner가 project-scoped command를 실행하기 때문이다. 여러 Folder를 한 번에 실행하는 것은 이후 별도 batch 설계가 필요하다.

`run`은 실제 action을 실행한다. 여기서 중요한 점은 서버가 브라우저에서 받은 command를 신뢰하지 않는다는 것이다. 브라우저가 어떤 값을 보내더라도 runner module은 action key를 고정된 command 배열로 변환한다.

```txt
validate-source -> ["run", "validate:posts", "--", "--source", "--project", project]
publish-dry-run -> ["run", "publish:posts", "--", "--project", project, "--dry-run"]
```

또한 한 번에 하나의 action만 실행하도록 lock을 뒀다. 처음 구현에서는 요청 body를 읽기 전에 lock을 잡을 수 있는 위험이 있었다. 느린 partial request가 들어오면 실제 runner는 시작하지 않았는데도 다른 실행이 `409 runner-busy`로 막힐 수 있었다.

리뷰 이후 lock 위치를 바꿨다. JSON body를 읽고 검증한 뒤, 실제 runner를 호출하기 직전에만 `runnerBusy`를 잡는다. 이 수정은 작은 차이처럼 보이지만, 로컬 운영 도구에서도 "실제로 실행 중인 작업"과 "아직 요청을 읽는 중인 연결"을 구분해야 한다는 점을 배웠다.

### 8. Dashboard UI에서 결과 로그를 보여줬다

Controlled Runner 패널은 선택한 Folder에서 실행 가능한 action button을 보여준다.

```txt
Controlled Runner
- Validate source
- Publish dry-run
- Copy dry-run
- Copy publish
```

여기서 full publish는 여전히 copy-only다. 즉, 브라우저 버튼으로 실행할 수 있는 것은 `validate-source`와 `publish-dry-run`뿐이다.

실행 결과는 status, exitCode, command, stdout, stderr, next action으로 보여준다.

```txt
status
failed

exitCode
1

command
npm run validate:posts -- --source --project sigak
```

로그는 무한히 쌓지 않고 stdout/stderr의 최근 32KB만 보여준다. 긴 로그 전체를 파일로 저장하는 기능도 유용할 수 있지만, v1.3에서는 로컬 파일을 새로 만들지 않는 원칙을 유지했다. 전체 로그가 필요하면 copy command로 같은 명령을 터미널에서 다시 실행하면 된다.

### 9. v1.3도 subagent-driven으로 재검토했다

v1.3은 runner module, server API, UI, 문서 갱신을 나눠 진행했다.

각 단계마다 spec review와 code quality review를 붙였다. 그 과정에서 실제로 문제가 잡혔다.

- UTF-8 로그 tail이 멀티바이트 문자를 중간에서 자를 수 있었다.
- timeout 이후 child process lifecycle을 충분히 기다리지 않을 수 있었다.
- slow partial request가 runner lock을 잡을 수 있었다.
- unknown `/api/*` 요청이 HTML dashboard로 fallback될 수 있었다.
- 실행 중 Folder를 바꾸면 이전 Folder의 runner result가 새 Folder에 표시될 수 있었다.
- preflight refresh가 runner 실패 error banner를 지울 수 있었다.

이 문제들은 "기능이 된다" 수준의 테스트만으로는 잘 보이지 않는다. 특히 Folder 변경 중 stale result 문제는 실제 사용자가 버튼을 누르고 바로 다른 Folder를 볼 때 생기는 UI 상태 버그다.

결국 v1.3에서 배운 핵심은 allow-list보다 조금 더 넓다. 명령 실행을 안전하게 만들려면 command string만 막는 것으로는 부족하다. 실행 범위, 요청 body, 동시 실행, 로그 크기, UI 상태 race까지 함께 봐야 한다.

### 10. Safe Mutations v1.4를 설계하고 구현했다

v1.4의 목표는 Dashboard에서 파일을 직접 바꾸는 첫 단계를 여는 것이었다. 하지만 바로 "수정 버튼"을 만드는 것은 위험했다. 지금 블로그는 source post와 published post가 나뉘어 있고, source post가 진짜 원본이다. 잘못 저장하면 발행본만 고치는 사고나, 오래된 화면 상태로 원본을 덮어쓰는 사고가 생길 수 있다.

그래서 v1.4에서는 모든 변경을 Safe Mutation으로 다뤘다.

```txt
read current file
-> calculate sourceHash or metadataHash
-> preview changes
-> show planned operations
-> apply only when the same hash is still valid
```

핵심은 "Dashboard에서 편하게 바꾸되, 사용자가 무엇을 바꾸는지 보기 전에는 저장하지 않는다"는 것이다.

이번 v1.4에서 추가한 mutation은 두 종류다.

```txt
Safe Edit
-> post frontmatter 수정

Folder Management
-> 새 Folder 등록
-> 비어 있는 Folder 삭제
```

새 글 생성, unpublish, tag 정책 편집, full publish 실행은 아직 넣지 않았다. 파일을 바꾸는 범위가 넓어질수록 preview와 rollback 기준이 더 복잡해지기 때문이다.

### 11. Safe Edit는 source post의 frontmatter만 다루게 했다

Safe Edit에서 수정 가능한 필드는 일부로 제한했다.

```txt
title
summary
type
tags
draft
featured
```

반대로 아래 값은 수정하지 못하게 했다.

```txt
project
slug
date
canonicalProjectPath
sourceRepository
relatedPosts
body
```

이 결정은 편의성보다 안전성을 우선한 것이다. 특히 `slug`, `date`, `project`는 URL, 파일 위치, sync 경계와 연결되어 있어서 단순 input으로 바꾸면 영향 범위가 커진다. v1.4에서는 "글 메타데이터를 다듬는 도구"까지만 열고, 글의 정체성이나 위치를 바꾸는 기능은 제외했다.

Safe Edit도 바로 저장하지 않는다. 먼저 source post를 읽고 `sourceHash`를 만든다. Preview는 변경될 frontmatter를 보여주고, Apply는 preview 당시의 `sourceHash`와 현재 파일 hash가 같을 때만 진행한다.

이렇게 하면 Dashboard를 열어둔 사이 파일이 터미널이나 에디터에서 바뀌었을 때, 오래된 화면 상태로 덮어쓰는 일을 막을 수 있다.

### 12. Folder 추가와 빈 Folder 삭제를 안전하게 열었다

Folder 추가는 사실 단순 디렉터리 생성이 아니다. 현재 구조에서는 최소 두 metadata가 같이 움직인다.

```txt
posts.config.yml
src/data/projects.json
```

그리고 source 쪽에는 기본 `docs/blog` setup 파일이 필요하다.

```txt
docs/blog/README.md
docs/blog/topic-queue.md
```

따라서 Folder 생성은 preview에서 어떤 파일과 metadata가 바뀌는지 먼저 보여주게 했다. Apply 단계에서는 `metadataHash`를 다시 확인하고, metadata 쓰기나 setup 파일 생성 중 실패하면 가능한 범위에서 rollback하도록 했다.

Folder 삭제는 더 보수적으로 잡았다. v1.4에서는 "비어 있는 Folder"만 삭제할 수 있다. source post, published post, private learning note, progress manifest, setup 외 custom file이 하나라도 있으면 삭제를 막는다.

삭제도 실제 파일을 바로 지우지 않는다. 기본 동작은 metadata에서 Folder 등록만 제거하는 것이다. source setup folder 제거는 사용자가 명시적으로 선택했을 때만 가능하게 했다.

이 기준은 단순하지만 중요하다.

```txt
글이 있으면 삭제 불가
비어 있으면 unregister 가능
setup folder 삭제는 별도 명시 필요
```

나중에 "글이 있는 Folder를 archive 처리"하거나 "다른 Folder로 이동 후 삭제" 같은 기능을 만들 수는 있지만, v1.4에서는 실수로 기록을 잃지 않는 쪽을 택했다.

### 13. v1.4도 PR, CI, production QA까지 확인했다

v1.4 구현 후에는 브랜치를 PR로 올리고 main에 squash merge했다.

```txt
PR #27 feat: add Blog Ops safe mutations
merge commit: 1e8667a
```

PR CI와 main CI가 모두 통과했고, Vercel production deployment도 성공했다. production에서는 `/`, `/about`, `/blog`가 정상 응답하고 최신 글 목록이 렌더링되는지 확인했다.

Dashboard v1.4 기능은 로컬 도구이므로 production에 직접 노출되지는 않는다. 대신 로컬 Dashboard에서 apply 없이 preview 중심으로 dogfooding했다.

```txt
Safe Edit read/preview
-> 정상

new Folder create preview
-> canApply true, metadataHash 있음

yonghyun-blog Folder delete preview
-> 글이 있어서 canApply false
```

실제 apply를 누르지는 않았다. 오늘은 기능 구현과 안전 장치 검증이 목적이었고, 실제 운영 데이터 변경은 별도 dogfooding 시나리오로 분리하는 편이 맞다고 봤다.

## 설계 고민

### 왜 내부 이름까지 Folder로 바꾸지 않았나

화면에서는 Folder가 자연스럽지만, 내부 계약은 아직 project다.

frontmatter는 `project` 필드를 사용하고, `posts.config.yml`도 project slug 기준으로 source를 찾는다. `sync:posts`, `publish:posts`도 `--project` 옵션을 사용한다.

이 상태에서 일부 변수만 `folder`로 바꾸면, 오히려 더 헷갈릴 수 있다.

```txt
project frontmatter
project command
folder UI
folder variable 일부
project variable 일부
```

이런 반쯤 바뀐 구조가 더 위험하다. 그래서 v1.2에서는 사용자에게 보이는 언어만 Folder로 바꾸고, 내부 계약은 그대로 유지했다. 나중에 정말 `collection`이나 `folder` 모델로 확장할 때 전체 rename을 별도 작업으로 다루는 편이 낫다.

### 왜 Smart View를 단일 선택으로 제한했나

처음부터 커스텀 Smart View나 다중 조건 조합을 넣을 수도 있었다.

예를 들어 `Sigak + Deep Dives + Needs Attention + Learning Queue`처럼 여러 조건을 조합하면 강력하다. 하지만 지금 필요한 것은 복잡한 검색기가 아니라 자주 쓰는 관점을 빠르게 전환하는 것이다.

그래서 v1.2에서는 named predicate 기반의 단일 Smart View만 만들었다.

```js
{
  key: "dev-log",
  label: "Dev Logs",
  matches: (post) => post.type === "dev-log",
}
```

이 구조라면 나중에 조합형 view를 만들 때도 같은 predicate를 재사용할 수 있다. 지금은 UI와 상태 모델을 단순하게 유지하고, 실제 사용 중 조합 요구가 반복되는지 관찰하기로 했다.

### 왜 runner readiness는 현재 화면 기준이 아닌가

대시보드에서 사용자가 보는 글과 Action Runner가 처리하는 글의 범위가 다를 수 있다. 이것이 오늘 가장 중요하게 배운 점이다.

rows는 현재 화면의 선택을 따라야 한다. 사용자가 Smart View를 켰으면 그 view에 맞는 글만 보여주는 것이 맞다.

하지만 runner는 command의 실제 영향 범위를 따라야 한다. `publish:posts -- --project sigak`는 Smart View를 모른다. 따라서 readiness도 Smart View를 몰라야 안전하다.

이 원칙은 나중에 실제 실행 버튼을 붙일 때 더 중요해질 것 같다. 버튼이 실행하는 명령과 UI가 보여주는 범위가 다르면, 사용자는 예상하지 못한 글까지 변경될 수 있다.

### 왜 v1.3에서 실행 action을 두 개만 허용했나

Dashboard에서 버튼을 누르는 경험은 편하다. 하지만 편하다는 이유만으로 바로 `sync:posts`나 full publish를 실행하면 위험하다.

`validate-source`와 `publish-dry-run`은 파일을 바꾸지 않는다. 실패해도 사용자가 고쳐야 할 문제를 알려줄 뿐이다. 그래서 runner API, allow-list, 로그 표시, 동시 실행 방지, UI 상태 관리를 먼저 검증하기에 적합했다.

반면 `sync:posts`는 발행본을 바꾼다. full publish는 sync, validation, test, build를 묶어서 실행한다. 이 단계는 변경 파일 preview, dirty state 확인, diff 확인, 실행 후 rollback 판단이 함께 필요하다.

그래서 v1.3은 실행 기반을 검증하는 단계로 제한했다.

```txt
v1.3: 파일을 바꾸지 않는 runner 실행
v1.4: Safe Edit + 저장 전 diff preview
later: sync/full publish/PR assistant
```

이렇게 나누면 Dashboard가 점점 강력해져도 각 단계의 위험을 따로 검증할 수 있다.

### 왜 브라우저에서 command string을 보내지 않았나

처음 생각하면 Dashboard 버튼에 command를 넣고 서버가 그대로 실행하면 단순해 보인다.

하지만 그렇게 하면 Dashboard가 작은 shell executor가 된다. UI에 보이지 않는 곳에서 command가 조작되거나, 나중에 기능을 붙이다가 임의 명령 실행 경계가 흐려질 수 있다.

그래서 브라우저는 command를 보내지 않는다.

```txt
browser -> { action, project }
server -> allow-list lookup
server -> fixed npm argv
```

이 구조에서는 action 이름이 늘어날 때마다 서버의 allow-list에 명시적으로 추가해야 한다. 번거롭지만, 운영 도구에서는 이 번거로움이 안전 장치가 된다.

### 왜 Safe Edit를 runner endpoint에 붙이지 않았나

v1.3 runner는 "정해진 명령을 실행하는 기능"이다. 입력은 `{ action, project }`이고, 서버는 action을 고정된 argv로 바꾼다.

반면 Safe Edit는 "파일 내용을 바꾸는 기능"이다. 입력은 command가 아니라 변경하려는 frontmatter 값이고, 저장 전에는 현재 파일 hash와 preview 결과를 비교해야 한다.

둘을 같은 endpoint에 붙이면 책임이 섞인다.

```txt
runner endpoint
-> allowed command 실행

safe edit endpoint
-> file read/preview/hash/apply
```

그래서 v1.4에서는 Safe Edit를 runner의 action 중 하나로 넣지 않았다. 별도 endpoint로 분리하고, preview/apply 규칙도 별도로 만들었다. 이 덕분에 runner는 여전히 작은 allow-list command runner로 남고, Safe Edit는 파일 mutation 전용 안전 규칙을 가질 수 있었다.

### 왜 hash 검증을 넣었나

Dashboard는 브라우저 화면이다. 사용자가 글을 열어둔 뒤, 같은 파일을 에디터나 터미널에서 고칠 수 있다. 이 상태에서 Dashboard가 예전 내용을 기준으로 저장하면 최신 변경을 덮어쓸 수 있다.

그래서 Safe Edit는 `sourceHash`, Folder create/delete는 `metadataHash`를 사용한다.

```txt
preview 때 본 hash
apply 직전 다시 읽은 hash
둘이 다르면 stale 상태로 차단
```

이 방식은 협업 도구의 optimistic concurrency control과 비슷하다. lock을 오래 잡는 대신, 저장 직전에 "내가 보고 있는 버전이 아직 최신인가"를 확인한다.

### 왜 Folder 삭제를 비어 있을 때만 허용했나

삭제 기능은 만들기 쉽지만, 운영 도구에서 가장 위험한 기능이기도 하다. 특히 블로그의 Folder는 단순 UI 그룹이 아니라 source post, published post, private learning note, progress manifest와 연결될 수 있다.

그래서 v1.4에서는 삭제를 "정리"가 아니라 "비어 있는 등록 해제"로 제한했다. 글이 하나라도 있으면 막고, 사용자가 직접 글을 옮기거나 정리한 뒤에만 Folder를 지울 수 있게 했다.

이 방식은 기능적으로는 덜 편하지만, 기록을 잃지 않는다는 점에서 지금 단계에 맞다.

## 트레이드오프

Folder 용어를 도입하면서 화면은 더 직관적이 됐다. 대신 내부 `project` 계약과 화면 `Folder` 용어가 함께 존재한다. 이 경계는 문서와 테스트로 계속 관리해야 한다.

Smart View는 글을 훨씬 빨리 찾게 해준다. 하지만 현재는 단일 선택만 가능하다. 복잡한 조건 조합은 일부러 미뤘다.

subagent-driven 방식은 품질이 좋아졌다. 특히 spec review와 quality review를 분리한 점이 효과적이었다. 대신 시간이 더 걸리고, 리뷰에서 나온 지적을 문서와 테스트까지 반영해야 하므로 작업량이 늘어난다.

Controlled Runner는 편의성을 크게 올렸다. 터미널로 가지 않아도 source validation과 publish dry-run을 실행할 수 있다. 대신 Dashboard 서버가 child process를 실행하는 책임을 갖게 됐다. 그래서 allow-list, project 검증, timeout, 로그 제한, 동시 실행 lock이 함께 필요해졌다.

또한 v1.3은 일부러 파일 변경 action을 넣지 않았다. 이 결정은 사용성을 제한하지만, Safe Edit와 diff preview가 없는 상태에서 발행본을 바꾸는 버튼을 먼저 만드는 것보다 낫다.

v1.4 Safe Mutations는 편의성을 더 올렸다. 이제 draft toggle, summary 수정, tag 수정, Folder 생성/삭제를 Dashboard에서 시작할 수 있다. 대신 구현은 훨씬 복잡해졌다. preview와 apply를 나눠야 했고, hash stale 검증, dirty metadata 차단, rollback, confirmation, invalid tag 표시까지 함께 봐야 했다.

Folder 삭제를 빈 Folder로 제한한 것도 트레이드오프다. 사용자는 당장 글이 있는 Folder를 한 번에 정리할 수 없다. 하지만 실수로 source post나 private learning note를 잃는 위험을 v1.4 범위에서 감수하지 않기로 했다.

테스트도 일부는 source-string 기반이다. HTML template dashboard라서 구조를 빠르게 보호하기에는 유용하지만, 장기적으로는 상태 계산 함수를 더 작게 분리해 runtime test를 늘리는 편이 좋을 수 있다.

| main CI | merge commit `1e8667a` 기준 CI 성공 |
| Vercel production | production deployment success, `/`, `/about`, `/blog` 정상 응답 확인 |

이 검증에서 중요한 것은 단순히 테스트가 통과했다는 점이 아니다. 테스트가 모두 통과한 뒤에도 최종 리뷰에서 runner scope 문제가 발견됐고, 그 문제를 브라우저 시나리오로 다시 검증했다.

v1.3 dogfooding에서 `validate-source`가 실패한 것도 기능 실패가 아니었다. 오히려 Dashboard가 원본 글의 frontmatter 누락을 버튼 실행 결과로 바로 보여준 사례다. 이전에는 터미널에서 명령을 직접 실행해야 알 수 있었던 문제를, 이제 Dashboard 안에서 확인할 수 있다.

v1.4 dogfooding은 실제 apply 대신 preview 중심으로 진행했다. Safe Mutations의 apply path는 테스트로 검증했지만, 운영 데이터에 실제 변경을 만드는 dogfooding은 다음 단계에서 더 작은 disposable Folder 시나리오로 분리하는 편이 맞다고 봤다.

## 내가 이해한 것

이번 작업을 통해 "필터링"과 "명령의 영향 범위"는 같은 말이 아니라는 점을 배웠다.

UI 필터는 사용자가 보고 싶은 subset을 고르는 장치다. 하지만 command는 실제로 파일과 발행 상태를 바꾸는 범위를 가진다. 두 범위가 다르면, 안전성 판단은 command 쪽을 따라야 한다.

또 하나 배운 점은 사용자 용어와 내부 계약을 한 번에 바꾸지 않아도 된다는 것이다. 화면에서는 Folder가 더 좋은 표현이지만, 내부 `project` 계약은 이미 frontmatter, config, CLI 명령과 연결되어 있다. 이럴 때는 "사용자에게 무엇을 보여줄 것인가"와 "시스템 내부 계약을 언제 바꿀 것인가"를 분리해서 생각해야 한다.

subagent-driven 방식도 학습 포인트였다. 구현자와 리뷰어를 분리하면 귀찮아 보이지만, 실제로는 내가 놓친 경계를 더 빨리 발견하게 해준다. 특히 "테스트는 통과하지만 의미상 위험한 상태"를 잡는 데 도움이 됐다.

v1.3에서는 "실행 버튼"이 단순히 편의 기능이 아니라는 점을 배웠다. 버튼 하나를 추가하려면 그 버튼이 실제로 어떤 범위에 영향을 주는지, 사용자가 보고 있는 화면과 실행 범위가 일치하는지, 실패했을 때 충분한 근거를 보여주는지까지 확인해야 한다.

또 하나 이해한 것은 allow-list의 의미다. allow-list는 단지 보안 용어가 아니라, 운영 도구에서 책임 경계를 코드로 고정하는 방식이다. 브라우저는 action intent만 보내고, 서버가 허용된 command만 선택한다. 이 구조 덕분에 UI가 복잡해져도 runner가 임의 shell executor로 변하지 않는다.

v1.4에서는 "파일을 바꿀 수 있는 UI"가 단순 CRUD가 아니라는 점을 배웠다. 수정 폼을 만드는 것보다 중요한 것은 사용자가 어떤 파일을 기준으로 보고 있는지, 그 파일이 아직 최신인지, 저장 전 어떤 diff가 생기는지, 실패하면 어디까지 되돌릴 수 있는지다.

또 하나 배운 점은 삭제 기능의 범위를 작게 시작하는 것이 안전하다는 것이다. Folder 삭제를 모든 정리 작업으로 키우지 않고, 비어 있는 Folder unregister로 제한하니 정책이 명확해졌다. 기능은 작아졌지만 설명 가능성은 좋아졌다.

## 남은 문제

`type: "note"`도 아직 없다. 일상 포스트나 학습 메모를 넣고 싶다면 type 정책과 tag 정책을 먼저 정해야 한다.

Smart View는 아직 단일 선택이다. 실제 사용 중 `Needs Attention + Deep Dives` 같은 조합 요구가 반복되면 커스텀 view를 검토할 수 있다.

Action Runner는 이제 preview-only가 아니다. 다만 실행 가능한 action은 파일을 바꾸지 않는 `validate-source`, `publish-dry-run`으로 제한되어 있다. `sync:posts`, full publish, test/build 실행은 아직 Dashboard 버튼으로 제공하지 않는다.

Safe Edit와 Folder create/delete는 구현했지만, 실제 운영 데이터에 apply하는 dogfooding은 아직 조심스럽게 남겨뒀다. 특히 disposable Folder를 만들고 지우는 시나리오는 v1.5 전에 별도로 한 번 더 확인하는 편이 좋다.

브라우저 상호작용 테스트도 아직 약하다. Safe Mutations UI는 문자열 기반 template test와 API test로 많이 보호했지만, 실제 DOM event 흐름을 Playwright 같은 도구로 확인하는 테스트는 다음 후보로 남았다.

Dashboard에서 `validate-source`를 실행해 보니 Sigak 원본 `2026-06-05-dev-log.md`에 frontmatter가 없다는 문제가 드러났다. 이 글 자체의 범위는 yonghyun-blog Dashboard v1.3이지만, 다음 실제 운영 작업에서는 해당 source post도 정리해야 한다.
