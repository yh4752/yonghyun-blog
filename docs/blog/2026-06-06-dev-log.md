# 2026-06-06 개발 로그: Blog Ops Dashboard를 Folder와 Smart View 중심으로 다듬기

## 요약

오늘은 Blog Ops Dashboard v1.2를 구현했다.

핵심은 대시보드가 글 목록을 단순히 프로젝트별로 나열하는 화면에서, "글을 어떤 묶음으로 보고 어떤 운영 판단을 해야 하는지"를 도와주는 화면으로 한 단계 이동한 것이다.

사용자에게는 `Projects`보다 `Folders`라는 표현이 더 자연스러웠다. 실제 내부 데이터 계약은 여전히 `project`, `activeProject`, `data-project`, `--project`를 사용하지만, 화면에서는 Folder가 글을 묶고 발행 범위를 고르는 단위로 보이게 했다.

또한 Smart View를 추가했다. `All Writing`, `Dev Logs`, `Deep Dives`, `Needs Attention`, `Learning Queue`처럼 자주 쓰는 관점을 버튼으로 두고, 선택한 Folder 위에 겹쳐서 글을 필터링할 수 있게 했다.

이번 작업은 subagent-driven 방식으로 진행했다. 구현만 빠르게 끝내는 것이 아니라, Task별 구현 후 spec review와 code quality review를 반복했다. 덕분에 마지막에 중요한 안전성 문제를 하나 잡았다. Smart View로 깨끗한 글만 보고 있어도, Action Runner의 publish command는 Folder 전체를 대상으로 실행된다. 따라서 runner readiness는 현재 화면에 보이는 Smart View subset이 아니라 Folder 전체를 기준으로 계산해야 했다.

## 오늘 완료한 일

### 1. Folder 용어로 화면을 정리했다

기존 대시보드는 왼쪽 navigation을 `Projects`로 보여줬다. 내부적으로는 맞는 표현이다. 글의 frontmatter에도 `project: "sigak"`이나 `project: "yonghyun-blog"`가 들어간다.

하지만 사용자가 대시보드에서 기대하는 것은 내부 데이터 모델이 아니라 "이 글들이 어떤 묶음에 들어 있는가"다. 앞으로 `notes`, `study`, `life` 같은 비프로젝트성 묶음도 만들 수 있다면, 화면에서는 Folder라는 표현이 더 확장성이 좋다.

그래서 화면에는 다음처럼 보이게 했다.

```txt
Folders
- All Folders
- Sigak
- Yonghyun Blog
```

각 Folder에는 총 글 수, draft 수, pending sync 수를 함께 보여준다. 모바일에서는 이 정보가 길어질 수 있으므로 `text-overflow: ellipsis`, `max-width`, 2줄 구조를 추가했다.

다만 내부 변수까지 전부 `folder`로 바꾸지는 않았다. v1.2에서 내부 이름을 부분적으로 바꾸면 오히려 위험하다. command와 frontmatter 계약은 여전히 `project` 기준이다.

```txt
UI label: Folder
internal state: activeProject
button attribute: data-project
command: --project <slug>
```

이 경계를 유지하는 것이 이번 작업의 첫 번째 기준이었다.

### 2. Smart Views를 추가했다

Folder만으로는 글을 찾기 어렵다. 같은 Folder 안에서도 개발 로그만 보고 싶을 때가 있고, deep-dive만 보고 싶을 때가 있고, 문제가 있는 글만 보고 싶을 때가 있다.

그래서 Smart View를 추가했다.

```txt
All Writing
Dev Logs
Deep Dives
Needs Attention
Learning Queue
```

필터 순서는 아래처럼 정했다.

```txt
Folder -> Smart View -> Content/Learning tab filter
```

예를 들어 `Sigak` Folder에서 `Dev Logs` Smart View를 선택하면 Sigak 글 중 `type: "dev-log"`인 글만 보인다. 그 상태에서 `Learning Ops` 탭으로 가면 dev-log 글의 학습 상태만 볼 수 있다.

Smart View는 아직 단일 선택만 허용한다. 여러 조건을 조합하는 커스텀 뷰는 매력적이지만 v1.2 범위에는 넣지 않았다. 먼저 기본 view가 실제로 충분한지 사용하면서 확인하는 편이 더 안전하다고 봤다.

### 3. 빈 상태에서 잘못된 글이 선택되는 문제를 고쳤다

Smart View를 추가하면서 새로 드러난 문제가 있었다.

특정 Folder와 Smart View 조합에서 글이 0개가 될 수 있다. 예를 들어 `Yonghyun Blog + Needs Attention`은 현재 문제가 있는 글이 없으므로 rows는 비어야 한다.

그런데 기존 `selectedPost()`는 현재 필터 결과가 비어 있으면 전체 글의 첫 번째 글로 fallback했다. 그러면 화면에는 "조건에 맞는 글이 없습니다"가 나오면서 오른쪽 inspector에는 전혀 다른 글이 표시될 수 있다.

이건 운영 도구로서는 위험하다. 사용자가 현재 보고 있는 조건과 inspector가 가리키는 글이 다르면, 잘못된 next action이나 command suggestion을 믿을 수 있다.

그래서 `selectedPost()`는 현재 보이는 글 목록 안에서만 선택하도록 바꿨다. 현재 조합에 글이 없으면 `null`을 반환하고, inspector는 "선택한 글이 없습니다"를 보여준다.

### 4. Action Runner readiness를 Folder 기준으로 고정했다

최종 리뷰에서 가장 중요한 문제가 발견됐다.

처음에는 `operationState()`가 `baseFilteredPosts()`를 사용했다. 이 함수는 Folder뿐 아니라 Smart View까지 적용한 결과를 반환한다.

겉보기에는 자연스럽다. 현재 화면에 보이는 글 기준으로 상태를 계산하는 것처럼 보이기 때문이다.

하지만 Action Runner Preview의 command는 다르다.

```bash
npm run publish:posts -- --project sigak --dry-run
npm run publish:posts -- --project sigak
```

이 명령은 현재 Smart View에 보이는 글만 발행하지 않는다. 선택한 Folder, 즉 내부적으로는 project 전체를 대상으로 한다.

따라서 `Sigak + Dev Logs` 화면에서 dev-log 글들은 깨끗해 보여도, 같은 Sigak Folder 안의 다른 글에 invalid tag나 frontmatter 오류가 있으면 runner는 "준비 완료"라고 말하면 안 된다.

이 문제를 해결하기 위해 범위를 분리했다.

```js
function folderScopedPosts() {
  return allPosts().filter((post) => {
    return state.activeProject === "all" || post.project === state.activeProject;
  });
}

function baseFilteredPosts() {
  return folderScopedPosts().filter((post) => smartViewMatches(post, state.activeSmartView));
}
```

rows, metrics, filter count는 `baseFilteredPosts()`를 쓴다. 사용자가 현재 선택한 Smart View를 반영해야 하기 때문이다.

반면 Action Runner의 readiness는 `folderScopedPosts()`를 쓴다. preview command가 Folder 전체를 대상으로 하기 때문이다.

이 구분이 오늘 작업에서 가장 중요한 설계 포인트였다.

### 5. subagent-driven 방식으로 구현과 리뷰를 분리했다

이번 작업은 구현자 하나가 한 번에 끝낸 것이 아니라, 단계별로 subagent를 붙여서 진행했다.

흐름은 다음과 같았다.

```txt
Task 구현
-> spec compliance review
-> code quality review
-> 지적 사항 반영
-> 다음 Task 진행
```

실제로 리뷰 과정에서 잡힌 문제들이 있었다.

- 모바일 Folder row 테스트가 너무 느슨했다.
- Smart View 빈 결과에서 inspector가 엉뚱한 글을 보여줄 수 있었다.
- UI에 `project slug`라는 내부 용어가 노출되고 있었다.
- Action Runner readiness가 Smart View subset을 기준으로 계산되고 있었다.

이 문제들은 혼자 빠르게 구현했다면 놓쳤을 가능성이 높다. 특히 마지막 runner scope 문제는 테스트가 모두 통과한 뒤 최종 리뷰에서 잡혔다.

## 설계 고민

### 왜 내부 이름까지 Folder로 바꾸지 않았나

화면에서는 Folder가 자연스럽지만, 내부 계약은 아직 project다.

frontmatter는 `project` 필드를 사용하고, `posts.config.yml`도 project slug 기준으로 source를 찾는다. `sync:posts`, `publish:posts`도 `--project` 옵션을 사용한다.

이 상태에서 일부 변수만 `folder`로 바꾸면, 오히려 더 헷갈릴 수 있다.

```txt
project frontmatter
project command
folder UI
folder variable 일부
project variable 일부
```

이런 반쯤 바뀐 구조가 더 위험하다. 그래서 v1.2에서는 사용자에게 보이는 언어만 Folder로 바꾸고, 내부 계약은 그대로 유지했다. 나중에 정말 `collection`이나 `folder` 모델로 확장할 때 전체 rename을 별도 작업으로 다루는 편이 낫다.

### 왜 Smart View를 단일 선택으로 제한했나

처음부터 커스텀 Smart View나 다중 조건 조합을 넣을 수도 있었다.

예를 들어 `Sigak + Deep Dives + Needs Attention + Learning Queue`처럼 여러 조건을 조합하면 강력하다. 하지만 지금 필요한 것은 복잡한 검색기가 아니라 자주 쓰는 관점을 빠르게 전환하는 것이다.

그래서 v1.2에서는 named predicate 기반의 단일 Smart View만 만들었다.

```js
{
  key: "dev-log",
  label: "Dev Logs",
  matches: (post) => post.type === "dev-log",
}
```

이 구조라면 나중에 조합형 view를 만들 때도 같은 predicate를 재사용할 수 있다. 지금은 UI와 상태 모델을 단순하게 유지하고, 실제 사용 중 조합 요구가 반복되는지 관찰하기로 했다.

### 왜 runner readiness는 현재 화면 기준이 아닌가

대시보드에서 사용자가 보는 글과 Action Runner가 처리하는 글의 범위가 다를 수 있다. 이것이 오늘 가장 중요하게 배운 점이다.

rows는 현재 화면의 선택을 따라야 한다. 사용자가 Smart View를 켰으면 그 view에 맞는 글만 보여주는 것이 맞다.

하지만 runner는 command의 실제 영향 범위를 따라야 한다. `publish:posts -- --project sigak`는 Smart View를 모른다. 따라서 readiness도 Smart View를 몰라야 안전하다.

이 원칙은 나중에 실제 실행 버튼을 붙일 때 더 중요해질 것 같다. 버튼이 실행하는 명령과 UI가 보여주는 범위가 다르면, 사용자는 예상하지 못한 글까지 변경될 수 있다.

## 트레이드오프

Folder 용어를 도입하면서 화면은 더 직관적이 됐다. 대신 내부 `project` 계약과 화면 `Folder` 용어가 함께 존재한다. 이 경계는 문서와 테스트로 계속 관리해야 한다.

Smart View는 글을 훨씬 빨리 찾게 해준다. 하지만 현재는 단일 선택만 가능하다. 복잡한 조건 조합은 일부러 미뤘다.

subagent-driven 방식은 품질이 좋아졌다. 특히 spec review와 quality review를 분리한 점이 효과적이었다. 대신 시간이 더 걸리고, 리뷰에서 나온 지적을 문서와 테스트까지 반영해야 하므로 작업량이 늘어난다.

테스트도 일부는 source-string 기반이다. HTML template dashboard라서 구조를 빠르게 보호하기에는 유용하지만, 장기적으로는 상태 계산 함수를 더 작게 분리해 runtime test를 늘리는 편이 좋을 수 있다.

## 검증

이번 작업은 다음 명령과 브라우저 QA로 확인했다.

| 검증 | 결과 |
| --- | --- |
| `node --test scripts/blog-ops-dashboard.test.mjs` | 12개 dashboard 테스트 통과 |
| `npm test` | 63개 테스트 통과 |
| `npm run validate:posts` | 발행본 26개 검증 통과 |
| `npm run build` | Astro check 0 errors, 0 warnings, 0 hints / 37페이지 빌드 |
| Browser QA desktop | Folder/Smart View 표시, command preview, console error 없음 |
| Browser QA mobile `430x932` | body overflow 없음, Folder/Smart View/Content Filter가 가로 스크롤 행으로 유지됨 |
| Runner scope 회귀 확인 | `Sigak + Dev Logs`에서 rows는 10개지만 runner는 Folder 전체 경고를 보고 `Blocked at validate:source` 유지 |

이 검증에서 중요한 것은 단순히 테스트가 통과했다는 점이 아니다. 테스트가 모두 통과한 뒤에도 최종 리뷰에서 runner scope 문제가 발견됐고, 그 문제를 브라우저 시나리오로 다시 검증했다.

## 내가 이해한 것

이번 작업을 통해 "필터링"과 "명령의 영향 범위"는 같은 말이 아니라는 점을 배웠다.

UI 필터는 사용자가 보고 싶은 subset을 고르는 장치다. 하지만 command는 실제로 파일과 발행 상태를 바꾸는 범위를 가진다. 두 범위가 다르면, 안전성 판단은 command 쪽을 따라야 한다.

또 하나 배운 점은 사용자 용어와 내부 계약을 한 번에 바꾸지 않아도 된다는 것이다. 화면에서는 Folder가 더 좋은 표현이지만, 내부 `project` 계약은 이미 frontmatter, config, CLI 명령과 연결되어 있다. 이럴 때는 "사용자에게 무엇을 보여줄 것인가"와 "시스템 내부 계약을 언제 바꿀 것인가"를 분리해서 생각해야 한다.

subagent-driven 방식도 학습 포인트였다. 구현자와 리뷰어를 분리하면 귀찮아 보이지만, 실제로는 내가 놓친 경계를 더 빨리 발견하게 해준다. 특히 "테스트는 통과하지만 의미상 위험한 상태"를 잡는 데 도움이 됐다.

## Codex에게 맡긴 것과 내가 검토한 것

Codex에게 맡긴 것은 다음과 같다.

- v1.2 구현 계획을 Task 단위로 실행
- Folder UI와 Smart View 구현
- dashboard test 보강
- subagent spec/code quality review 진행
- 브라우저 QA와 검증 명령 실행
- 이 dev-log 초안 작성

내가 검토해야 하는 것은 다음과 같다.

- 화면에서 Folder라는 표현이 실제로 덜 헷갈리는가?
- 내부 `project` 계약을 유지하는 결정이 타당한가?
- Smart View가 실제 사용에서 충분한가, 아니면 조합형 view가 필요한가?
- runner readiness를 Folder 기준으로 둔 이유를 내 말로 설명할 수 있는가?
- 실제 실행 버튼을 붙일 때 어떤 안전 장치가 필요한가?

## 남은 문제

Folder 추가/삭제는 아직 구현하지 않았다. Empty Folder 삭제는 안전하게 할 수 있어 보이지만, 그 전에 Folder를 화면에서 안정적으로 보여주고 필터링하는 구조가 먼저 필요했다.

`type: "note"`도 아직 없다. 일상 포스트나 학습 메모를 넣고 싶다면 type 정책과 tag 정책을 먼저 정해야 한다.

Smart View는 아직 단일 선택이다. 실제 사용 중 `Needs Attention + Deep Dives` 같은 조합 요구가 반복되면 커스텀 view를 검토할 수 있다.

Action Runner도 아직 실행 버튼이 아니라 preview-only다. 실제 실행 버튼을 붙이려면 allow-list, dirty state check, diff preview, 로그 panel이 먼저 필요하다.
