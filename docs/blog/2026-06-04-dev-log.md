# 2026-06-04 개발 로그: 블로그 운영 대시보드와 발행 루틴 다듬기

## 요약

오늘은 블로그를 "글을 쓰는 사이트"에서 한 단계 더 나아가 "글의 상태를 보고, 검증하고, 발행 루틴을 관리하는 작업대"로 다듬은 날이다.

핵심은 두 가지였다.

첫째, Blog Ops Dashboard를 단순한 보기 화면이 아니라 운영 판단을 돕는 로컬 도구로 정리했다. 어떤 글이 원본에만 있는지, 발행본에만 남아 있는지, 학습 질문 세트가 준비됐는지, draft 글도 학습 대상으로 올릴 수 있는지 같은 상태를 한 화면에서 확인하려는 목적이다.

둘째, 발행 과정을 `publish:posts` 명령으로 묶었다. 글을 가져오고, frontmatter와 편집 정책을 검증하고, 테스트와 빌드를 거쳐야 한다는 규칙은 이미 있었지만, 매번 사람이 순서를 기억해서 실행하는 방식은 실수하기 쉬웠다. 그래서 프로젝트 단위로 안전한 발행 체인을 실행하는 명령을 추가했다.

## 오늘 완료한 일

### Blog Ops Dashboard 사용 기록 정리

먼저 실제 대시보드를 실행해서 현재 블로그 상태를 점검했다.

`npm run ops:dashboard`로 로컬 대시보드를 띄우고, `/api/inventory`를 통해 글 목록과 상태가 어떻게 수집되는지 확인했다. 이 과정에서 `sigak`, `yonghyun-blog` 두 프로젝트의 글 상태가 함께 보였고, 발행본만 남은 글, source에만 있는 draft 글, learning 질문 세트가 준비된 글을 구분해서 볼 수 있었다.

여기서 중요한 점은 대시보드가 "수정 화면"이 아니라 "판단 화면"으로 먼저 자리 잡아야 한다는 것이었다. 바로 CRUD를 붙이면 편해 보이지만, source of truth가 어디인지 흐려지고, 검증 없이 발행본을 고치는 위험이 생긴다.

### Safe CRUD 경계 보강

대시보드 설계 문서에 안전한 수정 범위를 추가했다.

허용한 방향은 다음과 같다.

- 원본 글은 각 프로젝트의 `docs/blog`에서 수정한다.
- `src/content/blog`의 발행본은 직접 수정하지 않는다.
- 수정 전에는 diff preview를 보여준다.
- 실행 가능한 명령은 allow-list로 제한한다.
- dirty git state와 main 직접 push를 경고한다.
- private note의 본문은 대시보드에 노출하지 않는다.

이 기준을 세운 이유는 블로그 운영을 편하게 만들면서도, 글의 신뢰성을 깨지 않기 위해서다. 특히 이 블로그는 포트폴리오와 학습 기록을 겸하기 때문에 "어떻게 발행됐는가"도 결과물의 일부라고 봤다.

### Claude 디자인을 실제 대시보드에 반영

Claude Design에서 받은 `Blog Ops Dashboard.html` 방향을 바탕으로 로컬 대시보드 UI를 새로 적용했다.

원래 대시보드는 기능 확인에 가까웠다. 오늘 반영한 버전은 macOS의 시스템 도구처럼 보이도록 정리했다. 왼쪽에는 프로젝트와 전체 지표를 두고, 가운데에는 Content Ops와 Learning Ops 탭을 배치했으며, 오른쪽 inspector에서 선택한 글의 상태와 다음 행동을 볼 수 있게 했다.

다만 디자인 파일을 그대로 붙인 것은 아니다. 실제 대시보드는 `/api/inventory`에서 수집한 데이터를 사용해야 하고, source/published/learning 상태를 현재 정책과 맞춰 보여줘야 한다. 그래서 HTML mockup의 분위기는 가져오되, 데이터 연결과 상태 해석은 기존 스크립트 구조에 맞춰 다시 정리했다.

### `publish:posts` 명령 추가

발행 루틴을 줄이기 위해 `publish:posts` 명령을 추가했다.

이 명령은 프로젝트를 지정해서 다음 순서를 실행한다.

```bash
npm run publish:posts -- --project yonghyun-blog
```

내부 흐름은 다음과 같다.

1. source 글 검증
2. 프로젝트 단위 sync
3. 발행본 검증
4. 테스트 실행
5. Astro 빌드

이전에는 이 과정을 사람이 각각 실행해야 했다. 그러면 `sync`만 하고 `build`를 빼먹거나, source 검증 없이 발행본만 확인하는 식의 실수가 생길 수 있다. 하나의 명령으로 묶으면 발행 전 검증 체인이 더 선명해진다.

### Sigak 글 동기화 흐름 점검

Sigak 쪽 6/4 dev-log도 정리하고 발행본과 맞췄다.

이 작업은 단순한 글 추가라기보다, 실제로 다중 프로젝트 블로그 구조가 작동하는지 확인하는 dogfooding에 가까웠다. `sigak`의 원본 `docs/blog`에서 쓴 글이 `yonghyun-blog`의 `src/content/blog/sigak`으로 들어오고, 태그와 frontmatter 정책을 통과하는지를 확인했다.

이 과정에서 블로그가 특정 프로젝트 하나에 고정된 것이 아니라, 앞으로 다른 프로젝트의 개발 기록도 같은 방식으로 모을 수 있다는 점을 다시 확인했다.

## 설계 고민

### 왜 바로 브라우저 CRUD로 가지 않았나

처음에는 글 수정, 비공개 처리, 발행 같은 작업을 블로그 안에서 바로 할 수 있으면 좋겠다고 생각했다. 실제로 그 방향은 장기 목표로 유효하다.

하지만 지금 바로 브라우저 CRUD를 붙이면 위험한 부분이 많다. 발행본을 직접 고칠 수 있게 되면 원본 글과 발행본이 달라지고, 그 차이가 나중에 추적되지 않을 수 있다. 또한 검증 없이 글이 바뀌면 frontmatter 오류나 태그 오류가 배포 뒤에 발견될 수 있다.

그래서 v1 방향은 "수정 가능한 CMS"가 아니라 "로컬 운영 대시보드"로 정했다. 먼저 상태를 정확히 보여주고, 다음에 해야 할 명령을 안내하며, 실제 변경은 source 파일과 PR 흐름을 통해 남기는 방식이다.

### 왜 `publish:posts`가 필요한가

블로그 발행 과정은 명령어 몇 개를 아는 문제처럼 보이지만, 실제로는 순서와 책임의 문제다.

예를 들어 source 글 검증 없이 sync를 하면 잘못된 frontmatter가 발행본까지 복사될 수 있다. 반대로 sync 후 발행본 검증을 하지 않으면 Astro Content Collection에서 걸릴 문제를 놓칠 수 있다. 테스트와 빌드를 생략하면 사이트 전체가 깨졌는지 알기 어렵다.

`publish:posts`는 이 순서를 코드로 고정한다. 사람이 매번 기억하는 것이 아니라, 명령이 발행 정책을 대신 지키게 만드는 것이다.

### 왜 대시보드에서 임의 명령 실행을 막아야 하나

대시보드가 편해질수록 위험한 기능도 붙이기 쉬워진다. 예를 들어 버튼 하나로 `sync`, `build`, `git push`까지 실행할 수 있으면 당장은 편하다. 하지만 임의 shell 실행을 허용하면 로컬 파일을 잘못 건드리거나, 검증되지 않은 상태에서 main에 반영하는 문제가 생길 수 있다.

그래서 대시보드에서 실행 가능한 작업은 allow-list로 제한하는 방향을 문서화했다. 장기적으로 버튼 실행을 붙이더라도, 내부에서는 `publish:posts`처럼 검증된 명령만 호출해야 한다.

## 트레이드오프

대시보드 디자인은 훨씬 나아졌지만, HTML 템플릿이 커졌다. 지금은 빠르게 검증하기 위해 하나의 템플릿 파일로 유지했지만, 기능이 더 늘어나면 상태 계산, UI 렌더링, 액션 버튼을 분리해야 할 수 있다.

`publish:posts`는 발행 과정을 편하게 만들지만, 사용자가 내부에서 무슨 일이 일어나는지 모르면 또 다른 블랙박스가 될 수 있다. 그래서 `--dry-run`으로 실행될 명령을 먼저 볼 수 있게 했고, 각 단계가 실패하면 그 지점에서 멈추도록 했다.

발행본만 남아 있던 글을 정리하는 것도 장단점이 있었다. 원본 중심의 신뢰성은 좋아지지만, 예전에 임시로 발행한 글들이 사라질 수 있다. 그래서 dev-log와 deep-dive의 역할을 더 분명히 나누고, 중요한 결정은 원본 글로 남기는 쪽이 맞다고 판단했다.

## 기술 포인트

대시보드 서버는 `scripts/blog-ops-dashboard.mjs`가 담당하고, 화면 템플릿은 `scripts/blog-ops-dashboard-template.html`로 분리했다. 이전처럼 서버 코드 안에 긴 HTML을 직접 넣지 않도록 바꿨다.

대시보드는 `/api/inventory`를 통해 실제 글 상태를 읽는다. Content Ops는 source/published/frontmatter/tag/sync 상태를 보여주고, Learning Ops는 질문 세트와 개인 답변 노트 상태를 보여준다.

`sync-posts`에는 `--project` 옵션을 추가했다. 이제 특정 프로젝트만 발행본으로 동기화할 수 있다. 다중 프로젝트 블로그에서는 중요한 기능이다. Sigak 글만 가져오려는데 yonghyun-blog 글까지 함께 건드리면 diff가 커지고 검토가 어려워진다.

`publish-posts.mjs`는 프로젝트 단위 발행 흐름을 감싼다. 새로운 로직을 많이 만든다기보다, 이미 있던 검증 명령들을 올바른 순서로 묶는 역할이다.

## 검증

오늘 작업은 다음 관점에서 확인했다.

| 항목 | 확인 내용 |
| --- | --- |
| 대시보드 서버 | 로컬에서 `/`와 `/api/inventory` 응답을 확인했다. |
| 대시보드 UI | 탭 전환, 글 선택, inspector 갱신, light/dark 전환을 확인했다. |
| source 검증 | `npm run validate:posts -- --source --project yonghyun-blog`에서 source 글 9개가 통과했다. |
| 동기화 | `npm run sync:posts -- --project yonghyun-blog`로 6/4 dev-log가 발행본에 추가됐다. |
| 전체 검증 | 발행본 26개 검증, 테스트 55개, Astro 빌드 37페이지가 통과했다. |

이 dev-log를 작성하면서도 새로 추가한 `publish:posts` 흐름을 사용해 yonghyun-blog 글 발행 과정을 다시 확인했다.

## 남은 문제

대시보드는 아직 읽기 중심이다. 다음 단계에서는 버튼으로 검증, sync, PR 준비를 도와줄 수 있다. 다만 이때도 임의 명령 실행이 아니라 allow-list 기반으로 제한해야 한다.

Learning Ops도 더 다듬어야 한다. 어떤 글은 질문 세트가 준비됐지만 개인 답변이 없고, 어떤 글은 다시 복습해야 할 수 있다. 이 상태를 어떻게 시각화하고, 완료된 글과 미완료 글을 어떻게 구분할지 더 명확히 해야 한다.

또한 대시보드 디자인을 실제 운영 도구로 유지하려면 데이터가 많아졌을 때의 밀도도 다시 봐야 한다. 지금은 글 수가 많지 않지만, 프로젝트가 늘어나면 필터, 정렬, 빠른 검색이 중요해질 것이다.
