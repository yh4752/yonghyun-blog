# 2026-07-21 개발 로그: 기능 PR을 정리하고 운영 근거를 남기기

## 요약

오늘은 새 기능을 더 얹기보다, 최근 병합한 SEO/GEO 기반, Pagefind 검색, 선택형 Giscus 댓글의 상태를 한 번에 확인했다. 중요한 구분은 두 가지였다. Blog Ops Dashboard는 글 원본과 로컬 파일을 다루는 운영 도구이고, production 블로그는 정적 산출물을 읽는 공개 사이트다.

그래서 Dashboard는 로컬에서만 확인했고, production에서는 `robots.txt`, RSS, Pagefind 산출물, 관련 글, 비활성 댓글의 HTML 부재를 따로 확인했다. 다음 Dashboard 기능은 새 글 생성 UI로 정하고, 빈 Folder rollback/delete UX는 실제 사용 중 불편함이 반복되는지 더 보기로 했다.

## 오늘 완료한 일

- `main`에 병합된 기능을 기준으로 운영 문서의 상태를 갱신했다.
  - v1.5 missing frontmatter quick fix는 완료로 기록했다.
  - 기존 `new:post` CLI와 아직 없는 Dashboard 새 글 생성 UI를 구분했다.
  - Giscus는 구현됐지만 기본 설정이 비활성이라는 운영 상태를 명시했다.
- 템플릿 비전 문서에 현재 개인 블로그에서 검증된 기능과 별도 템플릿 저장소에서 해야 할 일을 나눠 적었다.
- 품질 기준 deep-dive는 `draft: true`로 유지했다. 구현 상태와 템플릿 분리 계획을 한 글에서 같은 완료 상태처럼 보이게 하지 않기 위해서다.

## 설계 고민

### 기능 구현과 운영 문서를 같은 PR로 섞지 않았다

검색, 댓글, SEO는 각각 코드와 테스트의 변경 범위가 다르다. 이를 한 번에 정리하면 CI 실패나 production 회귀가 났을 때 원인을 좁히기 어려워진다.

그래서 기능은 각각 PR로 병합하고, 이번에는 병합 결과를 읽는 운영 문서와 QA 기록만 별도 PR로 다룬다. 문서는 구현을 대신 증명하지 않는다. 어떤 명령과 어떤 환경에서 확인했는지 남겨서 나중에 다시 판단할 근거를 만든다.

### local Dashboard와 production 정적 사이트의 책임을 나눴다

Dashboard는 source post, Folder, 발행 상태를 읽고 preview/apply 또는 allow-list runner를 제공한다. 이 성격의 도구를 production 정적 사이트에 넣으면 인증, 원격 파일 변경, shell 실행 같은 문제가 따라온다.

반대로 production은 build된 HTML, RSS, sitemap, Pagefind index처럼 독자가 읽는 결과물을 제공하면 된다. 이번 QA도 이 경계를 따라 두 환경을 따로 점검했다.

## 로컬 Dashboard QA

`npm run ops:dashboard`를 실행해 `http://127.0.0.1:4317`에서 확인했다. 이 점검에서는 실제 source post를 고치거나 missing-frontmatter 복구를 실행하지 않았다.

- 인벤토리가 35개 source post와 상태 요약을 읽었다.
- `All Folders`에서는 runner 실행이 차단되고, 단일 Folder를 선택해야 한다는 안내가 보였다.
- `yonghyun-blog` Folder를 선택하자 해당 Folder의 source validation과 publish dry-run만 실행 후보로 나타났다.
- full publish는 브라우저에서 실행되지 않고 copy-only로 남아 있었다.

이 결과는 Dashboard가 Smart View를 실행 범위로 오해하지 않고, 선택한 Folder로 실행 범위를 제한한다는 것을 확인한다. 다만 이것은 로컬 운영 도구의 QA이며 production 블로그의 파일 변경 기능을 뜻하지 않는다.

## Production 정적 사이트 QA

현재 production URL인 `https://yonghyun-blog.vercel.app`에서 아래 항목을 확인했다.

| 대상 | 확인 결과 |
| --- | --- |
| `/robots.txt` | HTTP 200, `sitemap-index.xml` 경로 포함 |
| `/rss.xml` | HTTP 200, RSS channel과 item 확인 |
| `/pagefind/pagefind.js` | HTTP 200, 비어 있지 않은 Pagefind browser asset 확인 |
| Sigak 6월 8일 dev-log | `related-posts` section 렌더링 확인 |
| 같은 글의 HTML | `giscus.app` 문자열 없음 |

마지막 항목은 오류가 아니라 의도한 기본값이다. `site.comments.enabled`가 `false`이고 Giscus 설정도 비어 있으므로, 외부 댓글 script는 production HTML에 포함되지 않아야 한다.

## 검증

이번 세션에서 실행한 검증은 다음과 같다.

| 명령 또는 확인 | 결과 |
| --- | --- |
| `npm test` | 211개 테스트 통과 |
| `node --test scripts/blog-ops-frontmatter-skeleton.test.mjs scripts/blog-ops-dashboard.test.mjs` | 70개 Dashboard 및 frontmatter skeleton 안전성 테스트 통과 |
| `npm run ops:dashboard` | 로컬 Dashboard 인벤토리와 Folder-scoped runner 확인 |
| production `curl` 점검 | robots, RSS, Pagefind, related posts 확인; 비활성 Giscus 미포함 확인 |
| `npm run validate:posts -- --source --project yonghyun-blog` | source post 12개 검증 통과 |
| `npm run validate:posts` | 발행본 30개 검증 통과 |
| `npm run build` | Astro diagnostics 0건, 정적 페이지 42개, Pagefind 문서 30개 색인 확인 |

최종 검증은 문서 변경과 새 dev-log 발행본을 포함해 다시 실행했다. 숫자만 남기지 않고, source, 발행본, build 산출물이 같은 발행 경로를 통과하는지 확인했다.

## 남은 문제

- Giscus를 실제로 켤 때에는 GitHub Discussions 설정과 실제 repo/category ID를 넣은 상태의 live QA가 필요하다. 지금은 기본 비활성 계약만 확인했다.
- Pagefind는 정적 배포에 잘 맞지만 한국어 어근 확장 검색까지 제공하지는 않는다. 검색어와 결과 품질은 실제 글이 더 쌓인 뒤 다시 관찰한다.
- Dashboard의 unknown 상태 3건은 이번 문서 작업에서 고치지 않았다. 실제 source 파일을 고칠 때는 preview와 stale-source guard를 포함한 별도 작업으로 다룬다.
