> 한 줄 요약: AI가 도와준 구현과 글쓰기를 그대로 발행하지 않고, 질문 세트와 개인 답변 노트를 거쳐 내가 설명할 수 있는 지식으로 바꾸는 작성 루틴을 만들었다.

## 문제

이 블로그를 만들면서 Codex는 많은 작업을 도왔다. Astro 프로젝트 구조를 잡고, frontmatter validation을 만들고, CI/CD를 붙이고, About 페이지와 디자인까지 함께 정리했다. 덕분에 결과물은 빠르게 좋아졌다.

하지만 속도가 빨라질수록 다른 문제가 생겼다. Codex가 구현하고 Codex가 글까지 정리하면, 글은 그럴듯해 보여도 내가 나중에 다시 읽었을 때 "왜 이 결정을 했는지"를 내 말로 설명하지 못할 수 있다.

이 위험은 단순히 글 안에 오류나 모순이 있을 수 있다는 정도에서 끝나지 않는다. 기술 블로그는 프로젝트의 판단 근거를 보여주는 문서다. 작성자가 내용을 이해하지 못한 채 발행하면, 글뿐 아니라 프로젝트 자체의 신뢰도도 떨어진다. 내가 어떤 기준으로 검토했고 무엇을 받아들였는지 설명하지 못하면, 설계 결정에 대한 책임감도 약해진다.

특히 CI/CD, frontmatter, branch protection, source mode처럼 처음에는 낯선 개념이 많았다. 이 개념들을 단순히 글로 발행해버리면 포트폴리오에는 남지만, 면접이나 코드 복습 상황에서는 내 지식으로 남지 않을 수 있다.

그래서 블로그 작성 방식을 바꿔야 했다. 목표는 AI가 쓴 글을 더 예쁘게 만드는 것이 아니라, AI가 도와준 결과를 내가 다시 이해하고 설명할 수 있는 루틴으로 바꾸는 것이었다.

## 제약

첫째, 공개 글과 개인 학습 노트는 역할이 다르다. 공개 글에는 문제, 선택지, 결정, 검증, 트레이드오프를 정리해야 한다. 반면 개인 노트에는 "잘 모르겠다", "이 개념은 아직 불안하다" 같은 내용도 남아야 한다. 이 둘을 한 파일에 섞으면 공개 글은 어색해지고, 개인 학습은 솔직하지 못해진다.

둘째, 이 루틴은 `yonghyun-blog`에만 묶이면 안 됐다. Sigak처럼 다른 프로젝트에서도 같은 방식으로 개발 로그와 기술 글을 작성할 수 있어야 했다. 따라서 스킬은 특정 경로나 프로젝트명을 하드코딩하지 않고, `project`, `sourcePost`, `mode`, `goal` 같은 입력으로 움직여야 했다.

셋째, AI가 대신 생각하게 두면 안 됐다. 사용자가 모르는 개념을 숨기고 바로 면접용 문장을 만들어주면 당장은 편하지만, 학습 효과는 약하다. 그래서 학습형 또는 hybrid 모드에서는 최종 문장보다 먼저 질문을 던지도록 설계했다.

## 선택지

처음 떠올릴 수 있는 방식은 세 가지였다.

| 방식 | 장점 | 한계 |
| --- | --- | --- |
| Codex가 완성 글을 바로 작성 | 빠르고 보기 좋다 | 내가 이해하지 못한 부분이 숨어 있을 수 있다 |
| 모든 글을 내가 처음부터 직접 작성 | 학습 효과가 크다 | 구현과 발행 속도가 크게 느려진다 |
| AI 초안 이후 질문 세트와 개인 답변 노트를 거친다 | 속도와 학습을 함께 가져갈 수 있다 | 한 번에 끝나지 않고 복습 단계가 필요하다 |

결정은 세 번째 방식이었다. AI가 초안을 만들 수는 있지만, 그 초안이 바로 최종 글이 되면 안 된다. 먼저 질문 세트로 내가 이해해야 할 지점을 드러내고, 개인 답변 노트에서 내 첫 답변을 남긴 뒤, 다시 공개 글을 다듬는 흐름이 필요했다.

## 결정

작성 루틴을 세 층으로 나눴다.

```txt
공개 블로그 글
  -> 문제, 선택지, 결정, 검증, 트레이드오프를 정리한다.

면접 질문 세트
  -> 이 글을 내 것으로 만들기 위해 답해야 할 질문을 남긴다.

개인 답변 노트
  -> 첫 답변, 부족한 개념, 코드 근거, 30-60초 답변을 분리한다.
```

이 흐름을 반복할 수 있게 `technical-blog-learning-writer` 스킬도 만들었다. 이 스킬의 기본 모드는 `hybrid`다. 글을 포트폴리오용으로 다듬는 것과, 내가 학습하고 면접에서 설명할 수 있게 만드는 것을 동시에 목표로 둔다.

스킬의 중요한 규칙은 "처음부터 완성된 문장을 주지 않는다"는 것이다. 특히 학습형 글에서는 최소 한 번 이상 핵심 질문을 먼저 던져야 한다. 예를 들어 다음과 같은 질문이다.

- 왜 이 도구나 구조를 선택했는가?
- 이 변경이 없었다면 어떤 문제가 생겼을까?
- 검증이 실제로 증명한 것은 무엇인가?
- 이 결정이 만든 트레이드오프는 무엇인가?

이 질문에 내가 먼저 답해야 글이 내 것이 된다.

## 트레이드오프

좋아진 점은 분명하다. AI가 도와준 결과를 숨기지 않으면서도, 내가 검토한 기준과 이해한 개념을 남길 수 있다. 또한 글을 쓸 때마다 면접 질문이 자연스럽게 생기므로, 포트폴리오와 면접 대비가 분리되지 않는다.

대신 한 번에 끝나는 글쓰기는 아니다. AI가 초안을 만들고, 내가 질문에 답하고, 다시 글을 고치는 단계가 필요하다. 빠른 발행만 목표라면 번거롭다.

또 하나의 비용은 개인 노트 관리다. 공개 글과 개인 답변을 분리하면 파일이 늘어난다. 하지만 이 비용은 의도된 비용이다. 공개 글에 모든 고민을 넣으려 하면 글이 산만해지고, 개인 노트까지 공개 문장처럼 쓰려 하면 학습 기록이 솔직하지 못해진다.

## 검증

이 글은 아직 발행하지 않은 `draft: true` 원본 글이다. 따라서 검증의 목표는 production 반영이 아니라, source post로서 frontmatter와 글 구조가 유효한지 확인하는 것이다.

이 초안을 작성한 브랜치에서 확인한 항목은 다음과 같다.

| 영역 | 확인 방법 | 현재 의미 |
| --- | --- | --- |
| 원본 글 검증 | `npm run validate:posts -- --source --project yonghyun-blog` | 5개 source post 검증 통과 |
| 자동 테스트 | `npm test` | 9개 테스트 통과 |
| Astro 빌드 | `npm run build` | Astro check 0 errors, 0 warnings, 0 hints / 19페이지 빌드 |

이 검증은 production 발행을 의미하지 않는다. 글은 여전히 `draft: true`이고, 발행하려면 내 답변을 반영해 글을 다시 다듬은 뒤 `draft: false`로 바꾸고 sync해야 한다.

## 내가 이해한 것

AI를 개발에 쓰는 문제는 "써도 되는가"보다 "어디까지 맡기고, 어디서 내가 판단할 것인가"에 가깝다.

Codex가 구현과 초안 작성을 도울 수는 있다. 하지만 문제를 어떻게 정의했는지, 어떤 선택지를 버렸는지, 검증이 무엇을 증명했는지는 내가 이해해야 한다. 이 부분까지 AI가 대신 정리해주면 글은 좋아 보일 수 있지만, 면접에서 깊게 질문을 받으면 약해진다.

그래서 블로그는 단순한 결과물 전시장이 아니라 학습 루프가 되어야 한다. 공개 글은 정리된 결과를 보여주고, 개인 답변 노트는 내가 아직 모르는 것을 드러내며, 질문 세트는 그 사이를 연결한다.

## Codex에게 맡긴 것과 내가 검토한 것

Codex에게 맡긴 것은 다음과 같다.

- 블로그 작성 패턴 초안 정리
- `technical-blog-learning-writer` 스킬 구조 작성
- 스킬 파일 검증
- 이 글의 초안 작성
- source 검증과 build 검증 실행

내가 검토해야 하는 것은 다음과 같다.

- 글과 문서에 명령, 파일 경로, 사실관계 오류가 없는가
- 내가 문제, 선택 이유, 검증, 트레이드오프를 내 말로 설명할 수 있는가
- 이해가 안 되는 부분을 그대로 승인하지 않고 추가 설명을 요구했는가
- 질문 세트가 너무 추상적이지 않고 실제 면접 답변으로 이어지는가
- 공개 글과 개인 답변 노트의 경계가 유지되는가
- 이 방식을 Sigak이나 앞으로의 프로젝트에도 그대로 적용할 수 있는가

중요한 지점은 "AI가 도왔다"는 사실을 감추지 않는 것이다. 대신 AI가 도운 결과를 내가 어떤 기준으로 검토했고, 어떤 질문을 통해 내 언어로 다시 만들었는지를 남겨야 한다.

- AI가 작성한 기술 글을 그대로 발행하면 어떤 위험이 있는가?

- AI가 도운 부분을 포트폴리오에서 어떻게 솔직하면서도 긍정적으로 설명할 수 있는가?

## 이 초안을 발행하기 전에 내가 답해야 할 핵심 질문

지금 단계에서 가장 중요한 질문은 하나다.

> Codex가 만든 구현과 글을 내가 검토했다고 말하려면, 나는 정확히 무엇을 확인했고 어떤 기준으로 받아들였다고 설명할 수 있어야 할까?

첫 답변은 "글을 읽고 오류가 없는지, 내가 이해 가능한 선인지 확인하고, 이해가 안 되면 설명을 요구해 이해 후 진행하는 것"이었다. 이 답변을 기준으로 보면 검토는 세 단계다. 첫째, 명령과 파일 경로, 사실관계의 오류를 확인한다. 둘째, 문제와 선택 이유, 트레이드오프를 내 말로 설명할 수 있는지 확인한다. 셋째, 이해가 안 되는 부분은 그대로 승인하지 않고 질문으로 되돌린다.

이 답변을 개인 답변 노트에 더 구체화한 뒤, 글의 `내가 이해한 것` 섹션을 한 번 더 다듬어야 한다.

그 전에 첫 번째 질문에도 답을 남겼다. AI가 작성한 기술 글을 그대로 발행할 때의 가장 큰 위험은 단순한 오류 가능성이 아니라, 프로젝트 신뢰와 작성자의 책임감이 약해지는 것이다. 기술 글이 설계 판단의 근거라면, 그 판단을 설명하지 못하는 글은 포트폴리오를 돕기보다 오히려 신뢰를 깎을 수 있다.
