# 2026-05-31 개발 로그: collection persistence 리팩토링

## 요약

오늘은 collection trigger 관측성 작업에 들어가기 전에 `CollectedArticlePersistenceService.publish()`의 흐름을 정리했다.
기능을 추가하지 않고, source resolve -> identity normalize -> duplicate lookup -> aggregate assembly -> save 단계가 보이도록 private helper로 나눴다.
별도 factory나 mapper를 만들지 않고 작은 private value object만 사용해 오버엔지니어링을 피했다.
검증은 collection focused test, 전체 backend test, backend check까지 실행했다.

## 오늘 완료한 일

- `docs/superpowers/specs/2026-05-31-collection-persistence-refactor-design.md`
  - collection persistence 리팩토링의 목표, 비목표, 보존해야 할 동작 계약을 정리했다.
- `docs/superpowers/plans/2026-05-31-collection-persistence-refactor.md`
  - 실행 단위를 baseline verification, helper extraction, focused verification, topic queue, final verification으로 나눴다.
- `backend/src/main/kotlin/com/sigak/collection/service/CollectedArticlePersistenceService.kt`
  - `CollectedArticlePersistenceIdentity` private value object를 추가했다.
  - `persistenceIdentityFor`, `buildArticleEntity`, `attachRawContent`, `attachCurrentEnrichment`, `attachTopics` helper로 `publish()` 흐름을 정리했다.
  - duplicate lookup 순서와 entity field mapping은 유지했다.
- `docs/blog/topic-queue.md`
  - `Collection trigger를 만들기 전에 persistence 흐름을 정리한 이유` 후보를 추가했다.

## 설계 고민 / 결정

다음 collection trigger에서는 단순히 "수집 실행"만 만드는 것이 아니라 fetched, published, skipped, failed 같은 count를 설명해야 한다.
그런데 persistence writer가 한 메서드 안에서 source 생성, URL 정규화, 중복 판단, entity 조립을 모두 처리하면 skipped/published의 기준을 코드에서 읽기 어렵다.
그래서 trigger를 먼저 붙이지 않고, 중복 판단과 저장 조립 단계를 먼저 드러내는 순서로 리팩토링했다.

새 파일이나 mapper 계층은 만들지 않았다.
현재 문제는 재사용 가능한 변환 계층이 필요한 것이 아니라 `publish()`의 도메인 순서가 흐려진 것이기 때문이다.
그래서 private helper와 작은 identity 값 객체만으로 범위를 제한했다.

## 트레이드오프

- 얻은 것
  - collection persistence 흐름을 신규 개발자가 따라가기 쉬워졌다.
  - collection trigger metric을 붙일 때 duplicate/skipped/published 판단 위치를 설명하기 쉬워졌다.
  - public API에 노출되는 article persistence 동작은 유지했다.
- 미룬 것
  - admin/internal collection trigger는 아직 구현하지 않았다.
  - collection status transition, retry, failure 저장은 아직 구현하지 않았다.
  - Docker 기반 실제 수집 smoke check는 이번 리팩토링 범위가 아니라 실행하지 않았다.

### 설계 고민 / 결정

처음에는 collection trigger가 단순히 수집 메서드를 호출하면 충분해 보였지만, 운영 관점에서는 "몇 개가 새로 저장됐는지"와 "중복이라 건너뛴 것인지"가 분리돼야 한다.
그래서 duplicate detection이 실제로 일어나는 persistence boundary에서 publish outcome을 만들고, 그 결과를 pipeline -> source collection -> run aggregation 순서로 올려보내게 했다.

trigger는 Spring Boot internal API로만 열었다.
command runner는 같은 `CollectionRunService`를 재사용할 수 있게 남겨두고, 이번에는 HTTP entrypoint와 service boundary 검증에 집중했다.
또한 collection 이후 projection rebuild를 자동 실행하지 않았다.
PostgreSQL이 source of truth이고 Elasticsearch, Qdrant, Neo4j는 rebuildable projection store라는 원칙을 유지하기 위해서다.

## 추가 진행: collection failure evidence 구현

### 요약

collection 실패 근거가 HTTP/CLI 응답이 끝나면 사라지는 문제를 줄이기 위해 `collection_failure_events` 테이블을 추가했다.
전체 run history나 자동 retry queue는 만들지 않고, 실패 event만 `runId`로 묶어 저장하는 방식으로 범위를 제한했다.
실패는 `TRANSIENT_FETCH`, `SOURCE_FORMAT`, `INVALID_ARTICLE`, `PERSISTENCE`, `UNKNOWN`으로 분류하고, 자동 재시도 대신 수동 재실행 판단용 `retryable` 힌트만 남긴다.

### 오늘 완료한 일

- `backend/src/main/resources/db/migration/V3__collection_failure_events.sql`
  - collection failure event 저장 테이블과 조회용 index를 추가했다.
- `backend/src/main/kotlin/com/sigak/collection/domain/CollectionFailureEventEntity.kt`
  - 실패 event JPA entity를 추가했다.
- `backend/src/main/kotlin/com/sigak/collection/service/CollectionFailureClassifier.kt`
  - stage/exception을 failure kind와 retryable 여부로 분류한다.
- `backend/src/main/kotlin/com/sigak/collection/service/CollectionFailureEventRecorder.kt`
  - failure summary를 PostgreSQL event로 저장하고 `failureEventId`를 돌려준다.
- `backend/src/main/kotlin/com/sigak/collection/service/SourceCollectionService.kt`
  - article publish 실패 summary에 article hint와 failure kind를 포함한다.
- `backend/src/main/kotlin/com/sigak/collection/service/CollectionRunService.kt`
  - run마다 `runId`를 만들고 source/article failure summary를 저장한다.
- `docs/API_SPEC.md`, `docs/STATUS.md`, `docs/ROADMAP.md`
  - internal collection response와 현재 진행 상태를 갱신했다.

### 설계 고민 / 결정

처음에는 `collection_runs` 테이블까지 만들 수 있었지만, MVP에서는 run lifecycle보다 실패 원인 디버깅이 더 중요하다.
그래서 run 자체는 응답의 `runId` UUID로만 표현하고, DB에는 실패 event만 저장했다.
이 구조는 bad feed나 invalid article을 나중에 찾아볼 수 있게 하면서도 scheduler, retry queue, 상태 전이 테이블을 끌어오지 않는다.

자동 retry도 넣지 않았다.
network timeout이나 5xx처럼 재실행 가능성이 있는 실패는 `retryable=true`로 표시하지만, 실제 재실행은 command runner나 internal endpoint를 사람이 다시 호출하는 방식으로 남겼다.

### 트레이드오프

- 얻은 것
  - collection 실패 근거가 요청 종료 후에도 PostgreSQL에 남는다.
  - 같은 run에서 나온 실패들을 `runId`로 묶어 볼 수 있다.
  - failure kind와 retryable hint로 bad feed와 invalid article을 구분할 수 있다.
- 미룬 것
  - 전체 run history table은 만들지 않았다.
  - 자동 retry queue나 scheduler는 만들지 않았다.
  - 이 단계에서는 failure event listing API를 아직 만들지 않았다.

`retryable=true`만 보고 무조건 재실행하라고 쓰면 운영 문서가 너무 거칠어진다.
반대로 자동 retry queue, acknowledgement, run lifecycle까지 만들면 현재 MVP 범위보다 커진다.
그래서 문서에서는 `failureKind`별로 "바로 재실행 가능한지", "무엇을 먼저 확인해야 하는지"만 정리했다.

이 결정은 기존 설계와 맞다.
`TRANSIENT_FETCH`는 network, timeout, 5xx, 429처럼 재실행으로 해결될 수 있지만, `SOURCE_FORMAT`, `INVALID_ARTICLE`, `PERSISTENCE`, `UNKNOWN`은 같은 입력으로 반복 실행하면 같은 실패를 숨길 가능성이 높다.
따라서 문서는 "재실행 버튼"이 아니라 "조사 후 재실행 판단"을 안내한다.

### 검증

| 영역 | 실행한 명령 | 결과 |
| --- | --- | --- |
| Markdown whitespace check | `git diff --check` | 통과 |

미검증:

- 문서 변경만 진행했으므로 backend/frontend/AI test suite는 다시 실행하지 않았다.
- 실제 새 failure kind를 추가하거나 retry 동작을 구현하지 않았다.
- Neo4j graph projection은 오늘 범위에서 제외했다.

## 추가 진행: retrieval benchmark 역할 분담 정리

### 요약

오늘 마지막에는 retrieval benchmark를 어떻게 준비할지 논의했다.
바로 runner를 구현하지 않고, 먼저 사람이 판단한 query label을 만드는 방향으로 정했다.
내 역할은 article catalog와 labeling template, 이후 benchmark runner와 metric/report를 만드는 것이고, 사용자 역할은 query와 정답 article 판단을 채우는 것이다.

### 오늘 완료한 일

- 현재 시작점으로 `docs/search-evaluation/queries.md`를 확인했다.
  - 이미 `graph`, `security`, `vector` query와 기대 article, 현재 smoke result가 있다.
- retrieval benchmark 준비 순서를 정리했다.
  - query set 작성
  - 사람이 정답 label 작성
  - keyword/vector/hybrid 결과 비교
  - Recall@5, MRR@5, Top1 hit, latency 기록
  - 결과 report와 블로그 후보 기록
- 역할 분담을 정했다.
  - 사용자: 실제 사용자가 검색할 법한 query와 relevance label 판단
  - Codex: article catalog, template, runner, metric 계산, report, topic queue 정리
- 오늘은 시간이 부족해 구현이나 템플릿 생성은 하지 않고, 내일 다시 시작하기로 했다.

### 설계 고민 / 결정

검색 품질 평가는 runner보다 label이 먼저다.
정답 기준이 없는 상태에서 hybrid/RRF 성능을 숫자로 계산하면, 그 숫자는 포트폴리오 근거가 아니라 장식이 된다.
그래서 처음부터 JSON 자동화로 가지 않고, 사용자가 직접 판단하기 쉬운 Markdown-first worksheet 방식으로 시작하기로 했다.

이 방식은 느리지만 장점이 있다.
사용자가 왜 특정 article이 strong relevant 또는 acceptable인지 한 줄 근거를 남길 수 있고, 나중에 benchmark 결과가 나왔을 때 "왜 이 검색이 맞거나 틀렸는가"를 설명할 수 있다.

### 트레이드오프

- 미룬 것
  - `queries.md` 라벨링 템플릿 확장은 내일로 미뤘다.
  - benchmark runner 구현은 아직 시작하지 않았다.
