# 출처를 URL로 등록하고 기존 기사는 보관하도록 바꾼 이유

> 출처 설정은 PostgreSQL에서 관리해 재배포 없이 바꾸고, 홈에서 제외한 기사도 본문·요약·작업 이력과 함께 남겼다.

## 배경과 문제

Sigak은 기술 글을 수집하고, 독자가 처음 상세 화면을 열 때 AI 요약을 만든 뒤 저장해 재사용하는 서비스다. 개발 트렌드와 실무 경험을 읽는 데 도움이 되도록 출처를 토스·우아한형제들·NAVER D2로 좁히는 과정에서 두 가지 문제가 드러났다.

출처 하나를 바꾸려면 Kotlin의 수집 목록을 수정해야 했다. DB에도 `news_sources`가 있었지만 실제 수집 대상은 코드가 정했다. 새 블로그를 추가할 때마다 피드 주소와 허용 호스트, 본문 추출 규칙을 함께 고치고 배포해야 했다.

수집 대상을 바꿔도 홈에는 이전 기사와 데모가 남았다. 기존 출처의 실제 기사 238개와 데모 5개를 어떻게 다룰지 정해야 했다. 이 중 기존 실제 기사에는 요약 작업 6개도 연결돼 있었다. 지금 읽을 글을 정리하는 요구가 저장된 기사와 유료 호출 이력의 삭제로 이어져도 되는지부터 구분할 필요가 있었다.

목표는 출처를 바꾸기 쉽게 만들면서 이미 쌓인 데이터를 지키는 것이었다. RSS 수집기나 외부 연동 서비스를 운영하면서 설정 변경과 데이터 보관을 고민한다면, 이번에 나눈 등록·검증·저장 경계를 참고할 만하다.

## 제약과 선택지

Spring Boot가 수집·저장·공개 API를 담당하고, PostgreSQL을 원본 저장소로 사용하는 구조는 유지했다. FastAPI는 AI/RAG 호출을 맡는다. 출처를 등록하거나 본문을 확인하는 과정에서는 유료 AI를 호출하지 않는다. 실제 요약은 기존처럼 상세 진입 시 요청하고 저장 결과를 공유하며, 승인된 총 5달러 안에서 앱 누적 4달러 중단 정책도 유지해야 했다.

출처 관리 방식은 세 가지를 비교했다.

| 방식 | 얻는 것 | 남는 부담 |
| --- | --- | --- |
| 코드 목록이나 YAML로 관리 | 구조가 단순하고 Git으로 변경 추적 가능 | 코드 목록은 배포가 필요하고, YAML도 적용·재시작과 DB 동기화를 관리해야 함 |
| DB 등록과 운영 명령 | 실행 중인 서비스의 재배포 없이 출처 추가·중지 가능 | 기존 데이터 이관, 검증 상태, 설정 버전 관리가 필요함 |
| 관리자 웹 화면 | 화면에서 직접 관리 가능 | 등록 로직에 더해 인증·권한·화면·공개 쓰기 경계까지 구현해야 함 |

두 번째를 선택했다. 기존 PostgreSQL에 설정을 두고 운영 명령으로 조작하면 실행 중인 서비스를 재배포하지 않아도 됐다. 관리자 화면은 뒤로 미뤘다. 현재 규모에서는 화면과 인증을 만드는 일보다 등록·검증·중지를 먼저 연결하는 편이 맞았다.

DB에 URL만 옮겨 담는 것으로는 충분하지 않았다. 어떤 설정으로 검증했는지, 지금 수집해도 되는지, 출처를 중지하는 동안 진행 중이던 작업은 어떻게 처리할지도 함께 정의해야 했다.

## 구현: URL을 등록한 뒤 검토하고 활성화한다

### 코드에는 수집 방식, DB에는 출처별 설정

코드에는 RSS/Atom 같은 형식을 읽는 수집기와 공통 본문 추출 알고리즘을 둔다. 개별 사이트의 URL·허용 호스트·본문 위치는 `news_sources`에서 관리한다.

출처별 설정은 역할에 따라 다음처럼 나눴다.

| 역할 | 주요 필드 |
| --- | --- |
| 식별 | 기존 DB ID, 고정 `source_key`, 표시 이름 |
| 접근 | `site_url`, `feed_url`, `allowed_hosts` |
| 본문 추출 | `body_mode`, `body_selector`, `exclude_selectors` |
| 수집 상태 | `collection_enabled`, `validation_status` |
| 검증한 설정 추적 | `config_version`, `validated_config_version`, `validated_at` |

표시 이름과 식별자도 분리했다. 이전에는 이름을 영문 식별 문자열인 slug로 바꿔 저장 출처를 찾았다. 한글 이름은 같은 기본값으로 겹칠 수 있었고 이름을 바꾸면 다른 출처가 될 여지도 있었다. 등록할 때 만든 고정 key를 수집부터 저장까지 전달하고, 기존 기사가 참조하는 출처의 DB ID(FK)는 그대로 뒀다.

실제 `SourceRegistry`는 이제 DB에서 읽은 출처 중 수집 가능한 항목을 반환한다.

```kotlin
fun sources(): List<NewsSource> =
    store.all().filter { it.collectable() }.map { it.asNewsSource() }
```

`collectable()`은 활성화 여부와 검증 성공을 확인한다. 검증한 설정 버전이 현재 버전과 일치해야 하고 피드 URL도 있어야 한다.

### 등록과 활성화를 나눈 이유

신규 출처의 운영 흐름은 다음과 같다.

```txt
블로그 또는 피드 URL 입력
  -> 비활성 출처 등록
  -> 피드 탐색·최근 글 최대 3건 검사
  -> 본문 처음·중간·끝을 원문과 대조
  -> 필요하면 피드·호스트·본문 위치 설정 후 재검증
  -> 운영자 활성화
  -> 다음 자동 수집 회차에 반영
```

운영 명령은 `register/check/configure/enable/disable/list`로 제공한다. 신규 URL의 `register`는 표본 검사까지 진행하지만 자동 수집을 켜지는 않는다. 활성화에는 현재 설정의 검증 성공과 원문 표본 확인이 필요하다. 검증 결과가 오래됐거나 설정이 바뀌었다면 활성화를 거부한다.

HTTP 응답이 성공했다고 본문까지 제대로 가져온 것은 아니다. RSS의 긴 텍스트가 소개글일 수도 있다. HTML에서 본문으로 고른 영역에 관련 글 목록이나 저자 소개가 섞이기도 한다.

실제 세 출처도 같은 방식으로 처리하지 않았다.

| 출처 | 선택한 본문 경로 | 확인·설정한 내용 |
| --- | --- | --- |
| 토스 테크 | AUTO에서 검토한 피드 전문 사용 | 원문 표본과 대조한 피드 본문 재사용 |
| 우아한형제들 | PAGE | `.post-content-body`를 본문으로 지정하고 저자 widget 제외 |
| NAVER D2 | FEED_FULL | 렌더링 원문과 피드 표본을 대조한 뒤 피드 전문 사용 |

D2 원문은 등록 검토 때 브라우저로 확인했다. 자동 수집은 피드를 읽으며 브라우저를 실행하지 않는다.

토스 원문을 비교하다가 `aside` 강조 상자 안의 내용이 빠진 것을 발견했다. 이를 불필요한 영역으로 보고 태그째 제거하던 규칙 때문에 처리 조건과 평가 기준이 누락됐다. `aside` 일괄 삭제 규칙을 없애고 제외할 widget을 설정으로 지정하도록 고쳤다.

“URL로 등록한다”는 기능이 모든 사이트의 정확한 수집을 보장하지는 않는다. 표준 피드와 지원 가능한 본문은 공통 경로로 처리한다. 맞지 않는 사이트는 필요한 설정과 실패 이유를 운영자에게 보여 준다. 목록 성격의 D2 글 한 건은 `BODY_LINK_LIST`로 남겼다. 표본 통과가 앞으로의 모든 글에 대한 완전성 보증도 아니다.

### 검증한 설정이 바뀌면 이전 결과를 그대로 쓰지 않는다

본문 위치나 허용 호스트를 변경하면 이전 검증 결과를 계속 신뢰할 수 없다. 그래서 설정에 버전을 붙이고 검증한 버전을 따로 저장한다.

버전은 수집 중지와 기사 저장이 겹칠 때도 사용한다. 수집을 시작할 때 활성 여부만 확인하면, 이후 출처를 중지했는데도 먼저 시작한 작업이 늦게 기사를 저장할 수 있다. 이를 막기 위해 기사 저장 트랜잭션에서도 출처 행을 잠그고 현재 버전과 수집 가능 여부를 확인한다.

```txt
수집 시작: 출처 A, 설정 버전 5
운영 중지: 출처 A, 설정 버전 6, enabled=false
이전 작업의 기사 저장: 버전·활성 상태 불일치로 거부
```

이미 시작한 외부 요청이 끝날 수는 있어도, 중지된 설정으로 새 기사를 저장하지 않게 한 것이다. 외부 HTTP 응답을 기다리는 동안 DB 행 잠금을 유지하는 구조는 피하고, 저장 시점에 다시 확인한다.

운영자가 입력한 URL에도 접근 제한을 적용했다. 피드 탐색·피드 읽기·본문 읽기는 승인된 HTTPS 호스트와 공개 IP를 확인하는 공통 경로를 사용한다. URL 등록을 쉽게 만드는 만큼 서버가 어디에 요청할 수 있는지도 제한해야 했다. 로그인이나 봇 차단을 우회하는 기능은 추가하지 않았다.

## 기존 기사는 삭제하지 않고 수집과 노출을 중지한다

### 홈 정리와 원본 삭제는 영향 범위가 다르다

기존 데이터 처리에도 선택지가 있었다.

| 방식 | 홈 정리 | 기존 링크·검색 | 요약 작업·근거 이력 |
| --- | --- | --- | --- |
| 기존 기사 삭제 | 가능 | 사라짐 | 연결된 데이터도 삭제될 수 있음 |
| 홈에서만 제외 | 가능 | 유지 | 유지되지만 이전 출처 수집은 계속됨 |
| 출처 수집 중지 + 홈 제외 + 데이터 보관 | 가능 | 보관한 실제 글 유지 | 유지 |

세 번째를 선택했다. 목적은 앞으로 읽을 출처를 좁히는 것이었고, 기존 기록을 폐기해야 할 이유는 없었다.

현재 스키마는 기사를 지우면 연결된 요약 작업도 함께 지우도록 정의한다.

```sql
article_id bigint not null references articles(id) on delete cascade
```

이 스키마에서 기사를 삭제하면 연결된 작업 이력도 사라진다. 어떤 입력으로 호출했는지, 결과를 받았는지, 비용을 확인하지 못한 작업이 무엇인지 설명할 근거를 잃는다.

누적 예산인 `summary_budget`은 별도 테이블이므로 기사 삭제만으로 누적 차감액이 초기화되는 것은 아니다. 문제는 차감액을 설명할 개별 호출의 입력·상태·결과를 잃는다는 데 있다. 요약을 재사용하고 차감 내역을 추적하려면 개별 작업 기록도 남겨야 했다.

### 홈은 출처 이름 대신 DB 상태를 따른다

수집을 DB 등록 방식으로 바꾼 뒤 화면에 다시 토스·우아한형제들·D2 이름을 고정하면, 다음 출처를 추가할 때 화면 코드를 또 고쳐야 한다.

Spring은 현재 `collection_enabled`를 `ArticleResponse.sourceEnabled`로 내려준다. 홈은 이 값이 true인 실제 글만 게시 시각 내림차순으로 표시한다. 같은 시각이면 기사 ID 내림차순을 사용한다.

아래는 실제 홈 코드에서 표시 규칙을 추린 부분이다.

```ts
const realArticles = articles.filter(
  (article) => article.summaryProvider !== 'curated-seed',
)

const latestArticles = realArticles
  .filter((article) => article.sourceEnabled === true)
  .sort((a, b) => Date.parse(b.publishedAt) - Date.parse(a.publishedAt) || b.id - a.id)
```

`curated-seed`는 데모 요약의 출처를 나타내는 값이다. 데모는 홈과 홈 검색에서 제외한다. 실제 보관 기사는 검색에 남기며, 검색 결과를 홈의 최신순으로 다시 정렬하지 않고 서버 관련도 순서를 유지한다.

```txt
수집 중지된 실제 기사
  ├─ 새 자동 수집: 제외
  ├─ 홈 최신 글: 제외
  ├─ 검색·직접 링크: 유지
  └─ 본문·요약·작업·예산 기록: 유지
```

별도의 `ARCHIVED` 상태나 기사별 보관 테이블은 만들지 않았다. 출처를 비활성으로 바꾸면 홈에서 제외하고 저장된 데이터는 그대로 둔다. 출처를 다시 활성화하면 기존 글도 홈 표시 대상이 된다. 수집은 계속하면서 홈에서만 숨기는 등의 요구가 생기면 수집 상태와 노출 상태를 분리해야 한다.

### 검색 저장소도 기존 기사를 유지한다

Elasticsearch·Qdrant·Neo4j는 PostgreSQL에서 다시 만들 수 있는 검색·관계 저장소다. 홈을 50개로 줄였다고 세 저장소까지 50개로 줄이지는 않았다. 보관한 실제 글을 검색하고 기존 관계를 읽을 수 있도록 전체 293개를 유지했다.

전체 기사 목록 API에도 보관 글이 남는다. 이번 변경은 홈 표시 정책이며 목록 API의 페이지 구분이나 전송량 최적화까지 해결한 것은 아니다. 기존 탭 캐시는 다음 목록 갱신까지 이전 활성 상태를 잠시 보여 줄 수도 있다. 현재 목록 신선도 기준은 60초다.

## 수집 설정을 바꿔도 유료 요약 이력은 그대로 둔다

출처 등록·표본 검사·본문 확보에는 유료 AI를 쓰지 않는다. 검토된 피드 전문은 기사와 함께 저장해 나중에 사용할 수 있지만, 본문이 준비됐다는 사실이 요약 생성 요청을 뜻하지는 않는다.

```txt
자동 수집 -> 기사·본문 저장 -> 검색 반영
독자의 첫 상세 진입 -> 비동기 요약 요청 -> 결과 저장·공유
```

출처나 selector를 바꿨다는 이유로 이전 본문과 요약을 일괄 덮어쓰거나, 유료 요약을 다시 생성하지 않는다. 기존 기사를 읽으며 처음 요약을 요청하는 경우에도 같은 누적 예산을 사용한다.

요약 호출 결과를 확정할 수 없는 `UNKNOWN` 작업도 그대로 남긴다. 결과를 못 받았다고 과금이 없었다고 단정할 수 없으므로 자동 재시도하거나 보수 차감액을 돌려주지 않는 기존 정책을 유지했다.

이번 구조 변경에서 지켜야 할 경계는 “운영 설정을 바꾼다”와 “유료 작업을 새로 실행한다” 사이였다. 출처를 관리하는 명령도 별도 프로세스에서 자동 수집·본문 worker·유료 요약을 끄고 실행하도록 구성했다.

보수 차감액 0.22달러는 앱이 호출당 일정 금액을 차감해 관리한 값이며 실제 청구액을 뜻하지 않는다. 누적 4달러 중단·총 200회·일 20회 등 기존 한도도 바꾸지 않았다.

이관과 운영 중지의 검증은 구분했다. DB 등록 구조로 바꿀 때에는 기존 source ID와 기사 FK를 보존하는 V6 migration을 적용했다. 이후 여섯 출처를 중지할 때에는 운영 명령으로 활성 상태와 설정 버전을 바꿨다. 그러므로 “출처 테이블 전체가 전후 동일하다”는 주장이 아니라, 의도한 설정 변경 외에 보존 대상 데이터가 유지됐는지를 확인한 것이다.

구현 세션의 최종 검사 명령과 결과도 개발 로그에 남겼다.

```bash
# 저장소 루트에서 실행한 백엔드 검사
./backend/gradlew -p backend test check bootJar

# frontend/에서 실행한 검사
npm test
npm run lint
npm run build
```

백엔드 344개 테스트에서 실패·오류·skip이 없었고, 프론트엔드 70개 테스트와 lint·build가 통과했다. 로컬·공개 사이트 HTTP smoke도 각각 7개를 통과했다. 이 숫자는 서비스 전체 검사 수이며 이번 변경에 새로 작성한 테스트 수는 아니다.

이번 변경에서 확인한 동작은 더 좁다. [출처 관리 테스트](https://github.com/yh4752/sigak/blob/3730583357984258e24089c46542200cc6ae05ef/backend/src/test/kotlin/com/sigak/source/service/SourceManagementServiceTest.kt#L77)에서는 설정 변경 후 이전 버전으로 활성화하는 요청을 거부하는지 검사했다. [홈 테스트](https://github.com/yh4752/sigak/blob/3730583357984258e24089c46542200cc6ae05ef/frontend/src/pages/HomePage.test.tsx#L59)는 비활성 출처와 데모를 제외하면서 보관한 실제 검색 결과의 순서는 유지하는지 확인한다. 새 metadata와 표시 정책을 검사하는 테스트가 먼저 실패하는 것을 보고 구현을 수정했다.

이 결과가 모든 사이트의 본문 완전성이나 장기 무인 운영 안정성을 증명하지는 않는다. 이번 세 출처와 관측한 수집 주기, 보관 정책의 동작을 확인한 결과다.

## 이번 설계에서 배운 점과 남은 일

출처를 쉽게 바꾸려면 URL 목록을 외부로 옮기는 것에 더해 식별자·검증 상태·설정 버전·활성화 시점을 관리해야 했다. 운영자가 입력할 항목을 줄이려면 시스템 내부에서는 어떤 조건에서 수집해도 되는지 더 분명히 판단해야 했다.

기사를 보관하는 결정도 단순한 저장 공간 문제가 아니었다. 지금 홈에 보여 줄 글을 바꾸더라도 예전에 만든 요약의 근거는 계속 필요했다. 수집과 홈 노출을 중지하고 읽기는 허용해 기존 링크와 이력을 지켰다.

대신 현재는 수집 활성 상태를 홈 표시 기준으로도 사용한다. 홈에서는 숨기되 수집은 계속해야 하는 출처가 생기면 두 상태를 분리해야 한다. 전체 목록 API의 페이지 구분과 전송량 개선, 장기 수집 관찰도 남았다. 관리자 화면·범용 크롤러·arXiv 논문 전문 처리는 이번 범위에 포함하지 않았다.

DB 등록이 언제나 더 나은 선택은 아니다. 출처 변경을 배포 주기에 맞춰도 되고 운영 상태가 단순하다면 코드나 YAML 목록만으로 충분하다. 이번에는 실행 중인 서비스에서 검증·추가·중지를 조작해야 했고, 이미 기사와 연결된 PostgreSQL이 있어 그곳에 상태를 모았다.

## 작성과 검토 범위

구현과 테스트 실행, 글 초안 작성에는 Codex를 활용했다. 출처를 URL로 관리한다는 요구, 기존 기사·요약을 보관하는 정책과 AI 예산 유지 조건은 내가 정했다. 설계안에서 이 조건이 어떻게 반영됐는지 검토하고 진행 방향을 선택했다. 코드와 검증 기록은 위 링크에 남겨 판단 근거를 확인하도록 했다.
