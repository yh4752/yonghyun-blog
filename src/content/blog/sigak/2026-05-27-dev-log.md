# 2026-05-27 개발 로그: 검색 인프라를 실제 MVP 흐름으로 연결하기

## 요약

오늘은 Sigak을 다시 시작하면서 프로젝트의 목표와 현재 상태를 재정렬하고, 3주 안에 포트폴리오용 MVP를 완성하기 위한 실행 계획을 구체화했다. 단순히 일정표를 만든 것에서 끝내지 않고, 실제 코드에서는 로컬 검색 인프라를 확장하고 Spring Boot가 Elasticsearch, Qdrant, Neo4j를 확인할 수 있는 readiness 경계를 추가했다. 이어서 PostgreSQL의 article 데이터를 Elasticsearch article projection으로 재생성하는 내부 endpoint까지 구현했다.

오늘의 핵심 변화는 Sigak이 "PostgreSQL 기반 article API"에서 "검색 projection store를 재생성할 수 있는 AI news search MVP"로 한 단계 이동했다는 점이다.

다만 아직 공개 검색 API가 Elasticsearch를 사용하는 것은 아니다. 현재 단계는 의도적으로 작게 잘랐다.

```txt
PostgreSQL source of truth
-> API-ready article 조회
-> Elasticsearch article projection rebuild
-> indexing metric 확인
```

이렇게 먼저 projection rebuild를 분리해 두면, 다음 단계에서 `/api/articles?query=...`의 내부 구현을 Elasticsearch keyword search로 바꾸더라도 public response shape를 크게 흔들지 않을 수 있다.

## 오늘 완료한 일

### 1. 프로젝트 목표와 3주 개발 일정 재정리

먼저 이력서 관점에서 Sigak이 보완해야 할 지점을 확인했다. 이 프로젝트는 단순 CRUD나 뉴스 카드 UI보다, 다음을 보여주는 편이 더 효과적이라고 판단했다.

- Spring Boot 기반의 명확한 backend architecture
- FastAPI를 AI/RAG 전용 boundary로 분리한 구조
- PostgreSQL을 source of truth로 두는 데이터 모델
- Elasticsearch, Qdrant, Neo4j를 projection store로 사용하는 검색/RAG 준비성
- Docker Compose로 재현 가능한 로컬 실행 환경
- 성능 지표와 indexing/search metric을 확인할 수 있는 구조

처음에는 2주 일정도 논의했지만, Elasticsearch, Qdrant, Neo4j, metrics, 문서화, 배포 준비까지 안정적으로 포함하려면 3주가 더 현실적이라고 봤다. 그래서 v0.1 목표를 2026-06-16까지의 3주 계획으로 정리했고, 프로젝트 상태와 로드맵 문서를 이에 맞춰 갱신했다.

### 2. 로컬 검색 인프라 Docker Compose 확장

검색 기능을 코드로 붙이기 전에 먼저 로컬 인프라가 재현 가능해야 했다. `infra/docker-compose.yml`에 다음 서비스를 정리했다.

- PostgreSQL
- Elasticsearch
- Qdrant
- Neo4j
- FastAPI AI server

Elasticsearch는 keyword search projection, Qdrant는 vector search projection, Neo4j는 article/topic/relation graph projection으로 역할을 나눴다. 중요한 점은 이 셋을 primary data store로 보지 않았다는 것이다. Sigak의 source of truth는 계속 PostgreSQL이고, 검색/그래프 저장소는 PostgreSQL에서 다시 만들 수 있는 projection store로 둔다.

이 결정은 MVP 안정성에 중요하다. 여러 저장소를 동시에 source of truth처럼 다루면 동기화 실패, partial write, 복구 방식이 빠르게 복잡해진다. 반대로 projection store로 정의하면, 실패했을 때 다시 rebuild하면 된다는 단순한 운영 모델을 유지할 수 있다.

### 3. AWS 배포 전략 ADR 작성

AWS 배포도 논의했지만, 오늘 결정은 "지금 당장 AWS를 중심으로 개발하지 않는다"였다. 대신 `docs/decisions/0005-aws-deployment-strategy.md`와 한국어 문서에 다음 방향을 남겼다.

- 로컬 Docker Compose를 기본 개발 및 재현 경로로 유지한다.
- v0.1 후반부에 단일 EC2 + Docker Compose 방식으로 데모 배포를 추가한다.
- ECS, RDS, Amazon OpenSearch Service 같은 managed service 조합은 MVP 이후로 미룬다.
- AWS Budgets, 예상 비용, teardown 절차를 먼저 문서화한 뒤 리소스를 만든다.

이 결정의 핵심은 "클라우드를 안 한다"가 아니다. 클라우드 배포는 포트폴리오의 완성도를 높이는 polish layer로 사용하되, 검색과 RAG의 핵심 흐름보다 앞세우지 않겠다는 뜻이다.

### 4. Spring Boot 검색 인프라 readiness 경계 추가

다음으로 Spring Boot가 Elasticsearch, Qdrant, Neo4j에 접근할 수 있는지 확인하는 readiness boundary를 만들었다.

추가한 내부 endpoint는 다음과 같다.

```http
GET /api/internal/search-infrastructure/health
```

응답은 세 저장소의 상태와 전체 상태를 함께 반환한다.

```json
{
  "overallStatus": "ready",
  "elasticsearch": {
    "status": "ready",
    "detail": "elasticsearch health check succeeded"
  },
  "qdrant": {
    "status": "ready",
    "detail": "qdrant health check succeeded"
  },
  "neo4j": {
    "status": "ready",
    "detail": "neo4j connectivity check succeeded"
  }
}
```

여기서는 실제 검색 기능을 바로 구현하지 않았다. 대신 typed configuration, `RestClient`, Neo4j `Driver`, service test, controller test를 먼저 만들었다. 이 작은 경계를 먼저 둔 이유는 다음 단계의 실패 원인을 더 명확하게 분리하기 위해서다.

```txt
인프라가 죽었는가?
설정값이 틀렸는가?
색인 로직이 잘못됐는가?
검색 쿼리가 잘못됐는가?
```

이 질문들이 한 기능 안에 섞이면 디버깅이 어려워진다. readiness endpoint는 이후 indexing/search 작업의 기반 점검 도구 역할을 한다.

### 5. Article search projection rebuild 구현

오늘의 가장 중요한 코드 변화는 article search projection rebuild다.

새로 추가한 내부 endpoint는 다음과 같다.

```http
POST /api/internal/search-projections/articles/rebuild
```

이 endpoint는 PostgreSQL에 저장된 API-ready article을 읽고, Elasticsearch의 `sigak-articles-v1` index에 색인한다.

현재 projection document에는 다음 필드를 넣었다.

- `id`
- `title`
- `source`
- `url`
- `publishedAt`
- `eventType`
- `primaryCategory`
- `topics`
- `summary`
- `whyItMatters`
- `importanceScore`
- `relatedArticleIds`

Rebuild 응답은 간단한 metric을 포함한다.

```json
{
  "status": "completed",
  "indexName": "sigak-articles-v1",
  "indexedCount": 5,
  "durationMs": 682,
  "failedReason": null
}
```

이 응답은 단순 편의 기능이 아니라, 앞으로 metrics와 research dashboard로 이어질 첫 단위다. 검색 품질이나 성능을 말하려면 먼저 "몇 개를 언제, 얼마나 걸려서 색인했는가"를 남길 수 있어야 한다.

## 설계 고민

### Source of truth와 projection store를 분리하기

오늘 가장 중요한 설계 기준은 PostgreSQL과 검색 저장소의 역할을 분리하는 것이었다.

PostgreSQL은 원문 article, enrichment, 관계형 metadata를 보존하는 source of truth다. Elasticsearch, Qdrant, Neo4j는 각각 keyword, vector, graph retrieval을 위한 projection store다.

이 구분이 중요한 이유는 복구 가능성 때문이다. 검색 인덱스는 언제든 깨질 수 있고, schema를 바꾸거나 analyzer를 바꾸면 다시 만들어야 한다. 이때 원본 데이터가 PostgreSQL에 안정적으로 남아 있으면 projection store는 과감하게 지우고 다시 만들 수 있다.

그래서 rebuild endpoint도 "Elasticsearch가 진짜 저장소"라는 식으로 만들지 않았다. PostgreSQL에서 API-ready article을 읽고, Elasticsearch에 projection을 다시 쓰는 구조로 만들었다.

### Public API와 internal operational API를 분리하기

오늘 추가한 endpoint는 모두 `/api/internal/...` 아래에 두었다.

```txt
/api/internal/search-infrastructure/health
/api/internal/search-projections/articles/rebuild
```

공개 사용자 기능과 운영/개발용 trigger를 섞지 않기 위해서다. 사용자가 보는 API는 계속 다음 형태를 유지한다.

```http
GET /api/articles
GET /api/articles?query={query}
GET /api/articles/{id}
```

반면 search projection rebuild는 개발자나 운영자가 호출하는 작업이다. 나중에 admin authentication이 붙으면 이 경계를 그대로 보호하면 된다.

### 바로 hybrid search로 가지 않은 이유

오늘은 Elasticsearch indexing까지만 진행하고, Qdrant vector indexing이나 RRF hybrid search는 붙이지 않았다.

그 이유는 순서 때문이다. Hybrid search는 keyword result와 vector result가 모두 있어야 의미가 있다. 그런데 지금 단계에서 Qdrant embedding까지 같이 붙이면 다음 문제가 동시에 생긴다.

- embedding 생성 방식 결정
- mock embedding 또는 deterministic embedding 정책
- Qdrant collection schema
- vector search API
- keyword/vector score normalization
- RRF fusion 방식
- benchmark query set

이 모든 것을 한 번에 붙이면 기능은 화려해 보이지만, 실패했을 때 어디가 문제인지 알기 어렵다. 그래서 오늘은 keyword projection rebuild까지만 고정했다.

## 트레이드오프

### Elasticsearch Java Client 대신 RestClient를 사용한 이유

Elasticsearch에는 전용 Java client가 있지만, 오늘은 Spring `RestClient`를 사용했다.

장점은 단순함이다. 현재 필요한 작업은 index 존재 여부 확인, index 생성, document 저장 정도다. 이 수준에서는 HTTP endpoint가 명확하고 테스트도 `MockRestServiceServer`로 가볍게 검증할 수 있다.

대신 손해도 있다. query DSL이 복잡해지고 bulk indexing, analyzer setting, search response parsing이 늘어나면 전용 client가 더 안전할 수 있다. 그래서 현재 선택은 "영구 결정"이 아니라 MVP 초반의 최소 구현이다. 다음 단계에서 bulk indexing이나 복잡한 search query가 필요해지면 client 도입을 다시 검토할 수 있다.

### Rebuild를 bulk API가 아니라 per-document PUT으로 시작한 이유

Elasticsearch indexing은 보통 bulk API가 효율적이다. 하지만 오늘은 seed article이 5개이고, 먼저 검증해야 할 것은 성능보다 데이터 흐름이었다.

그래서 document마다 다음 형태로 저장했다.

```http
PUT /sigak-articles-v1/_doc/{id}?refresh=true
```

이 방식은 큰 데이터셋에는 비효율적이지만, MVP 초기에는 디버깅이 쉽다. 어떤 article ID가 어떤 document로 들어가는지 바로 확인할 수 있고, 테스트 기대값도 명확하다. 나중에 article 수가 늘면 bulk API와 alias 기반 zero-downtime rebuild를 추가하는 것이 더 맞다.

### 실패 시 HTTP 500 대신 metric 응답을 유지한 이유

Projection rebuild service는 실패하면 `status = failed`, `failedReason`을 응답에 담도록 만들었다.

이 선택은 운영 관점에서 약간의 트레이드오프가 있다. HTTP status code만 보면 실패가 명확하지 않을 수 있기 때문이다. 하지만 현재 endpoint는 로컬 개발과 MVP 검증용 내부 endpoint이고, 목표는 "실패 원인을 응답에서 바로 확인하는 것"이다.

추후 admin UI나 CI smoke check에서 사용하게 되면, HTTP status code 정책을 더 엄격하게 바꿀 수 있다. 지금은 metric 응답의 일관성을 우선했다.

## 기술 포인트

### Typed configuration

검색 인프라 설정은 `sigak.search.*` prefix 아래로 묶었다.

```yaml
sigak:
  search:
    elasticsearch:
      url: ${SIGAK_ELASTICSEARCH_URL:http://localhost:9200}
      article-index-name: ${SIGAK_ELASTICSEARCH_ARTICLE_INDEX:sigak-articles-v1}
    qdrant:
      url: ${SIGAK_QDRANT_URL:http://localhost:6333}
    neo4j:
      uri: ${SIGAK_NEO4J_URI:bolt://localhost:7687}
      username: ${SIGAK_NEO4J_USERNAME:neo4j}
      password: ${SIGAK_NEO4J_PASSWORD:sigak-neo4j-password}
```

이 설정은 `SearchInfrastructureProperties`로 바인딩하고 테스트로 검증했다. 문자열을 여러 service에 흩뿌리지 않기 위해서다.

### Elasticsearch index mapping

초기 mapping은 article search에 필요한 필드만 명시했다.

- `title`, `summary`, `whyItMatters`: `text`
- `source`, `eventType`, `primaryCategory`, `topics`: `keyword`
- `publishedAt`: `date`
- `importanceScore`: `integer`
- `relatedArticleIds`: `long`

아직 analyzer tuning은 하지 않았다. 검색 품질 비교를 하기 전에는 analyzer를 과하게 조정하지 않는 편이 낫다고 봤다. 먼저 baseline을 만들고, 실제 query set과 실패 사례를 보고 조정하는 것이 더 공학적인 순서다.

### TDD 흐름

오늘 backend feature는 테스트를 먼저 작성하고 구현했다.

작성한 테스트 범주는 다음과 같다.

- 설정 바인딩 테스트
- readiness service 테스트
- internal health controller 테스트
- projection rebuild service 테스트
- Elasticsearch indexer 테스트
- internal rebuild controller 테스트

특히 Elasticsearch indexer는 실제 Elasticsearch를 테스트에서 띄우지 않고 `MockRestServiceServer`로 HTTP 요청 형태를 검증했다. 반면 최종 smoke check에서는 실제 local Compose의 Elasticsearch에 색인하고 `_count`를 확인했다.

테스트 계층을 이렇게 나눈 이유는 빠른 단위 테스트와 실제 통합 확인의 역할이 다르기 때문이다.

```txt
unit/service test: 코드 계약을 빠르게 고정
local smoke test: Docker Compose 환경에서 실제 연결 확인
```

## 공학적 주제화

### 재생성 가능한 projection은 검색 시스템의 안전장치다

검색 시스템은 원본 데이터베이스와 다르게 자주 바뀐다. index mapping, analyzer, vector dimension, graph projection shape는 제품이 발전하면서 계속 조정된다. 이때 projection을 재생성 가능하게 만들지 않으면, 매번 migration과 동기화 문제가 커진다.

오늘 작업은 작은 endpoint 하나처럼 보이지만, 실제 주제는 "derived data를 어떻게 안전하게 운영할 것인가"에 가깝다.

### 기능보다 관측 가능성을 먼저 둔다

검색 결과를 보여주기 전에 readiness와 rebuild metric을 먼저 만든 것도 의도적인 순서다.

기능이 동작하는지 보여주는 것도 중요하지만, 왜 안 되는지 확인할 수 있어야 다음 기능을 빠르게 붙일 수 있다. `overallStatus`, `indexedCount`, `durationMs`, `failedReason` 같은 값은 작지만 나중에 운영과 실험의 언어가 된다.

### 포트폴리오 프로젝트에서도 운영 경계를 작게 만들어야 한다

포트폴리오 프로젝트는 종종 "많은 기술을 붙였다"는 방향으로 흐르기 쉽다. 하지만 실제로는 기술을 붙인 것보다, 그 기술을 어떤 경계로 격리하고 어떤 순서로 검증했는지가 더 중요하다.

오늘 Sigak에서는 Elasticsearch, Qdrant, Neo4j를 한꺼번에 기능으로 노출하지 않았다. readiness, projection rebuild, public search 전환을 단계로 나눴다. 이 흐름은 MVP에서도 운영 가능한 사고방식을 보여준다.

## 취업용 기술 포인트로 정리하면

이 글에서 강조할 수 있는 역량은 다음과 같다.

- PostgreSQL source of truth와 Elasticsearch/Qdrant/Neo4j projection store를 분리한 설계
- internal readiness endpoint로 인프라 상태를 먼저 관측 가능하게 만든 작업
- public API와 internal operational API를 분리한 backend boundary 설계
- Elasticsearch index mapping과 rebuild endpoint를 통한 derived data 운영 모델
- `MockRestServiceServer` 기반 client test와 Docker Compose smoke test를 분리한 테스트 전략
- `indexedCount`, `durationMs`, `failedReason` 같은 metric을 응답에 포함한 관측 가능성 설계
- AWS를 MVP 후반의 demo deployment로 미루고 local reproducibility를 우선한 범위 조절

## 다음 단계

다음 작업은 Elasticsearch에 색인된 projection을 실제 공개 검색 흐름에 연결하는 것이다.

권장 순서는 다음과 같다.

1. Elasticsearch keyword search service를 추가한다.
2. `/api/articles?query=...`의 내부 구현을 Elasticsearch 우선으로 바꾼다.
3. Elasticsearch가 준비되지 않았을 때는 PostgreSQL 검색 fallback을 유지한다.
4. keyword search latency와 result count를 metric으로 남긴다.
5. 같은 query set으로 PostgreSQL fallback과 Elasticsearch 결과를 비교한다.

이 단계까지 가면 Sigak은 단순히 "Elasticsearch가 Docker에 떠 있다"가 아니라, 실제 article search path에서 Elasticsearch를 사용하는 프로젝트가 된다. 그 다음에 Qdrant vector indexing과 hybrid search로 넘어가는 것이 자연스럽다.
