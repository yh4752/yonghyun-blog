# AI 에이전트가 더 잘 개발하게 만드는 문서 구조 만들기

> 한 줄 요약: Codex가 개발할 때 참고하는 프로젝트 문서가 두 곳에 중복되며 어긋나기 시작했다. 규칙의 단일 출처(AGENTS.md)를 만들고, "읽기 순서 → 개발 생애주기 → 검증 게이트 → 세션 마무리"라는 4블록 구조로 재설계해, 에이전트가 매 세션 일관되게 일하고 검증 없이 끝내지 못하게 했다.

## 이 글에서 다루는 것

- 문제: 사람이 아니라 AI 코딩 에이전트가 주 개발자인 프로젝트에서, 에이전트가 따르는 문서가 중복·분산되면 개발 품질이 흔들린다.
- 핵심 결정: 규칙의 단일 출처를 정하고, 변동 정보와 안정 규칙을 분리하며, "완료"를 명령어로 강제했다.
- 드러나는 역량: 개발 워크플로 설계, 문서를 시스템으로 다루는 관점, AI 에이전트와의 협업 구조화.

## 배경과 문제

Sigak은 내가 직접 손으로 코딩하기보다, Codex 같은 코딩 에이전트에게 구현을 시키고 리뷰하는 방식으로 개발한다. 이 방식에서 **프로젝트 문서는 사람을 위한 참고 자료가 아니라 에이전트의 실행 컨텍스트**다. 에이전트는 매 세션 백지에서 시작해 문서를 읽고 그대로 행동한다.

그런데 문서가 쌓이면서 세 가지 문제가 드러났다.

첫째, 같은 규칙이 두 파일에 중복됐다. 루트에 `AGENTS.md`(Codex가 읽음)와 `CLAUDE.md`(Claude Code가 읽음)가 따로 있었고, 둘 다 아키텍처·기술스택·원칙·MVP 범위를 담았다. 합쳐서 470줄에 가까웠다. 문제는 **둘이 이미 어긋나 있었다**는 점이다. `CLAUDE.md`에는 빌드·테스트 명령어가 있는데 `AGENTS.md`에는 없었고, 반대로 `AGENTS.md`에는 상세 블로그 규칙이 있는데 `CLAUDE.md`에는 없었다. 같은 규칙의 출처가 둘이면 반드시 드리프트가 난다.

둘째, 안정적인 규칙과 자주 변하는 상태가 한 파일에 섞여 있었다. `AGENTS.md`의 "MVP Scope: 현재 포함/나중에" 같은 내용은 `STATUS.md`·`ROADMAP.md`와 겹치는 변동 정보였다. 이게 규칙 파일에 박혀 있으면 상태가 바뀔 때마다 여러 곳을 고쳐야 하고, 안 고치면 에이전트가 낡은 범위로 일한다.

셋째, "어디서부터 읽어라"가 없었다. 2,000줄이 넘는 에이전트 문서가 있는데, 현재 상태는 어디에, 다음 할 일은 어디에, 이 작업의 설계는 어디에 있는지 알려주는 라우팅이 없었다. 에이전트는 매번 컨텍스트를 헤매거나 핵심 문서를 안 읽고 추측했다.

근본 원인은 하나였다. **문서를 "사람이 읽는 글"로만 관리했지, "에이전트가 실행하는 시스템"으로 설계하지 않았다.**

## 선택지와 결정

중복 정리 방식에 세 가지 선택지가 있었다.

| 선택지 | 내용 | 비용 |
| --- | --- | --- |
| 두 파일 유지 + 동기화 규칙만 추가 | 기존 구조 유지, "한쪽 고치면 다른 쪽도" 규칙 추가 | 변경 최소지만 드리프트 근본 원인이 남음 |
| 라우팅/검증만 추가, 통합은 보류 | 읽기 순서와 완료 게이트만 보강 | 효과는 보지만 중복은 그대로 |
| **AGENTS.md를 단일 정본으로 통합** | 규칙은 한 곳, 다른 파일은 그걸 가리킴 | 재작성 비용이 크지만 드리프트 원인 제거 |

세 번째를 골랐다. 이유는 명확했다. 드리프트는 "조심하자"는 규칙으로 막히지 않는다. **출처가 하나여야 구조적으로 어긋날 수 없다.** `CLAUDE.md`에는 도구별 고유 정보(빌드 명령, 파일 책임)만 남기고, 규칙은 전부 `AGENTS.md`로 모은 뒤 "충돌 시 AGENTS.md가 이긴다"를 명시했다.

## 구현

`AGENTS.md`를 7개 블록으로 재작성했고, 그중 네 가지가 핵심이다.

**1. 읽기 순서 + 상태 위치 표 (§0).** 에이전트가 매 세션 무엇을 어떤 순서로 읽을지 못박았다.

```txt
1. AGENTS.md         (규칙)
2. docs/STATUS.md    (현재 상태)
3. docs/ROADMAP.md   (다음 할 일)
4. 해당 spec/plan    (이 작업의 설계)
5. CODING_CONVENTIONS.md (코드 작성 전)
```

그리고 "어떤 정보가 어디 사는가"를 표로 만들어, 같은 정보를 규칙 파일에 다시 복사하지 못하게 했다. MVP 범위 같은 변동 정보는 `STATUS.md`·`ROADMAP.md`로 추방하고 포인터만 남겼다.

**2. 개발 생애주기 (§3).** 그동안 암묵지로만 존재하던 흐름을 명문화했다. 각 단계에 실제 디렉터리를 연결했다.

```txt
결정    -> 구조적 결정이면 docs/decisions/ 에 ADR
스펙    -> docs/superpowers/specs/
계획    -> docs/superpowers/plans/ (체크박스 task)
구현    -> 가장 작은 유용한 변경
검증    -> Definition of Done 게이트 (아래)
기록    -> STATUS 갱신 + 세션 마무리
```

**3. Definition of Done 검증 게이트 (§4).** "무엇을 돌려야 끝난 것인가"를 서비스별 정확한 명령어로 한 곳에 강제했다. 이전에는 이게 세 파일에 흩어져 있었다.

```bash
# backend
./gradlew test
./gradlew check
# frontend
npm test
npm run lint
npm run build
# ai
.venv/bin/python -m pytest
```

핵심은 "**돌리지 않은 명령을 성공으로 쓰지 마라, 검증 안 한 것은 미검증으로 보고하라**"는 규칙을 박은 것이다. 이건 같은 세션에서 정비한 dev-log 작성 규칙(세션에서 검증한 사실만 쓴다)과 정확히 같은 뿌리다. AI 에이전트는 그럴듯한 성공을 지어내기 쉬워서, 완료의 정의를 명령어로 못박지 않으면 검증 없이 끝낸다.

**4. 세션 마무리 루프 (§6).** 세션이 끝날 때 STATUS 갱신 → dev-log 작성 → topic-queue 적립 → 검증/미검증 보고를 하나의 절차로 닫았다.

`CLAUDE.md`는 헤더에서 "`AGENTS.md`가 규칙 정본, 충돌 시 AGENTS 우선"을 명시하고, 중복되던 원칙·git·테스트 블록을 포인터 한 단락으로 축소했다. 빌드 명령·파일 책임 같은 도구별 고유 정보만 남겼다.

## 트레이드오프

얻은 것은 분명하다. 규칙의 출처가 하나가 되어 드리프트가 구조적으로 불가능해졌고, 에이전트는 매 세션 "정본 1 + 현재 상태 1 + 해당 plan 1"만 읽으면 된다. 완료의 정의가 명령어로 강제돼 검증 없이 끝내기 어려워졌다.

미룬 것도 있다. 통합 재작성에는 적지 않은 편집 비용이 들었고, 앞으로 규칙을 바꿀 때 "이건 안정 규칙(AGENTS)인가, 변동 상태(STATUS/ROADMAP)인가"를 매번 판단해야 한다. 이 분류 비용은 감수할 만하다고 봤다. 분류가 흐려질 때 생기는 혼란보다, 경계를 의식적으로 지키는 비용이 더 싸기 때문이다.

`docs/superpowers/specs|plans`의 역할과 포맷을 설명하는 README는 이번에 만들지 않고 다음으로 미뤘다. 생애주기 §3이 가리킬 실제 템플릿이 아직 없다.

## 검증

이번 작업은 코드가 아니라 문서 구조 변경이라, 검증은 "의도한 변경이 실제 파일에 반영됐는가"다.

- `AGENTS.md`: 7개 블록(읽기 순서 / 프로젝트 / 아키텍처 / 생애주기 / DoD 게이트 / 코딩 규칙 / 마무리 루프 / git·보안)으로 재작성. 변동 정보(MVP Scope)는 제거하고 STATUS/ROADMAP 포인터로 대체.
- `CLAUDE.md`: 헤더에 정본 위임 명시, 중복 원칙 블록을 포인터 단락으로 축소.
- DoD 게이트의 명령어는 실제 프로젝트 설정에서 확인한 값을 사용했다(`frontend/package.json`의 `vitest run`/`eslint .`/`tsc -b && vite build`, `ai`의 `.venv` 기반 pytest).

아직 검증하지 못한 것: 이 구조가 **실제로 에이전트의 개발 품질을 높이는지**는 다음 개발 세션에서 Codex가 새 구조를 따라 일해 봐야 확인된다. 지금은 구조를 정비한 단계이고, 효과 측정은 미검증이다.

## 다른 프로젝트에 가져갈 원칙

이 작업에서 일반화할 수 있는 것은 다음과 같다. AI 에이전트가 주 개발자인 프로젝트라면 처음부터 이렇게 시작하는 게 낫다.

1. **규칙은 단일 출처.** 같은 규칙을 두 파일에 두지 않는다. 도구별 파일은 정본을 가리키기만 한다.
2. **안정 규칙과 변동 상태를 분리.** 자주 바뀌는 범위·진행 상황은 규칙 파일에 넣지 않는다.
3. **읽기 순서를 명시.** 에이전트에게 "무엇을 어디서 어떤 순서로 읽어라"를 첫 줄에 준다.
4. **완료를 명령어로 정의.** "done"은 의견이 아니라 통과해야 할 명령 목록이어야 한다. 검증 안 한 것은 미검증으로 보고하게 강제한다.
5. **세션 루프를 닫는다.** 종료 시 상태 갱신·기록·보고를 하나의 절차로 만든다.

문서를 글이 아니라 **에이전트의 실행 시스템**으로 설계하면, AI와의 협업은 매 세션 백지에서 다시 시작해도 일관성을 유지한다.

## 다음 단계

- 다음 개발 세션에서 새 AGENTS.md 구조를 따라 Codex가 일하게 하고, 검증 게이트와 마무리 루프가 실제로 작동하는지 관찰한다.
