# 숫자는 맞았지만 조건이 빠진 AI 요약을 고친 과정

> 원문에 있는 숫자를 인용했는지 확인하는 것과 그 숫자가 뜻하는 범위를 보존하는 것은 달랐다. 요약 지침을 바꾸되 이미 저장된 결과와 미확정 호출을 다시 과금하지 않도록 했다.

## 37%가 무엇을 측정한 결과인가

Sigak은 기술 블로그 본문을 모아 첫 상세 방문 때 한국어 요약을 만든다. 토스·우아한형제들·D2에서 한 편씩 실제 요약을 확인하던 중 우아한형제들 기사에서 조건 누락을 발견했다.

요약에 담긴 LCP 37% 개선은 원문에 있는 숫자였다. 문제는 Galaxy S22+와 Wi-Fi라는 측정 조건이 빠졌다는 점이었다. 원문에는 별도로 실사용에서 관측한 25–35% 개선도 있었다. 두 결과를 구분하지 않으면 특정 장비에서 얻은 값을 실제 사용자 전체의 결과로 읽을 수 있다.

이 사례는 2026-11-02 구현 기록에서 확인했다. 아래 표는 당시 읽고 대조한 조건을 정리한 것이며 새로운 실험 결과가 아니다.

| 결과 | 함께 읽어야 하는 조건 |
| --- | --- |
| LCP 37%, 1340→847ms | Galaxy S22+·Wi-Fi·가게홈 측정 |
| 실사용 LCP 25–35% | 주요 기기 한 대·적용 전후 각 1주일·p50/p75/p90 |

인용 문장이 원문에 있는지 검사해도 조건 누락은 남았다. 인용한 문장은 맞아도 요약에서 조건을 생략하거나 다른 실험의 조건을 붙이면 의미가 달라진다.

## 지침, 구조화된 수치, 두 번째 검토 모델을 비교했다

사용자는 수치와 측정 조건을 함께 담도록 개선하되 기존 5달러 한도를 유지하도록 요청했다. 세 가지 방법을 비교했다.

| 방법 | 기대한 효과 | 감수할 비용 |
| --- | --- | --- |
| 기존 요약 지침 강화 | 현재 응답 형식에서 조건 보존을 요구 | 모델이 지침을 항상 지킨다고 보장할 수 없음 |
| 수치·조건을 별도 필드로 추출 | 화면과 검증에서 대응 관계를 명시 | API·저장·화면 계약을 함께 늘려야 함 |
| 두 번째 모델로 결과 검토 | 생성 결과를 별도로 읽고 확인 | 매번 추가 호출과 대기, 검토 모델의 오류 가능성 |

우선 기존 지침을 강화했다. 한 건의 확인된 문제에 대응하면서 API와 화면을 넓히지 않는 선택이었다. 나중에 체계적인 수치 비교가 제품 기능이 되면 구조화된 필드를 검토할 수 있지만, 지금은 요약 문장 안에서 범위를 지키는 것이 목표였다.

## 숫자보다 조건을 남길 수 있게 했다

새 지침은 해석에 필요한 측정 조건을 골라 남기도록 했다. 장비·네트워크·작업량·데이터셋·기간·백분위 중 원문에 있고 결과를 이해하는 데 필요한 조건을 수치와 같은 문장에 담는다.

실험실 결과와 실사용 관측, 추정값을 구분하고 다른 실험의 조건을 합치지 않게 했다. 문장이 길어지면 덜 중요한 사실을 빼고, 맥락이 부족하면 수치 자체를 생략하도록 했다. 원문에 없는 조건이나 통계적 유의성을 만들어 넣는 것도 금지했다.

이 규칙은 `summary`와 `whyItMatters` 모두에 적용한다. 본문 전체를 보내는 경계와 기존 출력 길이·입력 크기·예산 한도는 유지했다. 모델을 바꾸거나 외부 자료를 검색해 빈 조건을 채우는 기능은 추가하지 않았다.

```txt
원문에 수치가 있음
  -> 결과의 종류와 필요한 측정 조건을 확인
  -> 같은 문장에 수치·조건·비교 기준을 보존
  -> 충분히 정확하게 설명하기 어려우면 수치를 생략
```

## 지침 변경과 기존 결과의 재생성은 별개다

새 지침은 `article-summary-v3-metric-context`로 식별한다. 버전만 바꿨다고 기존 결과를 전부 다시 만들지는 않는다.

이미 저장된 v2 전문 요약은 `READY`로 재사용한다. 과거 `UNKNOWN`도 지침이 달라졌다는 이유로 새 요청이 되지 않는다. 응답을 잃은 외부 호출을 다시 보내면 같은 기사에 비용을 또 쓸 수 있기 때문이다. 전문 준비 worker도 기존 전문 작업을 알아보고 복구 대상을 고른다.

| 기존 상태 | 지침 변경 뒤 처리 |
| --- | --- |
| 유효한 v2 FULL_TEXT READY | 기존 결과 반환 |
| 이전 지침의 UNKNOWN | 보수 차감 유지, 자동 재호출 없음 |
| 새로 요약이 필요한 기사 | v3로 요청, 기존 예산 사용 |

공개 응답은 두 버전 모두 `FULL_TEXT`로 표시한다. API와 화면에 버전 선택 기능을 노출하지 않았다. 지침의 버전 관리와 사용자가 보는 본문 범위를 구분한 것이다.

## 실제 비교는 문제를 발견한 한 건으로 제한했다

2026-11-02에는 기사 221 한 건만 별도로 v3 작업에 예약했다. 이 작업도 직접 AI를 부르는 지름길을 만들지 않고 기존 Spring의 작업 확보·보수 차감·호출·저장을 거쳤다.

예약 전에는 기사 행을 잠그고 이전 READY와 입력 hash, 본문 일치, 새 v3 작업과 UNKNOWN의 부재, 예산을 확인했다. 새 결과가 성공하기 전까지 기존 요약을 계속 보여 주고, 성공한 뒤에만 현재 결과를 전환했다. 공개 재생성 API나 전체 일괄 갱신 기능은 만들지 않았다.

당시 새 결과에서 위 표의 실험과 실사용 조건이 구분된 것을 읽고 확인했다. 저장된 전문과 AI 입력은 같았고, 이전 9개 작업 행과 이전 요약 텍스트는 보존됐다.

| 2026-11-02 관측 | 값과 범위 |
| --- | --- |
| 새 생성 | 기사 221 한 건, READY/FULL_TEXT/v3 |
| 확인된 입력·출력 | 8668 / 524 token |
| 설정 단가로 계산한 추정액 | $0.002363 |
| 앱의 보수 차감 | $0.02 추가, 당시 누적 $0.18→$0.20 |
| 저장 결과 재요청 | 추가 호출 0 |

추정액은 결제 영수증이 아니며 이전 UNKNOWN의 실제 비용은 이 계산으로 확정하지 못한다. 이번 글 작성에서는 새 유료 요약을 생성하지 않았다. 총 5달러 요청에 따른 앱 4달러 중단·일 20회·총 200회 규칙도 유지했다.

## 검증: 계약 검사와 의미 평가는 나눴다

AI fixture는 실제 모델 대신 가짜 응답을 사용한다. 지침이 신뢰된 `instructions`에 들어가는지, 원문 전체와 버전·한도가 유지되는지, 결과의 근거 인용과 형식이 검증되는지를 확인한다. 가짜 응답에 조건을 넣고 통과했다고 실제 모델이 모든 기사에서 조건을 잘 보존한다고 말할 수는 없다.

이번 2026-11-03 배치에서는 AI 70개와 backend 344개 테스트 및 `check`가 통과했다. backend 일별 한도 검사는 처음에 테스트 DB의 한국 날짜와 운영 UTC 날짜가 달라 실패했고, 테스트 준비 날짜 두 곳을 UTC로 맞춘 뒤 재검증했다. 운영 로직은 바꾸지 않았다.

```bash
# ai/: 실제 키 대신 시험용 값, 가짜 응답과 로컬 HTTP fixture
OPENAI_API_KEY=test-only-not-a-real-key .venv/bin/python -m pytest

# 저장소 루트: Testcontainers DB와 mock provider를 사용하는 검사
./backend/gradlew -p backend test check
```

새 지침의 의미 준수 근거는 여전히 과거 실제 한 건의 비교다. 기사 길이·표·단위·상반된 실험이 더 복잡한 글까지 넓힌 품질 평가와 사용자 평가는 남아 있다.

이 사례에서 다시 설명할 질문은 세 가지다. 근거 인용이 존재하는데도 요약이 왜 오해를 만들었는가? 조건을 모두 나열하기보다 숫자를 생략하는 선택은 언제 필요한가? 지침을 개선하면서도 기존 결과와 미확정 비용을 왜 자동 재처리하지 않았는가?

구현·검증과 글 정리에는 Codex를 활용했다. 사용자가 요청한 조건 보존과 예산 제약이 실제 코드에 어떻게 반영됐는지, 기록으로 확인한 결과와 아직 평가하지 못한 범위를 구분했다.
