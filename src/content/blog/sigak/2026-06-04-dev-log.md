# 2026-06-04 개발 로그: graph-aware evaluation runner 구현과 smoke 검증

## 요약

오늘은 graph-aware article detail을 검색 성능이 아니라 설명 가능성 관점에서 평가하기 위한 runner를 구현했다.
기존 retrieval benchmark runner에 `--include-graph-context` 옵션을 추가하고, public search top-k 결과를 source article로 삼아 public article detail과 public graph-context를 수집하도록 연결했다.
결과 artifact는 search miss, related baseline coverage, graph reason coverage, topic coverage, failure/empty context, public API round-trip latency를 분리해서 남긴다.
3-query/6-article label set으로 local smoke를 실행했지만, 이 값은 품질 결론이 아니라 pipeline 재현성 확인 근거로만 해석한다.

## 설계 고민 / 결정

Graph-aware detail은 query-to-article ranking 자체를 바꾸는 기능이 아니다.
따라서 이번 runner는 검색 metric을 graph 점수로 대체하지 않고, public search top-k에서 사용자가 들어갈 수 있는 article detail이 related reason/topic으로 어떤 설명 근거를 제공하는지 따로 기록한다.

Backend internal graph endpoint를 호출하지 않고 public endpoint만 사용했다.
이렇게 하면 artifact가 실제 사용자에게 노출되는 public-safe shape에 맞춰지고, Neo4j timing이나 relation type 같은 내부 진단 정보가 report에 섞이지 않는다.

Metric에서는 `searchMissedPositiveIds`를 별도로 둔다.
검색 단계에서 positive article을 놓친 경우와 graph context가 설명하지 못한 경우를 섞으면 개선 방향이 흐려지기 때문이다.

## 트레이드오프

- 얻은 것: graph-aware context를 기존 retrieval benchmark artifact와 같은 흐름에서 재현 가능하게 실행할 수 있다.
- 얻은 것: failure context와 empty context를 분리해서 Neo4j 장애/빈 projection/설명 부족을 구분할 수 있다.
- 포기한 것: 이번 범위에서는 pure Neo4j query latency를 측정하지 않는다. `averageGraphLatencyMs`는 public API round-trip이다.
- 포기한 것: relation reason을 사실 검증하지 않는다. report에는 `stored_projection_reason`이라는 출처만 남긴다.
- 미룬 것: 3-query/6-article smoke set은 품질 주장에 부족하므로, 더 큰 catalog와 label set 확장은 다음 단계로 둔다.

## 다음 단계

- 현재 3-query/6-article smoke label set을 더 큰 catalog와 10-15개 이상 reviewed query로 확장한다.
- Graph-aware report에서 search miss가 많은 query와 graph reason이 실제로 도움이 되는 query를 나눠 블로그/포트폴리오 설명으로 정리한다.
- `/research` 또는 report 기반 metrics view에서 retrieval metric과 graph-aware explanation metric을 함께 보여줄 방법을 설계한다.
- 필요하면 pure Neo4j query latency를 위한 backend-side/internal metric을 별도 설계한다.
