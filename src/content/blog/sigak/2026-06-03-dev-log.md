# 2026-06-03 개발 로그: Neo4j graph projection, public detail reason, graph-aware evaluation 설계

## 요약

오늘은 PostgreSQL에 저장된 API-ready article/topic/relation metadata를 Neo4j projection으로 재생성하는 흐름을 구현했다. 이어서 public article detail 화면에서 related article의 relation reason을 볼 수 있도록 public graph-context companion API와 frontend 표시를 추가했다.

핵심 방향은 PostgreSQL을 source of truth로 유지하고, Neo4j는 Elasticsearch/Qdrant와 같은 rebuildable projection store로만 쓰는 것이다. Public `ArticleResponse`는 바꾸지 않고, 별도 `GET /api/articles/{id}/graph-context` endpoint로 graph reason을 보강했다.

마무리 단계에서는 이 graph reason이 실제로 어떤 설명 가치를 주는지 평가하기 위한 `graph-aware evaluation` 설계도 정리했다. 구현은 아직 하지 않았고, 작은 3-query/6-article dataset에서는 품질 결론을 내리지 않는다는 해석 기준까지 문서에 명시했다.

작성 기준:

- 이 로그는 GitHub 커밋 `a277e41 feat: add neo4j graph-aware article detail`과 `6c86ed1 docs: add graph-aware evaluation plan`에 남은 작업/검증 기록을 기준으로 정리했다.
- `f4d7ecb feat: add retrieval benchmark system comparison`의 strict `HYBRID`/`PUBLIC` 검색 평가 비교는 `docs/blog/2026-06-02-dev-log.md`의 추가 진행과 별도 주제 글에 이미 기록되어 있어 이 로그에서는 중복으로 풀어 쓰지 않았다.
- 이번 문서 작성 세션에서는 backend/frontend/AI 테스트를 재실행하지 않았다. 아래 검증 표의 test/smoke 결과는 당시 구현 세션 기록 기준이다.

## 설계 고민 / 결정

Neo4j를 원본 저장소로 쓰지 않고 projection store로 제한했다. Article의 최종 응답 데이터는 여전히 PostgreSQL에서 읽고, Neo4j에는 article metadata, topic, relation type, relation reason만 저장한다.

Projection rebuild는 collection 직후 자동 실행하지 않았다. MVP에서는 수동 rebuild endpoint로 먼저 count, latency, context shape를 관찰하는 편이 실패 원인 분리에 유리하다고 봤다.

Internal graph context를 먼저 만든 뒤 public article detail에 붙였다. 이때 기존 `ArticleResponse`에 graph field를 넣지 않고 별도 public companion endpoint를 추가했다. `ArticleResponse`는 list/search/detail/bulk lookup이 공유하므로, 상세 화면에만 필요한 graph reason 때문에 공용 응답 계약을 흔들지 않는 쪽이 더 안전하다고 판단했다.

Public graph-context endpoint는 PostgreSQL article 존재 여부를 먼저 확인한다. Neo4j context가 없거나 Neo4j가 내려가 있으면 empty context로 degrade한다. Relation reason은 보조 정보이므로 graph 장애가 article 본문 조회 실패로 번지지 않게 했다.

Graph-aware evaluation은 새 backend internal endpoint부터 만들지 않고 기존 Node retrieval benchmark runner를 확장하는 방향으로 설계했다. 이유는 지금 필요한 것이 순수 Neo4j query latency나 relation type 진단이 아니라, public article detail에서 실제로 보이는 graph context가 related article baseline보다 어떤 설명 정보를 더 주는지 확인하는 것이기 때문이다.

평가 해석도 일부러 보수적으로 잡았다. 현재 label set은 3-query/6-article이라 통계적 의미가 없으므로, report는 smoke only로 표시해야 한다. 또 positive article이 public search top-k에서 빠지면 graph context를 볼 기회가 사라지기 때문에, `searchMissedPositiveIds`와 graph coverage를 분리하기로 했다. Reason/topic도 "검증된 사실"이 아니라 저장된 projection reason이라는 출처를 report에 남기도록 설계했다.

## 트레이드오프

얻은 것:

- Neo4j graph projection을 실제 backend application flow로 재생성할 수 있다.
- Relation reason과 shared topic을 internal API로 확인할 수 있다.
- Public article response shape를 바꾸지 않고 상세 화면에서 relation reason을 표시할 수 있다.
- Neo4j unavailable 상황에서도 public graph-context endpoint가 empty context로 degrade한다.

미룬 것:

- Graph-aware context를 keyword/vector/hybrid retrieval baseline과 비교하는 구현과 smoke run은 아직 하지 않았다. 대신 평가 설계만 완료했다.
- Topic synonym, multilingual normalization, relation quality scoring은 MVP 이후 관찰 데이터가 쌓인 뒤 다시 설계한다.
- Backend-side Neo4j query latency 측정은 미뤘다. 이번 graph-aware evaluation은 public API round-trip latency만 기록하도록 설계했다.

`docs/blog/topic-queue.md`의 `PostgreSQL source of truth와 Neo4j projection store를 분리한 이유` 후보를 public graph-aware detail 내용으로 보강했다.

이 주제는 새 projection store 도입, source of truth/projection 경계, manual rebuild trade-off, internal/public API 분리, public fallback, smoke count/latency 검증이 모두 있어 회사 기술 블로그 소재로 발전시키기 좋다.
