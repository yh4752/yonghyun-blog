## 설계 고민 / 결정

검색 평가 도구는 이제 "만들었다"보다 "어떤 수준까지 검증했는가"가 더 중요해졌다.
그래서 사용자 수동 확인을 자동 테스트처럼 과장하지 않고, 실제 브라우저 사용 확인과 Codex가 실행한 정적 검사를 분리했다.

다음 작업은 바로 benchmark runner를 만들기보다, 먼저 API-ready article을 더 큰 frozen catalog로 export하는 설계를 잡는 쪽이 맞다.
현재 seed article 5개만으로는 Recall@5나 MRR@5 같은 수치가 포트폴리오에서 설득력 있는 검색 품질 근거가 되기 어렵기 때문이다.

### 설계 고민 / 결정

첫 benchmark는 Spring Boot command나 Python IR toolchain이 아니라 Node.js script로 만들었다.
이유는 현재 목적이 검색 알고리즘 튜닝이 아니라 "사람이 만든 정답지 기준으로 검색 결과를 재현 가능하게 평가하는 최소 흐름"을 고정하는 것이기 때문이다.

또한 keyword/vector/hybrid 3-way 비교를 바로 넣지 않았다.
현재 public API는 hybrid mode를 기본으로 사용하고, 공정 비교를 하려면 같은 query를 같은 조건에서 mode별로 실행하는 계약이 더 필요하다.
그래서 이번에는 현재 public search API run을 평가하고, mode 비교는 다음 확장으로 남겼다.

### 트레이드오프

- 얻은 것
  - backend가 꺼져 있어도 label parsing과 metric 계산을 단위 테스트할 수 있다.
  - `qrels -> run -> metrics -> report` 구조가 생겨 나중에 query와 mode를 늘려도 artifact 형태를 유지할 수 있다.
  - Top1 Strong Hit, Recall@5, MRR@5, LatencyMs를 실제 JSON/Markdown report로 남길 수 있다.
- 미룬 것
  - keyword-only/vector-only/hybrid 공정 비교는 아직 없다.
  - nDCG, p50/p95 반복 측정, 통계 검정은 아직 없다.
  - 이번 smoke는 deterministic embedding mode이므로 semantic search 품질 근거로 쓰지 않는다.

### 설계 고민 / 결정

Related article N+1은 frontend만 고쳐서는 해결되지 않는다.
기존 detail response가 `relatedArticleIds`만 제공하므로, 백엔드에 같은 article response 배열을 반환하는 bulk ID 조회를 추가하는 쪽이 가장 작은 변경이었다.
이 방식은 detail DTO를 새로 키우지 않고도 요청 수를 줄이고, PostgreSQL source of truth에서 API-ready article만 다시 읽는 기존 원칙을 유지한다.

Repository graph prefetch는 처음에 repository interface default method로 옮겼지만, Spring Data가 이를 query method로 해석해 context 생성이 실패했다.
그래서 custom repository fragment로 바꿨다. 이 선택은 service의 persistence loading 전략 책임을 줄이면서도 Spring Data의 확장 패턴 안에 머무르는 절충이다.

### 트레이드오프

- 얻은 것
  - related article 2개면 detail API 2회가 아니라 bulk API 1회로 줄어든다.
  - 날짜 parsing과 elapsed measurement 중복이 사라졌다.
  - collection HTTP fetch가 무한 대기하지 않도록 timeout 기본값을 갖게 됐다.
  - enrichment 저장 시 model name을 persistence service 문자열이 아니라 response metadata에서 가져온다.
- 미룬 것
  - Kotlin mock enrichment와 FastAPI mock enrichment를 완전히 하나로 합치지는 않았다. Spring HTTP enrichment mode 전환은 S2/S3 범위의 구조 변경으로 남겼다.
  - related article summary를 detail response에 inline으로 싣는 방식은 DTO를 키우는 변경이라 이번에는 선택하지 않았다.
  - 브라우저 화면 수동 smoke는 이번 세션에서 실행하지 않았다.
