# 2026-05-07 개발 로그: Mock MVP에서 Persistence와 Research Portfolio 구조로 이동하기

## 요약

5월 5일에는 mock data 기반으로 Sigak의 제품 계약과 UI 흐름을 먼저 고정했다. 이후 작업의 중심은 실제 서비스에 필요한 데이터 기반으로 옮겨갔다. 오늘 글은 2026-05-06부터 2026-05-08까지 이어진 persistence, collection, enrichment, 문서 구조 정리 작업을 하나의 흐름으로 정리한다.

핵심 변화는 Sigak이 단순 mock article demo에서 PostgreSQL source of truth, collection pipeline, mock enrichment, research portfolio strategy를 갖춘 프로젝트로 이동했다는 점이다.

```txt
Mock article API
-> PostgreSQL persisted article model
-> Collection and enrichment foundation
-> Public API stabilization
-> Research portfolio documentation
```

이 단계에서도 Elasticsearch와 Qdrant는 바로 붙이지 않았다. 먼저 원본 article과 enrichment output을 저장하고, public API가 API-ready article만 노출하도록 안정화하는 것이 더 중요했기 때문이다.

## 오늘 완료한 일

### 1. PostgreSQL 기반 persistence MVP 도입

Mock article data를 PostgreSQL 기반 persisted model로 옮겼다. 주요 작업은 다음과 같다.

- PostgreSQL Docker Compose 구성
- Spring Boot datasource와 Flyway 설정
- article, source, raw content, enrichment, topic, relation schema 작성
- JPA entity와 repository 구현
- curated seed article data 추가
- persisted article list/detail/search API 연결
- Testcontainers 기반 PostgreSQL integration test 작성

이 작업으로 article API는 더 이상 메모리 mock data만 의존하지 않게 됐다. 특히 raw content와 enrichment output을 분리한 점이 중요하다. 나중에 요약 prompt를 바꾸거나 embedding을 다시 만들거나 Graph RAG metadata를 보강할 때, 원문과 AI 결과를 따로 보존해야 재처리가 가능하다.

### 2. Public API-ready filtering 안정화

Persistence가 들어오면 모든 row가 곧바로 public API에 노출되면 안 된다. 수집 중인 article, enrichment가 실패한 article, 아직 publish되지 않은 article이 public response mapping을 깨뜨릴 수 있기 때문이다.

그래서 public article API는 `PUBLISHED` 상태이고 current enrichment가 있는 article만 노출하는 방향으로 정리했다. 이 결정은 단순한 필터링이 아니라 public contract의 안정성을 지키는 장치다.

### 3. Collection foundation 구현

수집 pipeline은 넓은 웹 크롤러가 아니라 명시적인 source registry에서 시작하도록 만들었다.

구성한 기반은 다음과 같다.

- source registry
- RSS/Atom collector parser
- arXiv collector parser
- collected article domain model
- article normalizer
- local mock enrichment client
- collection pipeline service
- collector, normalizer, service tests

초기 source는 공식 블로그, 연구 source, 주요 기술 update를 중심으로 제한했다. Hacker News 같은 aggregator나 일반 개인 블로그는 초기 원본 source에서 제외했다. Sigak은 "많이 모으는 서비스"가 아니라 "중요한 기술 변화를 신뢰 가능한 source에서 선별하는 서비스"이기 때문이다.

### 4. FastAPI AI server와 mock enrichment 위치 정리

FastAPI server는 AI/RAG 전용 boundary로 유지했다. 현재는 외부 API key 없이도 local development가 가능해야 하므로 mock enrichment mode를 먼저 사용한다.

의도한 방향은 다음과 같다.

```txt
AI_ENRICHMENT_MODE=mock
AI_ENRICHMENT_MODE=openai
AI_ENRICHMENT_MODE=local
```

중요한 점은 AI agent를 먼저 만드는 것이 아니라, 구조화된 enrichment contract를 먼저 안정화하는 것이다. summary, why-it-matters, topics, category, importance candidate처럼 output schema가 명확한 작업은 agent보다 일반 LLM call과 validation으로 시작하는 편이 더 안전하다.

### 5. MVP article flow 안정화

Persistence와 collection 기반이 추가되면서 기존 public flow의 리스크도 정리했다.

- API-ready article만 public API에 노출
- article detail에서 related article stale state 방지
- FastAPI enrichment input validation 강화 방향 정리
- CORS와 persisted article test 정합성 보강

이 작업은 기능 추가보다 안정화에 가깝다. 하지만 수집 pipeline이 붙기 시작하면 데이터 상태가 다양해지기 때문에, public API가 incomplete data에 흔들리지 않도록 먼저 정리해야 했다.

### 6. Research portfolio 방향 정리

Sigak은 단순 뉴스 앱이 아니라 LLM/RAG 연구 포트폴리오로도 읽힐 수 있어야 한다. 그래서 연구 방향을 다음처럼 정리했다.

```txt
실제로 사용할 수 있는 기술 뉴스 인사이트 서비스
+ LLM/RAG 실험 결과를 제품 안에서 보여주는 Research Dashboard
```

핵심은 "RAG를 썼다"가 아니라 "retrieval 방식이 품질을 개선했는지 평가했다"를 보여주는 것이다.

준비한 연구 트랙은 다음과 같다.

- keyword/BM25, dense retrieval, hybrid retrieval 비교
- no-RAG vs retrieved-context RAG 비교
- graph-aware context가 insight 품질에 주는 영향 분석
- unsupported claim, evidence coverage 같은 failure analysis
- event type/category/importance bucket classification의 zero-shot, few-shot, fine-tuning 비교

Fine-tuning은 바로 생성형 요약 모델을 학습시키기보다 작은 classification task부터 시작하는 방향으로 정했다. 데이터셋과 baseline 없이 fine-tuning을 붙이면 오히려 설득력이 떨어질 수 있기 때문이다.

### 7. 문서 구조 재정리

문서가 늘어나면서 읽는 순서가 흐려졌다. 그래서 docs 구조를 portfolio-facing 문서와 working record로 나눴다.


- ADR과 blog는 의사결정과 개발 과정을 보여주는 역사 기록으로 유지한다.
- `superpowers/`는 구현 중 작성한 spec과 plan으로 두되, 메인 독자 경로에서는 분리한다.

## 설계 고민

### Persistence를 붙이기 전에 public API를 유지해야 했다

DB를 붙이는 순간 데이터 상태가 다양해진다. 단순히 article table이 생기는 것보다 중요한 문제는 어떤 article을 public API에 노출할 것인가다.

그래서 `PUBLISHED`이고 current enrichment가 있는 article만 public response로 변환하는 기준이 필요했다. 이 기준이 없으면 수집 중인 incomplete article이 API 응답 변환 중 오류를 만들 수 있다.

### Raw content와 enrichment output을 분리한 이유

AI 기능은 한 번 만들고 끝나는 영역이 아니다. prompt, model, category rule, importance scoring 기준이 계속 바뀔 수 있다.

그래서 article raw content와 enrichment result를 분리해서 저장해야 한다. 원본을 다시 scraping하지 않고도 새로운 prompt나 embedding strategy로 재처리할 수 있어야 하기 때문이다.

### Collection을 broad crawling으로 시작하지 않은 이유

뉴스 수집이라고 하면 crawler를 넓게 만드는 방향으로 가기 쉽다. 하지만 Sigak은 범용 crawler가 아니라 기술 뉴스 insight platform이다.

초기에는 source registry를 명시적으로 두고, 신뢰할 수 있는 source만 수집하는 편이 맞다. 이 방식은 수집량은 제한되지만 품질, 재현성, debugging 측면에서 유리하다.

## 트레이드오프

### PostgreSQL은 도입하고 Elasticsearch/Qdrant는 미룬 이유

PostgreSQL은 지금 필요했다. article, raw content, enrichment, topic, relation metadata를 보존해야 collection과 AI pipeline이 의미를 갖기 때문이다.

반면 Elasticsearch와 Qdrant는 아직 미뤘다. 검색 인덱스와 vector store는 source of truth가 안정화된 뒤 projection으로 붙이는 편이 낫다. 원본 데이터가 안정화되기 전에 검색 store를 붙이면 schema와 동기화 방식이 계속 흔들릴 수 있다.

### Mock enrichment를 유지한 이유

외부 LLM API를 바로 붙이면 실제 AI 기능처럼 보일 수 있다. 하지만 API key, 비용, rate limit, 응답 비결정성이 local development를 어렵게 만든다.

그래서 mock enrichment를 유지했다. 이 선택은 AI 기능을 포기한 것이 아니라, LLM provider를 나중에 교체할 수 있는 boundary를 먼저 만든 것이다.

### Research Dashboard를 문서가 아니라 제품 안에 두려는 이유

연구 결과를 README 표로만 보여주면 서비스와 연구가 분리되어 보일 수 있다. 반대로 `/research` 같은 제품 내부 route에서 retrieval benchmark, RAG evaluation, failure analysis를 보여주면 실제 데이터 pipeline 위에서 실험이 돌아간다는 점을 더 잘 보여줄 수 있다.

다만 dashboard가 서비스보다 먼저 커지면 안 된다. article persistence, collection, enrichment, search가 먼저 안정화되어야 research dashboard가 의미를 가진다.

## 기술 포인트

### Flyway와 JPA entity

Persistence는 Flyway migration으로 schema를 만들고 JPA entity로 읽는 구조를 사용했다. Schema가 명시적으로 남기 때문에, 포트폴리오 독자도 어떤 데이터 모델을 의도했는지 확인할 수 있다.

JPA entity는 Hibernate proxy를 고려해 Kotlin all-open 설정을 보강했다. Kotlin class는 기본적으로 final이기 때문에 JPA와 함께 쓸 때 이 지점이 중요하다.

### Testcontainers 기반 integration test

Local PostgreSQL에 직접 의존하는 테스트는 개발자 환경에 따라 흔들릴 수 있다. 그래서 핵심 persistence test는 Testcontainers 기반으로 격리했다.

이 선택은 테스트 속도에는 약간의 비용이 있지만, schema와 repository 동작을 실제 PostgreSQL에 가깝게 검증할 수 있다.

### Collection pipeline boundary

수집 흐름은 collector, normalizer, enrichment client, persistence service로 나눴다.

```txt
source registry
-> collector
-> normalizer
-> enrichment client
-> persistence
-> public article API
```

각 단계가 분리되어 있어야 RSS/Atom, arXiv, future API source를 추가해도 전체 pipeline을 매번 다시 쓰지 않아도 된다.

## 공학적 주제화

### 데이터 상태가 많아질수록 public contract가 중요해진다

Mock data에서는 모든 article이 완성된 상태다. 하지만 실제 pipeline에서는 discovered, fetched, normalized, enriched, failed, published 같은 상태가 생긴다.

이때 public API가 어떤 상태의 데이터를 노출하는지 명확하지 않으면 사용자는 불완전한 데이터를 보게 되고, 백엔드는 response mapping에서 실패할 수 있다. 오늘 작업의 핵심은 persistence 자체보다 public contract를 데이터 상태로부터 보호하는 것이었다.

### AI 기능은 provider보다 boundary가 먼저다

OpenAI API나 local model을 붙이는 것은 중요하지만, 더 먼저 필요한 것은 입력과 출력의 schema다. 어떤 raw content를 보내고, 어떤 summary와 topic과 importance signal을 받아야 하는지 정해야 provider를 교체할 수 있다.

Mock enrichment는 이 boundary를 검증하기 위한 장치다.

### 연구 포트폴리오는 기능명이 아니라 평가로 설득해야 한다

RAG, GraphRAG, fine-tuning이라는 단어만으로는 충분하지 않다. 어떤 baseline과 비교했고, 어떤 query set을 사용했고, 어떤 failure case를 발견했는지가 더 중요하다.

그래서 Sigak의 연구 방향은 기능 추가보다 evaluation artifact를 남기는 쪽으로 잡았다.
