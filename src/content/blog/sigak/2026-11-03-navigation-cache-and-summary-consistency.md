# 화면 복귀의 대기를 줄이면서 완성된 AI 요약을 지키기

> 같은 데이터를 다시 기다리는 시간을 줄이되, 새로 완성된 요약을 오래된 응답이 지우지 않게 했다.

## 읽고 돌아왔는데 목록을 다시 기다렸다

Sigak에서는 기술 글 목록에서 기사를 열고 홈으로 돌아올 수 있다. 이미 본 목록인데도 홈이 다시 mount될 때 데이터를 버리고 전체 목록 GET을 기다렸다. 기사 상세도 목록에서 받은 제목과 소개글을 다시 받을 때까지 로딩 화면을 보였다.

2026-10-30 기록의 목록은 173개, 238,743bytes였다. 같은 응답의 로컬 GET은 0.224초였지만 외부 identity 전송은 28.430초, gzip 전송은 76,571bytes에 4.795초였다. Caddy 압축은 이미 켜져 있었다. 서버 압축을 새로 켜는 것보다 화면 이동마다 같은 데이터를 다시 기다리는 구조를 먼저 바꿀 이유가 있었다.

이 문제는 목록과 상세를 오가는 다른 서비스에도 생긴다. 데이터를 저장하는 것에 더해, 언제 보여 주고 언제 갱신하며 늦은 응답을 어떻게 다룰지 정해야 한다. Sigak에서는 상세를 연 뒤 AI 요약이 비동기로 완성되므로, 캐시된 기사의 내용도 요청 사이에 달라졌다.

## 탭 안에서 짧게 재사용하는 쪽을 택했다

| 방식 | 얻는 것 | 감수할 점 |
| --- | --- | --- |
| 화면 진입마다 GET | 매번 서버 응답을 확인 | 복귀 때도 전송을 기다림 |
| 탭 메모리에 DTO 보관 | 기존 내용을 즉시 표시 | 만료·갱신 실패·응답 경합을 처리해야 함 |
| 브라우저 영구 저장이나 별도 조회 라이브러리 | 재시작 뒤 재사용 또는 더 넓은 캐시 관리 | 저장 버전·무효화 또는 새 도구를 관리해야 함 |

이번 구현은 두 번째다. 마지막 행은 확장할 때 비교할 대안이며, 모든 도구를 실제로 도입해 성능 비교한 결과는 아니다. 현재 요구에는 목록과 상세의 같은 DTO를 잠시 재사용하는 범위로 시작했다.

저장 후 60초 동안은 GET 없이 재사용한다. 60초가 지나도 5분까지는 이전 내용을 먼저 보여 주고 갱신을 기다린다. 5분을 넘긴 항목은 읽을 때 제거한다. 목록은 검색어 키 12개, 상세는 기사 ID 256개로 제한한다. 이 제한은 Map의 항목 수이며, 목록 배열까지 포함한 전체 메모리의 byte 상한은 아니다.

```txt
화면 진입
  ├─ 5분 이내 DTO가 있으면 먼저 표시
  └─ 데이터 요청
       ├─ 60초 이내면 캐시 반환
       └─ 그보다 오래됐으면 GET 공유 → 검증 → 병합 → 저장
```

`articles.ts`는 Zod를 통과한 응답만 캐시에 넣는다. 검색어는 앞뒤 공백을 제거한 키로 구분하고, 같은 키의 진행 중 GET은 하나의 Promise를 공유한다. 빈 목록도 정상 결과로 재사용한다. 갱신이 실패하면 HomePage는 이전 목록과 갱신 실패 안내를 함께 보여 준다.

목록에서 받은 DTO로 상세 캐시도 채운다. 이 경로는 조회한 기사 데이터를 재사용한다. 요약 생성 POST는 기존처럼 실제 상세 화면을 연 때에만 보낸다. 저장된 GPT 본문 요약이 있으면 바로 표시하고 근거 metadata는 GET으로 받는다. graph context와 관련 기사 조회도 별도 요청으로 남는다.

## 가장 늦게 온 응답이 가장 새로운 정보는 아니다

재사용을 붙이자 서로 다른 시점의 데이터가 같은 기사 캐시에 들어올 수 있었다.

```txt
1. 요약이 비어 있는 상세 GET 시작
2. 비동기 요약이 READY가 됨 → 캐시 갱신
3. 1번의 GET이 늦게 완료됨 → 빈 요약 DTO 도착
```

도착 순서대로 응답 전체를 저장하면 3번이 완성된 요약을 지운다. 화면의 요청을 취소하거나 이전 경로의 응답을 무시하는 검사만으로는 공용 캐시의 이 경합을 해결하지 못한다.

`summaries.ts`는 비어 있지 않은 `READY/FULL_TEXT` 결과를 기존 상세 DTO에 반영한다. 이후 기사 GET이나 목록 GET이 들어오면 `mergeReadySummary()`가 새 DTO와 기존 요약을 병합한다. 실제 보호 조건은 다음과 같다.

```ts
cached?.summary &&
cached.summaryScope === 'FULL_TEXT' &&
article.summaryScope !== 'FULL_TEXT' &&
cached.url === article.url
```

조건에 맞으면 summary·whyItMatters와 요약의 scope·provider·status만 보존한다. 제목 같은 다른 필드는 새 응답을 사용한다. 이 조건은 `summaryStatus === 'READY'`를 다시 검사하지 않는다. 기존 전문 요약을 새 응답 전체보다 우선하는 일반적인 버전 관리도 아니다. 같은 URL의 전문 요약이 소개글 범위나 빈 DTO로 되돌아가는 경우를 막는다.

## 큰 목록에서는 병합과 제거의 순서도 중요했다

상세 캐시는 256개인데 새 목록이 301개라면 어떻게 될까. 한 건씩 저장하면서 다음 항목을 병합하면, 먼저 쓴 항목들이 기존 전문 요약을 Map에서 밀어낼 수 있다. 뒤쪽 항목을 병합할 때에는 보존할 요약이 이미 사라진다.

그래서 `rememberArticles()`는 전체 응답을 기존 캐시와 먼저 병합한 뒤, 그 결과 중 첫 256개를 상세 캐시에 기록한다. 반환하는 목록은 병합된 전체 배열이다. 저장 공간을 줄이기 전에 병합에 필요한 이전 정보를 먼저 사용한다.

화면이 어떤 응답을 보여 줄지도 따로 정한다. HomePage는 이전 검색 effect의 응답을 무시한다. ArticleDetailPage는 현재 경로와 기사의 ID를 맞춰 보고, 관련 기사와 graph context에도 소유 기사 ID를 붙여 이전 화면의 보조 정보가 섞이지 않게 한다. 공용 캐시에서 무엇을 보존할지와 현재 화면에서 어떤 응답을 쓸지를 나눠 처리한다.

## 검증

2026-11-03 이번 배치에서는 frontend 전체 70개 테스트와 lint·build가 통과했다. 가짜 HTTP 응답과 화면 fixture의 계약을 확인했으며, 아래의 과거 브라우저 이동 시간을 새로 측정한 것은 아니다.

아래 수치는 **2026-10-30 구현 세션의 기록**이다. 코드·fixture·보존된 관측 파일을 읽고 대조했으며 브라우저 측정은 새로 실행하지 않았다.

| 당시 확인한 항목 | 기록과 해석 범위 |
| --- | --- |
| 같은 공개 브라우저의 상세 이동 | 1,864→80ms |
| 같은 브라우저의 홈 복귀 | 1,811→50ms |
| 수정 후 해당 이동의 요청 | 목록·상세 GET 0, summary metadata·graph context GET 2 |
| frontend 전체 검사 | 10개 파일·63개 테스트, lint 경고 0, build 성공 |
| 비용 상태 | 시험 전후 6회·보수 차감 120,000micros·UNKNOWN 1 유지, 새 유료 호출 0 |

이 이동 시간은 소수 관측이며 사용자 집단의 p50/p95가 아니다. 앞의 API 전송 시간과 브라우저 이동 시간도 측정 대상이 다르므로 같은 값처럼 비교하지 않는다. 원자료와 검증 경과는 [당시 개발 로그](https://github.com/yh4752/sigak/blob/2b80dd22af9afef0c9fcc167a1e65044cb10f392/docs/blog/2026-10-30-dev-log.md)에 남아 있다.

현재 fixture에는 진행 중 GET 공유, 61초 후 갱신, 5분 만료, invalid 응답 제외, 이전 검색 응답 무시, 갱신 실패의 이전 목록 유지가 있다. 늦은 GET과 301개 목록 경합은 [요약 캐시 테스트](https://github.com/yh4752/sigak/blob/2b80dd22af9afef0c9fcc167a1e65044cb10f392/frontend/src/api/summaries.test.ts)에서 응답 순서를 통제한다. 실제 유료 AI를 호출하는 시험은 아니다.

다음은 같은 계약을 좁혀 다시 확인할 때 쓸 명령이다. 이번 배치에서는 이 검사를 포함한 전체 frontend 테스트를 실행했다.

```bash
# frontend/에서 실행: 가짜 HTTP 응답과 화면 fixture 사용
npm test -- articles.test.ts summaries.test.ts HomePage.test.tsx ArticleDetailPage.test.tsx ArticleSummary.test.tsx
npm run lint
npm run build
```

## 남은 대기와 다시 설명할 질문

첫 접속·강제 새로고침·미리보기 만료 뒤에는 네트워크가 필요하다. 탭을 닫으면 캐시도 사라진다. 목록 페이지 구분과 전송량 감소, 장기 메모리 사용, 여러 네트워크 조건의 반복 측정은 별도 과제다. 캐시가 이미 만료됐거나 제거된 뒤에도 요약을 영원히 보존한다고 보장하지 않는다.

코드를 다시 읽을 때는 [캐시 병합과 저장 순서](https://github.com/yh4752/sigak/blob/2b80dd22af9afef0c9fcc167a1e65044cb10f392/frontend/src/api/articleReadCache.ts), [조회 공유와 Zod 경계](https://github.com/yh4752/sigak/blob/2b80dd22af9afef0c9fcc167a1e65044cb10f392/frontend/src/api/articles.ts), [READY 반영](https://github.com/yh4752/sigak/blob/2b80dd22af9afef0c9fcc167a1e65044cb10f392/frontend/src/api/summaries.ts)을 함께 보면 좋다.

- 왜 화면의 오래된 응답을 무시하는 것과 공용 캐시를 병합하는 것이 모두 필요한가?
- 60초 신선도와 5분 미리보기는 각각 어떤 대기를 줄이고 어떤 오래된 정보를 허용하는가?
- 저장 항목을 제한하기 전에 병합해야 하는 이유를 301개 목록으로 설명할 수 있는가?

코드·기록 대조와 원고 작성·문장 검토에는 Codex를 사용했다. 이 글의 성능 수치는 명시한 과거 관측 범위에 한정한다.
