# AI 요약을 첫 클릭까지 미룬 이유와 중복 비용을 다룬 방법

> 기사 수집과 유료 요약을 분리하고, 첫 상세 진입에서 요청한 요약을 DB에 저장해 공유했다. 응답을 확인하지 못한 호출은 재시도하지 않고 비용 추적 대상으로 남겼다.

## 출발점은 모델보다 호출 시점이었다

Sigak은 기술 글을 모아 한국어 요약과 관련 정보를 보여 주는 서비스다. 실제 AI를 연결할 때 쓸 수 있는 예산은 총 5달러였다. 처음에는 새 기사를 수집할 때 요약을 만드는 방식을 검토했다. 하지만 읽히지 않는 기사에도 비용을 쓰는 건 아까웠다. 그래서 상세 화면을 처음 연 기사만 요약하고 결과를 저장하는 방향을 선택했다.

기존 mock 호출을 유료 API로 교체하는 것만으로 끝낼 수는 없었다. 당시 수집 파이프라인은 enrichment를 호출한 다음 저장 단계에서 중복 기사를 검사했다. 그 순서를 유지하면 이미 수집한 글에도 유료 요청을 보낼 수 있었다.

호출 시점을 옮긴 뒤에도 중복 비용 문제는 남았다. 여러 방문자가 같은 기사를 동시에 열 수 있고, AI가 처리한 뒤 응답만 잃을 수도 있다. 브라우저가 떠났다고 서버에서 이미 시작한 작업이 사라지는 것도 아니다.

이 글은 유료 외부 API를 작은 예산으로 운영하면서 요청 중복과 실패를 어떻게 다뤘는지 설명한다. 문서 생성이나 번역처럼 결과를 여러 사용자에게 공유하는 기능에도 같은 문제를 적용해 볼 수 있다.

## 어디까지 구현할지 먼저 정했다

호출 시점을 기준으로 세 가지를 비교했다.

| 방식 | 이점 | 감수할 점 |
| --- | --- | --- |
| 수집할 때 전부 생성 | 첫 방문부터 요약이 준비됨 | 읽히지 않는 기사와 수집 중복에도 비용이 생길 수 있음 |
| 첫 상세 진입 시 생성·공유 | 읽기 흐름에 추가 버튼 없이 필요한 글부터 생성 | 첫 방문자는 기다리고, 실수로 연 글에도 요청이 생김 |
| 요약 버튼을 눌렀을 때 생성·공유 | 요약 의사를 더 분명하게 확인 | 기사마다 클릭을 한 번 더 해야 함 |

두 번째를 선택했다. 더 적게 쓰려면 명시적 버튼도 가능하지만, 이번에는 기사를 열면 요약이 준비되는 흐름을 택했다. 대신 첫 방문의 대기를 화면에서 드러내고, 원문 링크와 기사 정보는 먼저 보여 준다.

Spring Boot는 공개 API와 작업·비용 상태를 관리한다. FastAPI는 Spring에서 받은 입력으로 AI를 호출한다. PostgreSQL을 원본 저장소로 사용하던 구조를 유지했고, 별도 메시지 브로커는 추가하지 않았다. 현재 규모에서는 DB에 작업을 남기고 worker가 가져가는 방식으로 시작했다.

## 조회와 생성을 다른 요청으로 나눴다

수집한 기사는 요약이 없어도 공개하고 검색할 수 있도록 바꿨다. 목록과 검색을 여는 일이 AI 호출로 이어지지 않게 하기 위해서다.

```txt
수집 -> 기사·원문 저장 -> 공개·검색

상세 진입 -> 요약 POST
           -> 본문 준비
           -> 공유 작업 등록
           -> worker가 유료 호출
           -> 결과 저장

이후 방문 -> 저장된 결과 재사용
```

`GET /api/articles/{id}/summary`는 상태를 읽고, `POST /api/articles/{id}/summary`는 요약을 요청한다. 정상 UI에서는 요약이 없는 기사의 상세 화면을 열 때 POST를 보낸다. 이후 처리 중 상태는 GET으로 확인한다. 목록·검색·관련 기사 조회를 위해 미리 읽은 데이터에서는 생성 요청을 하지 않는다.

여기서 ‘첫 클릭’은 화면 동작의 기준이다. 서버가 실제 사람의 관심까지 증명하는 것은 아니다. 자동화된 브라우저가 상세를 열거나 누군가 POST를 직접 호출해도 요청은 생길 수 있다. Origin 검사와 요청 제한을 두었지만 인증이나 사용자별 과금 체계는 없으며, 누적 예산 제한이 별도로 필요했다.

페이지를 떠나면 화면의 상태 확인은 중단한다. 이미 서버에서 전송한 AI 요청까지 취소하는 구조는 아니다. 완료된 결과를 저장해 다음 방문에서 사용한다.

## 본문이 준비되는 것과 AI 요청은 다르다

소개글만 보내면 기사 전체를 요약했다고 보기 어렵다. 현재 구현은 지원하는 기사의 본문을 먼저 확보하고, 요약 요청이 있는 경우에 유료 작업으로 넘긴다.

자동 수집 때 검토된 피드 전문을 저장하거나 본문을 미리 가져와도 `requested_summary=false`라면 AI 작업을 만들지 않는다. 본문 확보에는 서버와 네트워크 자원이 들지만 유료 생성 API는 호출하지 않는다.

상세에서 처음 요청했는데 본문이 없다면 먼저 준비 상태를 반환한다. 본문 저장 후 요청이 있었는지 확인해 요약 작업을 연결한다. 본문을 저장한 직후 프로세스가 종료된 경우에도, 요청된 READY 본문에 작업이 없으면 worker가 다시 연결한다.

본문을 못 받았거나 입력 크기를 넘긴 기사는 유료 호출 전에 중단한다. 긴 전문을 앞부분으로 자르거나 소개글로 대체해 요약하지 않는다. Spring에서는 중첩 JSON 입력에 56KiB, AI 쪽에서는 지침·출력 스키마를 포함한 전체 요청에 64KiB 제한을 둔다. 두 값은 같은 대상을 재는 것이 아니다.

## 동시 요청은 하나의 영속 작업으로 합쳤다

브라우저에서 중복 클릭을 막는 것만으로는 다른 탭과 방문자의 요청을 합칠 수 없다. 서버 프로세스의 메모리만 사용하면 재시작 후 작업 상태도 잃는다.

`SummaryJobStore.request()`는 짧은 DB 트랜잭션 안에서 기사 행을 잠근다. 이미 저장된 유효 요약이나 공유할 작업이 있으면 그대로 반환한다. 새 작업이 필요할 때만 입력을 저장하고 `PENDING`을 만든다.

DB에는 다음 조합의 unique 제약도 둔다.

```sql
unique(article_id, input_hash, prompt_version, model_name)
```

`input_hash`는 본문뿐 아니라 제목·출처·URL·발행일·토픽·입력 범위를 담은 실제 입력 JSON의 SHA-256이다. 같은 기사에서 파생된 작업도 어떤 입력을 사용했는지 남기고, 동일 조합의 중복 행을 막는다.

중복 요청 식별과 기존 결과의 재생성 정책은 별도로 뒀다. 모델이나 지침이 바뀌어도 저장된 유효 전문 요약을 자동 재생성하지 않는다. 현재 구현은 이전 전문 요약 지침의 READY 결과도 재사용한다. 새 버전을 만들지는 별도 운영 판단으로 남겼고, 만든다면 기존 예산을 함께 사용해야 한다.

## 유료 호출 전에 원장과 작업 상태를 함께 바꾼다

작업을 등록했다고 바로 AI를 호출하지 않는다. worker가 DB에서 작업을 확보할 때 비용을 먼저 기록한다.

```txt
짧은 DB 트랜잭션
  1. 예산 행 잠금
  2. PENDING 작업 확보
  3. 누적·일별·횟수 한도 검사
  4. 보수 차감과 DISPATCHED 기록
  5. 커밋

DB 트랜잭션 밖
  6. private FastAPI -> 외부 AI 호출

다시 짧은 DB 트랜잭션
  7. 입력 일치·결과 확인 후 저장
```

예산을 기록하기 전에 유료 요청부터 나가면 원장으로 비용을 통제하기 어렵다. 차감과 작업 상태 변경을 같은 트랜잭션으로 묶고, 커밋이 끝나야 외부 호출로 넘어가도록 했다. 반대로 외부 AI의 응답을 기다리는 동안 DB 잠금을 유지하지는 않는다.

`ArticleSummaryService.runOne()`의 핵심 흐름을 줄이면 다음과 같다. `claim()`과 `complete()` 안의 DB 작업, 그 사이의 네트워크 호출을 나눠 볼 수 있다.

```kotlin
val job = store.claim() ?: return false
try {
    val output = provider.enrich(job.input)
    validate(output, job.input)
    store.complete(job, output)
} catch (exception: Exception) {
    // 실제 코드는 오류 종류에 따라 전체 호출 중단 여부도 결정한다.
    store.fail(job)
}
```

결과를 저장할 때에는 현재 본문으로 만든 입력 hash가 작업의 입력 hash와 같은지도 확인한다. 처리 중 입력이 바뀌었다면 이전 입력의 결과를 current 요약으로 적용하지 않는다. 정상 결과일 때만 기존 enrichment를 이력으로 남기고 새 결과로 전환한다.

## 응답을 잃으면 실패와 비용을 확정하지 않는다

가장 조심한 경우는 다음 순서였다.

```txt
서버가 요청 전송
  -> AI가 처리했을 수 있음
  -> 응답 연결이 끊김
  -> 우리 서버에는 성공 결과가 없음
```

이때 재시도하면 이미 처리된 작업에 비용을 한 번 더 쓸 수 있다. 그래서 전송 뒤 결과를 확정하지 못한 작업은 `UNKNOWN`으로 남기고 보수 차감을 유지한다. 다시 상세를 열어도 자동 재전송하지 않는다. 전송 계층의 자동 retry도 껐다.

주요 상태는 다음처럼 사용한다. DB의 `DISPATCHED`는 공개 응답에서는 `PENDING`으로 표시한다.

| 내부 상태 | 의미 | 이후 처리 |
| --- | --- | --- |
| PENDING | 아직 유료 전송 전인 작업 | 한도가 허용하면 worker가 확보 |
| DISPATCHED | 원장을 기록하고 전송 단계에 진입 | 결과를 기다림 |
| READY | 결과 검증·저장 완료 | 방문자에게 공유 |
| UNKNOWN | 전송 후 결과나 사용량을 확정하지 못함 | 차감 유지, 자동 재호출 없음 |
| FAILED | 예를 들어 완료 시 입력이 달라 결과를 적용하지 못함 | 실패 이유 보존 |
| BUDGET_EXHAUSTED | 누적 예산·시도 횟수 한도로 전송 불가 | 추가 유료 호출 안 함 |

재시작도 이 불확실성을 없애 주지 않는다. worker는 5분 넘게 남은 `DISPATCHED`를 `UNKNOWN`으로 격리한다. 실제 전송 직전에 프로세스가 멈췄다면 돈을 쓰지 않았는데도 앱의 보수 차감만 남을 수 있다. 처음 구현에서는 그 손실을 감수하고 자동 재호출을 피했다.

DB와 외부 AI 호출 전체를 하나의 원자적 트랜잭션으로 만든 것은 아니다. ‘외부 처리는 정확히 한 번’이라고 보장하는 대신, 확인되지 않은 호출을 새 작업처럼 되풀이하지 않는 쪽을 택했다. 자동 복구율을 낮춘 선택이므로 UNKNOWN이 많아지면 운영자가 원인을 확인해야 한다.

## 5달러를 실제 청구액처럼 계산하지 않았다

앱은 총 5달러 예산에서 여유를 남기고 누적 4달러를 한도로 사용한다. 매번 달라지는 token 추정액을 곧바로 사용 가능 예산으로 돌려주지 않고, 전송 예약 1회마다 0.02달러를 보수적으로 차감한다.

| 항목 | 현재 정책 |
| --- | --- |
| 앱 누적 한도 | 4달러 |
| 전송 예약 1회당 앱 차감 | 0.02달러 |
| 누적 시도 상한 | 200회 |
| 일별 시도 상한 | 20회 |
| 성공·UNKNOWN 후 차감 환급 | 하지 않음 |
| 재시작·배포 후 원장 | 유지 |

0.02달러는 모델의 실제 단가가 아니라 앱에서 정한 보수적인 값이다. 확인된 token 사용량의 추정 비용은 별도 필드로 기록한다. UNKNOWN의 실제 비용은 모르는 채로 남긴다. 계정의 다른 API 사용이나 청구 내역까지 이 원장이 관리하지는 않는다.

초기 pilot 모드는 최대 10회로 제한했고 운영 모드로 전환한 뒤에도 누적 한도는 유지했다. 일별 한도에 도달한 PENDING은 다음 집계일에 다시 처리할 수 있지만 누적 한도는 날짜가 바뀌어도 초기화하지 않는다. 현재 코드의 일별 집계는 UTC 날짜 기준이다. 재시작으로 사용 한도가 생기지 않도록 원장은 PostgreSQL에 둔다.

실제 사용량의 추정액이 작아도 앱의 시도 상한에 도달하면 멈춘다. 실제 비용이 차감액보다 작아도 시도 횟수를 돌려주지 않기 때문이다. 다만 작은 예산으로 처음 운영하는 단계에서는 사용량의 불확실성을 줄이는 쪽을 우선했다. 모델·요금·입력 제한이 바뀌면 차감 가정도 다시 검토해야 한다.

## 검증: 동시 최초 요청과 완료 후 재요청을 구분했다

2026-11-02 글을 작성하면서 요약 관련 백엔드 테스트 24개와 AI fixture 테스트 62개를 다시 실행해 통과를 확인했다. 백엔드는 운영 DB와 분리된 Testcontainers PostgreSQL을 사용하고 AI provider를 mock으로 교체한다. AI 테스트도 가짜 응답을 사용한다. 실제 유료 요약은 새로 만들지 않았다.

```bash
# 저장소 루트: 요약 기능의 DB·HTTP·worker 테스트
./backend/gradlew -p backend test --tests 'com.sigak.article.summary.*'

# ai/ 디렉터리: 가짜 응답과 로컬 서버를 사용하는 테스트
```

이 검증은 해당 기능의 focused 검사다. 앱 전체 테스트와 운영 요약 품질을 다시 검증한 결과로 해석하지 않았다.

테스트에서 확인하는 계약은 아래와 같다.

| 상황 | 기대하는 동작 |
| --- | --- |
| 최초 요청 12개가 동시에 진입 | PENDING 작업 1개, 전송 전 차감 0 |
| 성공한 작업을 다시 요청 | 같은 요약 반환, provider 추가 호출 없음 |
| 다음 차감으로 누적 한도 초과 | 전송 전에 거부 |
| 전송 후 응답 유실 | UNKNOWN과 차감 유지, 재요청해도 추가 전송 없음 |
| worker가 처리하던 작업이 오래 남음 | UNKNOWN으로 격리, 재시도·환급 없음 |
| 본문이 없거나 너무 김 | 본문 준비 또는 거부, 아직 유료 호출 없음 |
| 전문 요약 지침 변경 | 기존 READY 재사용, 이전 UNKNOWN 자동 재호출 없음 |

구현 당시 실제 서비스에서 관측한 결과도 남아 있다. 아래는 **2026-10-30의 소수 관측**이며 이번 글을 쓰면서 다시 측정한 값은 아니다.

| 실제 관측 | 결과 | 해석 범위 |
| --- | --- | --- |
| Google 기사 본문 2,293자 첫 요약 | READY/FULL_TEXT, 첫 결과 확인 11.423초 | 첫 방문은 본문 준비와 생성을 기다림 |
| 저장된 Google 요약 재요청 | 0.059초 | 저장 결과를 반환한 한 번의 관측 |
| 완료된 요약을 6건 동시 재요청 | 전체 0.288초, 추가 호출 0회 | 완료 후 재사용 확인이며 최초 생성 경합 시험은 아님 |
| GitHub 기사 요약의 private AI 응답 502 | UNKNOWN 유지 | 실제 AI 처리·청구 여부를 확정하지 못함 |
| OpenAI 원문 접근 403 | 본문 단계 중단, 추가 유료 호출 0회 | 본문 실패를 유료 오류와 구분 |
| 그 시점 재시작 후 원장 | 6회·보수 차감 0.12달러·UNKNOWN 1건 유지 | 당시 작업·비용 상태 보존 확인 |

전체 기사에 적용되는 속도 보장이나 요약 품질 점수는 아니다. 입력 길이와 측정 조건이 달라 이전 소개글 요약과의 속도 개선율도 계산하지 않았다. 현재 사용량을 뜻하는 표도 아니므로 이후 호출 누적과 구분해야 한다.

## 남은 한계와 다음 판단

첫 방문 대기를 없애지는 못했다. 더 빨리 보이게 하려고 모든 기사를 미리 요약하면 처음 피하려던 비용 문제가 돌아온다. 관심 신호를 모아 선별적으로 미리 만들거나 요약 버튼으로 바꾸는 선택은 실제 읽기 패턴을 보고 결정할 일이다.

현재는 저장된 결과를 모든 방문자에게 공유한다. 개인별 관점의 요약, 작업 취소, UNKNOWN의 운영자 확인 화면과 자동 재처리는 구현하지 않았다. 별도 브로커와 여러 인스턴스 운영도 이 글에서 검증한 범위가 아니다.

근거 인용이 본문에 있는지 검사한다고 문맥과 측정 조건까지 항상 정확해지는 것도 아니다. 이번 글은 요청·상태·비용을 다루며, 요약의 의미 품질은 별도 평가가 필요하다.
