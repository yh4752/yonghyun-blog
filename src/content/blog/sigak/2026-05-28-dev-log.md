# 2026-05-28 개발 로그: DB 구조를 시각화 가능한 개발 자산으로 만들기

## 요약

오늘은 Sigak의 현재 DB 구조를 다시 확인하고, PostgreSQL schema를 시각적으로 볼 수 있는 도구를 로컬 개발 흐름에 추가했다. 단순히 ERD 이미지를 한 번 그리는 것이 아니라, 마이그레이션이 바뀔 때마다 재생성할 수 있는 SchemaSpy 기반 workflow를 Docker Compose에 붙였다.

핵심 결정은 SchemaSpy를 상시 실행 서비스로 두지 않고, `tools` profile 뒤에 둔 것이다. 덕분에 평소 개발용 Compose 실행은 그대로 가볍게 유지하면서, 필요할 때만 HTML ERD를 생성할 수 있게 됐다.

```txt
PostgreSQL schema
-> SchemaSpy one-off container
-> outputs/db-schema/index.html
```

또한 Docker에 익숙하지 않은 상태에서도 실수 없이 사용할 수 있도록 인프라 README에 Docker 명령어 치트시트를 추가했다.

## 오늘 완료한 일

### 1. 현재 DB 구조 확인

먼저 Flyway migration과 JPA entity를 기준으로 Sigak의 DB 구조를 다시 확인했다.

현재 핵심 테이블은 다음과 같다.

- `news_sources`
- `articles`
- `article_raw_contents`
- `article_enrichments`
- `article_topics`
- `article_relations`

구조상 `articles`가 중심 노드 역할을 하고, `article_relations`가 기사 간 edge 역할을 한다. 이 덕분에 현재 PostgreSQL schema는 단순 article list 저장소를 넘어, Neo4j graph projection으로 확장하기 좋은 형태를 이미 갖고 있다.

### 2. SchemaSpy 기반 DB schema 시각화 추가

`infra/docker-compose.yml`에 `db-schema` 서비스를 추가했다.

```yaml
db-schema:
  image: schemaspy/schemaspy:6.2.4
  platform: linux/amd64
  profiles:
    - tools
```

중요한 점은 `profiles: ["tools"]`다. 이 설정 때문에 다음 기본 실행에는 SchemaSpy가 포함되지 않는다.

```bash
docker compose -f infra/docker-compose.yml up -d
```

DB 문서가 필요할 때만 아래 명령으로 실행한다.

```bash
docker compose -f infra/docker-compose.yml --profile tools run --rm db-schema
```

SchemaSpy는 PostgreSQL에 접속해 현재 schema를 읽고, HTML 문서를 생성한다. 결과물은 다음 위치에 생성된다.

```txt
outputs/db-schema/index.html
```

`outputs/`는 로컬 산출물이므로 `.gitignore`에 추가했다. ERD 결과물 자체보다 중요한 것은, 누구든 같은 명령으로 최신 DB 문서를 다시 만들 수 있다는 점이다.

### 3. Docker 명령어 치트시트 작성

Docker에 익숙하지 않은 상태에서도 프로젝트를 안정적으로 운영할 수 있도록 `infra/README.ko.md`와 `infra/README.md`에 자주 쓰는 명령을 표로 정리했다.

정리한 명령은 다음 범주다.

- 전체 인프라 켜기
- PostgreSQL만 켜기
- 컨테이너 상태 확인
- 서비스 로그 확인
- 특정 서비스 재시작
- PostgreSQL만 중지
- 전체 인프라 중지
- DB ERD 생성
- 로컬 volume까지 포함한 전체 초기화

특히 `down`과 `down -v`를 구분해서 적었다. `down`은 컨테이너와 네트워크를 정리하지만 volume 데이터는 유지한다. 반면 `down -v`는 PostgreSQL, Elasticsearch, Qdrant, Neo4j의 로컬 데이터를 함께 삭제한다. 이 차이는 Docker 초반에 가장 실수하기 쉬운 부분이라 문서에서 명확히 강조했다.

## 설계 고민

### DB 시각화 도구를 프로젝트 안에 둘 것인가?

DB 구조를 보는 방법은 여러 가지가 있다. DBeaver, IntelliJ Database 탭, DataGrip 같은 로컬 GUI를 쓰면 실시간 탐색이 편하다. 하지만 이런 도구는 개인 개발 환경에 의존한다.

Sigak은 포트폴리오 프로젝트이므로 "내 컴퓨터에서는 볼 수 있다"보다 "저장소를 받은 사람이 같은 방식으로 재현할 수 있다"가 더 중요하다. 그래서 GUI 도구만 추천하는 대신, 프로젝트 안에 SchemaSpy 실행 방법을 남기는 쪽을 선택했다.

### 왜 상시 컨테이너가 아니라 일회성 도구인가?

SchemaSpy는 애플리케이션이 런타임에 의존하는 서비스가 아니다. PostgreSQL, Elasticsearch, Qdrant, Neo4j처럼 계속 떠 있어야 하는 저장소와 다르게, DB 문서를 생성하는 순간에만 필요하다.

따라서 기본 Compose 실행에 포함하면 매일 개발할 때 불필요한 컨테이너가 늘어난다. 반대로 `tools` profile과 `run --rm`을 사용하면 필요한 순간에만 컨테이너가 뜨고, 끝나면 자동으로 삭제된다.

이 선택은 작은 결정이지만 로컬 개발 경험에는 중요하다. 개발 환경은 기능을 많이 넣는 것보다, 매일 켜고 끄는 흐름이 예측 가능해야 한다.

## 트레이드오프

### SchemaSpy vs DBeaver

SchemaSpy는 HTML 문서와 ERD를 생성하는 데 강하다. 커밋하지 않더라도 산출물의 생성 절차를 프로젝트에 남길 수 있고, 변경된 migration을 기준으로 다시 만들 수 있다.

반면 실시간 데이터 조회나 임시 SQL 실행은 DBeaver 같은 GUI가 훨씬 편하다. 그래서 오늘의 선택은 DBeaver를 대체하는 결정이 아니다. 역할을 나누는 결정이다.

```txt
DBeaver / IntelliJ Database: 개발 중 실시간 DB 탐색
SchemaSpy: 프로젝트에 남길 수 있는 재현 가능한 DB 문서 생성
```

### 생성물을 커밋하지 않는 이유

`outputs/db-schema/index.html`은 유용하지만, 생성된 정적 파일이다. 이런 산출물을 매번 커밋하면 실제 schema 변경보다 HTML, JS, 이미지 diff가 더 크게 보일 수 있다.

그래서 `outputs/`를 ignore하고, 대신 생성 명령을 README에 남겼다. 소스 저장소에는 "어떻게 만들 수 있는가"를 남기고, 생성물은 로컬에서 필요할 때 만드는 방식이다.

## 기술 포인트

### Docker Compose profile

Compose profile은 선택적 서비스를 정의할 때 유용하다.

```yaml
profiles:
  - tools
```

이렇게 두면 기본 실행에서는 제외되고, 아래처럼 profile을 명시했을 때만 포함된다.

```bash
docker compose -f infra/docker-compose.yml --profile tools run --rm db-schema
```

Sigak에서는 앞으로도 "항상 필요한 서비스"와 "개발 보조 도구"를 구분할 때 같은 방식을 사용할 수 있다.

### `run --rm`의 의미

`docker compose run --rm db-schema`는 `db-schema` 서비스를 일회성 작업처럼 실행한다. `--rm`은 작업이 끝난 뒤 컨테이너를 자동 삭제한다는 뜻이다.

이 흐름 덕분에 SchemaSpy는 별도로 끌 필요가 없다. PostgreSQL은 계속 켜 둔 채로 DB 문서만 다시 생성할 수 있다.

### Apple Silicon platform 명시

현재 SchemaSpy 이미지 실행 시 Apple Silicon 환경에서 platform 경고가 나올 수 있어 `platform: linux/amd64`를 명시했다.

이는 기능 동작 자체보다 개발자 경험에 가까운 설정이다. 경고를 줄이고, 어떤 platform으로 실행되는지 Compose 파일에 명시적으로 남긴다.

## 공학적 주제화

오늘 작업은 "DB 문서화"라기보다 "개발 환경의 관측 가능성"에 가깝다.

애플리케이션이 커질수록 DB 구조는 코드만큼 중요한 설계 문서가 된다. 특히 Sigak처럼 PostgreSQL을 source of truth로 두고 Elasticsearch, Qdrant, Neo4j를 projection store로 사용할 계획이라면, 원본 schema가 어떻게 생겼는지 빠르게 확인할 수 있어야 한다.

ERD를 자동 생성할 수 있으면 다음 효과가 있다.

- 새로운 기능을 만들기 전에 관계 구조를 빠르게 파악할 수 있다.
- graph projection을 설계할 때 어떤 테이블이 node/edge 후보인지 확인할 수 있다.
- migration이 늘어날수록 문서와 실제 DB 사이의 차이를 줄일 수 있다.
- 포트폴리오 독자에게 데이터 모델링 의도를 더 쉽게 보여줄 수 있다.

즉, 오늘의 작업은 기능 개발 속도를 높이는 보조 장치이면서, 프로젝트 설명력을 높이는 문서화 기반이다.

## 검증

다음 명령으로 Compose 설정과 SchemaSpy 실행을 검증했다.

```bash
docker compose -f infra/docker-compose.yml --profile tools config
docker compose -f infra/docker-compose.yml --profile tools run --rm db-schema
test -f outputs/db-schema/index.html
git diff --check
```

SchemaSpy 실행 결과 `outputs/db-schema/index.html`이 생성됐다. 실행 중 PostgreSQL 16 catalog 조회와 Graphviz label 관련 경고가 일부 출력됐지만, 명령은 exit code `0`으로 종료됐고 HTML 산출물도 정상 생성됐다. 이 경고는 README에도 주의사항으로 남겼다.

## 다음 단계

다음 개발 단계는 DB 문서화가 아니라 실제 검색 사용자 흐름으로 돌아가는 것이다.

우선순위는 다음과 같다.

1. `/api/articles?query=...`가 Elasticsearch keyword search를 사용하도록 내부 구현을 연결한다.
2. 검색 결과 수, 검색 시간, fallback 여부 같은 metric을 응답 또는 로그에서 확인할 수 있게 한다.
3. Qdrant vector projection과 검색 endpoint를 추가한다.
4. keyword search와 vector search를 결합하는 hybrid search 실험으로 확장한다.

오늘 만든 DB schema 시각화는 이 다음 작업들에서 데이터 관계를 확인하는 기준점 역할을 할 것이다.
