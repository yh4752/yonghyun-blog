# 2026-05-05 개발 로그: 제품 계약과 Mock MVP를 먼저 고정하기

## 요약

오늘은 Sigak의 첫 MVP foundation을 만들었다. 작업의 핵심은 많은 기능을 붙이는 것이 아니라, 앞으로 검색, AI 요약, Graph RAG로 확장될 제품의 기본 계약을 먼저 고정하는 것이었다.

초기 Sigak은 "AI-powered news insight platform"이라는 넓은 아이디어에서 출발했다. 이를 AI, 소프트웨어 개발, 컴퓨터공학 분야의 중요한 기술 뉴스를 선별하고, 요약과 "왜 중요한가"를 함께 설명하는 서비스로 좁혔다. 이 정의를 바탕으로 Spring Boot, FastAPI, React, Docker Compose, docs를 갖는 monorepo 구조를 만들고, mock data 기반의 article list/search/detail 흐름을 구현했다.

이날의 중요한 판단은 DB, Elasticsearch, Qdrant를 바로 붙이지 않은 것이다. 대신 public API 응답 모양과 프론트엔드 사용자 흐름을 먼저 검증했다. 데이터 저장소와 검색 엔진은 내부 구현이 바뀌어도 public contract가 흔들리지 않아야 하기 때문이다.

## 오늘 완료한 일

### 1. 제품 방향과 MVP 범위 정리

Sigak의 초기 타깃을 AI, 개발, CS 분야의 중요한 기술 변화를 따라가고 싶은 사용자로 정의했다. 수집 대상도 무작정 넓히지 않고 다음 범위로 제한했다.

- 주요 AI/CS 연구 발표
- 심각한 보안 이슈
- 공식 기업/기관 발표
- 중요한 오픈소스 릴리즈
- 개발자 생태계에 영향을 줄 수 있는 기술 변화

반대로 일반 개인 기술 블로그, 튜토리얼, 홍보성 콘텐츠, 낮은 영향도의 패치 릴리즈는 초기 MVP에서 제외했다. MVP에서는 많은 source를 수집하는 것보다, 신뢰할 수 있는 source와 일관된 기준을 먼저 세우는 편이 더 중요하다고 봤다.

### 2. Graph RAG 방향을 MVP 범위 안으로 낮추기

Graph RAG는 장기적인 차별점으로 남기되, 처음부터 full graph explorer를 만들지는 않기로 했다. 그래서 article 응답에 다음처럼 나중에 graph-aware insight로 확장할 수 있는 필드를 포함했다.

- `topics`
- `primaryCategory`
- `relatedArticleIds`
- `whyItMatters`
- `importanceScore`

이 결정으로 초기 MVP는 뉴스 목록, 검색, 상세, 관련 article 힌트에 집중할 수 있었다. 그래프 UI와 고급 Graph RAG는 product-market fit이나 데이터 흐름이 더 안정화된 뒤 붙이는 편이 낫다.

### 3. Monorepo와 문서 구조 생성

초기 구조는 다음처럼 나눴다.

```txt
sigak/
├── backend/
├── frontend/
├── ai/
├── infra/
└── docs/
```

역할도 명확히 분리했다.

- `backend`: Spring Boot 메인 API 서버
- `frontend`: React + TypeScript + Vite UI
- `ai`: FastAPI 기반 AI/RAG 기능 영역
- `infra`: Docker Compose와 로컬 개발 인프라
- `docs`: 제품, API, 아키텍처, 의사결정 문서

Spring Boot를 main backend로 두고, FastAPI는 AI/RAG 전용 서버로 분리했다. 프론트엔드는 기본적으로 Spring Boot만 호출한다. 이 구조는 프론트엔드가 여러 backend service를 직접 알지 않아도 되게 만들고, AI 관련 변경이 main product API에 과하게 번지지 않게 한다.

### 4. Kotlin Spring Boot Article API 구현

백엔드는 Kotlin Spring Boot로 세팅하고, mock article data 기반의 public API를 구현했다.

```http
GET /api/articles
GET /api/articles?query={query}
GET /api/articles/{id}
```

응답에는 단순 title/summary만 두지 않고, product direction이 드러나는 필드를 포함했다.

- `eventType`
- `primaryCategory`
- `topics`
- `summary`
- `whyItMatters`
- `importanceScore`
- `relatedArticleIds`

이 응답 모양은 이후 PostgreSQL, Elasticsearch, Qdrant, Neo4j를 붙여도 유지해야 할 public contract가 된다.

### 5. 첫 keyword search API 구현

첫 검색은 in-memory keyword filter로 구현했다.

```http
GET /api/articles?query=rag
```

검색 대상은 다음으로 제한했다.

- `title`
- `summary`
- `primaryCategory`
- `topics`

앞뒤 공백과 대소문자는 무시했다. 이 단계의 목적은 검색 엔진 성능이 아니라 검색 API의 사용자 경험과 응답 계약을 검증하는 것이었다.

### 6. Swagger/OpenAPI 추가

`springdoc-openapi`를 추가해 실행 가능한 API 문서를 제공했다.

```txt
http://localhost:8080/swagger-ui/index.html
http://localhost:8080/v3/api-docs
```

Spring REST Docs도 고려했지만 초기 MVP에는 도입 비용이 더 컸다. 대신 Swagger/OpenAPI는 실행 가능한 API 문서로, `docs/API_SPEC.md`는 사람이 읽는 설계 문서로 역할을 나눴다.

### 7. React + TypeScript + Vite 프론트엔드 구현

프론트엔드는 Vite 기반으로 구성했다. 첫 화면은 검색 중심의 뉴스 경험으로 만들었다.

- 중앙 검색바
- Today's Important News
- Popular News
- 기사 카드
- article detail route

API 호출은 `fetch`를 컴포넌트에 직접 흩뿌리지 않고 `src/api/` 아래에 모았다. HTTP 요청은 Axios로 통일했고, 응답 검증에는 Zod를 사용했다.

```txt
frontend/src/api/httpClient.ts
frontend/src/api/articles.ts
```

Zod를 둔 이유는 TypeScript 타입이 런타임 응답을 보장하지 않기 때문이다. 백엔드 응답이 바뀌었을 때 화면 깊숙한 곳에서 깨지는 것보다 API client boundary에서 먼저 실패하는 편이 디버깅과 안정성에 더 좋다.

### 8. React Router와 article detail 구현

`react-router-dom`을 추가하고 다음 route를 만들었다.

```txt
/              -> HomePage
/articles/:id  -> ArticleDetailPage
```

Detail page에서는 category, event type, title, source, published date, summary, why-it-matters, topics, related article 목록을 보여준다. Related article은 `relatedArticleIds`를 기반으로 가져온다.

### 9. 프론트엔드 시각 언어와 상태 처리 정리

UI는 전문적인 기술 뉴스 서비스 느낌을 주기 위해 serif headline, restrained color, article 중심 layout을 사용했다. `importanceScore`는 UI에 숫자로 노출하지 않고 Popular News ranking에만 내부적으로 사용했다.

상태 처리도 추가했다.

- loading state
- empty state
- error state
- retry action
- detail 실패 시 back link

정상 데이터가 있을 때만 동작하는 MVP는 데모에서는 좋아 보일 수 있지만, 실제 사용 흐름에서는 쉽게 깨진다. 그래서 복잡한 기능보다 기본 상태 처리를 먼저 보강했다.

## 설계 고민

### API contract를 먼저 고정한 이유

초기 단계에서 DB와 검색 엔진을 먼저 붙이면 기술적으로는 더 완성되어 보일 수 있다. 하지만 product shape가 불안정하면 저장소 구조도 계속 흔들린다.

그래서 먼저 public API contract를 고정했다. `/api/articles`와 `/api/articles/{id}`가 어떤 응답을 반환해야 하는지 정해 두면, 이후 내부 구현을 mock에서 PostgreSQL, Elasticsearch, hybrid search로 바꿔도 프론트엔드와 문서의 기준은 유지할 수 있다.

### Frontend가 Spring Boot만 알게 한 이유

FastAPI AI server가 존재하더라도 프론트엔드가 직접 FastAPI를 호출하지 않게 했다. 사용자-facing API boundary는 Spring Boot가 담당하고, Spring Boot가 필요한 경우 AI server를 호출하는 구조가 더 단순하다.

이렇게 하면 인증, CORS, API versioning, error handling을 main backend에서 통제할 수 있다. 포트폴리오 프로젝트라도 초기에 boundary를 잘 나눠 두면 이후 기능 추가가 덜 흔들린다.

### importanceScore를 숨긴 이유

`importanceScore`는 정렬과 큐레이션을 위한 내부 신호다. 하지만 seed data가 수동 curated data인 상태에서 88/100 같은 숫자를 직접 보여주면 오히려 신뢰를 해칠 수 있다.

그래서 사용자가 보는 중요도 설명은 `whyItMatters`가 담당하고, 점수는 Popular News ranking에만 사용했다. 데이터 품질이 더 좋아지고 평가 기준이 명확해지면 qualitative label이나 score display를 다시 검토할 수 있다.

## 트레이드오프

### Mock data를 먼저 사용한 선택

Mock data의 장점은 빠른 검증이다. API 응답, 검색 UI, detail route, related article 흐름을 DB 없이 빠르게 확인할 수 있었다.

대신 한계도 명확하다. 수집, enrichment, 검색 인덱스, Graph RAG는 결국 원본 article과 AI output을 저장해야 의미가 있다. 그래서 mock은 최종 구조가 아니라 public contract를 검증하기 위한 첫 단계로 사용했다.

### Elasticsearch와 Qdrant를 미룬 선택

검색과 RAG를 생각하면 Elasticsearch와 Qdrant를 바로 붙이고 싶어진다. 하지만 초기에 붙이면 API contract, UI, 데이터 모델, 인프라 문제가 동시에 발생한다.

오늘은 in-memory search로 충분하다고 봤다. 검색 엔진 도입은 public API와 article model이 안정화된 뒤 하는 편이 더 안전하다.

### Swagger를 선택하고 Spring REST Docs를 미룬 선택

Swagger/OpenAPI는 빠르게 실행 가능한 API 문서를 제공한다. Spring REST Docs는 테스트 기반 문서화라는 장점이 있지만 초기 설정과 유지 비용이 있다.

MVP 단계에서는 Swagger로 개발 피드백을 빠르게 얻고, 사람이 읽는 계약은 `docs/API_SPEC.md`에 남기는 조합이 더 적절하다고 판단했다.

## 기술 포인트

### API client boundary에서 Zod 검증

프론트엔드에서 Zod를 사용한 것은 작은 프로젝트치고는 약간의 추가 비용이 있다. 하지만 backend와 frontend가 동시에 바뀌는 MVP에서는 런타임 응답 검증이 꽤 큰 안전장치가 된다.

API 응답이 깨졌을 때 화면 컴포넌트가 조용히 잘못된 값을 렌더링하는 것보다, client boundary에서 명시적으로 실패하는 편이 좋다.

### Thin controller와 service boundary

백엔드는 controller가 요청을 받고 service가 business rule을 담당하는 방향으로 시작했다. 아직 mock 단계라 로직이 작지만, 이 구조는 이후 DB repository, search service, AI client가 추가될 때 자연스럽게 확장된다.

### CSS token 기반 디자인

CSS Custom Properties로 색상과 타이포그래피 기준을 한 곳에 모았다. 컴포넌트마다 색상을 임의로 쓰는 것보다, 나중에 전체 디자인 언어를 조정하기 쉽다.

## 공학적 주제화

### MVP는 기술 스택 목록이 아니라 계약 검증이다

오늘 작업은 많은 인프라를 붙이지 않았지만 중요한 의미가 있었다. 사용자가 보는 API와 화면 흐름을 먼저 고정했기 때문이다.

MVP에서 가장 먼저 확인해야 하는 것은 "이 기술을 썼다"가 아니라 "이 제품 경험이 어떤 계약으로 유지되는가"다. DB, 검색 엔진, AI 모델은 그 계약을 구현하는 내부 수단이다.

### 작은 상태 처리가 제품 신뢰도를 만든다

Loading, empty, error, retry는 화려한 기능은 아니다. 하지만 실제 서비스에서는 이런 상태가 사용자 신뢰를 만든다. 포트폴리오에서도 정상 케이스만 보여주는 것보다 실패와 회복 흐름을 다루는 편이 더 좋은 엔지니어링 습관을 보여준다.
