# 2026-05-30 개발 로그: Public Hybrid Search를 실제 API 흐름에 연결하기

## 요약

오늘은 Sigak의 공개 article search를 keyword-only 흐름에서 hybrid search 흐름으로 확장했다. `/api/articles?query=...`의 응답 형태는 그대로 유지하면서, 내부적으로는 Elasticsearch keyword 후보와 Qdrant vector 후보를 함께 사용하고 reciprocal rank fusion(RRF)으로 순위를 합치도록 바꿨다.

핵심은 검색 저장소를 source of truth로 만들지 않는 것이다. Elasticsearch와 Qdrant는 빠른 후보 생성용 projection store로 두고, 최종 article response는 항상 PostgreSQL에서 다시 읽는다.

```txt
query
-> Elasticsearch keyword candidates
-> Qdrant vector candidates
-> RRF fusion
-> PostgreSQL article reload
-> List<ArticleResponse>
```

5월 31일 푸시 전에는 Docker Compose 기반 smoke test를 추가로 실행해 `HYBRID`, `KEYWORD_ONLY`, `VECTOR_ONLY`, `POSTGRES_FALLBACK` mode가 실제 local infra에서 모두 관측되는지 확인했다.

## 오늘 완료한 일

### 1. Hybrid search 설정과 후보 모델 추가

`sigak.search.mode`와 `sigak.search.hybrid.*` 설정을 추가했다.

초기 기본값은 다음 방향으로 잡았다.

- mode: `hybrid`
- RRF k: `60`
- keyword weight: `1.0`
- vector weight: `1.0`
- keyword candidate limit: `20`
- vector candidate limit: `20`
- result limit: `20`

이 값들은 튜닝 결과가 아니라 baseline이다. 지금 단계에서 중요한 것은 "최적값"을 찾는 것이 아니라, keyword/vector/hybrid를 비교하고 나중에 조정할 수 있는 설정 경계를 만드는 것이다.

### 2. Reciprocal Rank Fusion 구현

RRF는 서로 다른 검색 시스템의 점수를 직접 비교하지 않고 rank 기반으로 결과를 합칠 수 있다.

```txt
score = weight / (rrfK + rank)
```

Elasticsearch score와 Qdrant similarity score는 의미와 분포가 다르다. 그래서 MVP 첫 hybrid baseline에서는 score normalization을 직접 설계하기보다, rank 기반 fusion을 선택했다.

tie-break는 다음 순서로 정했다.

1. fused score가 높은 후보
2. 가장 좋은 개별 rank가 높은 후보
3. article ID가 낮은 후보

이 규칙은 완벽한 검색 품질 전략이 아니라 deterministic baseline이다. 같은 입력이면 같은 결과를 내야 테스트와 smoke check가 안정적으로 유지된다.

### 3. Vector candidate boundary 분리

기존 내부 vector search service는 article response까지 조립하는 diagnostics endpoint 역할이었다. 이 서비스를 public search에서 직접 호출하면 다음 순환 의존성이 생길 수 있었다.

```txt
ArticleService
-> ArticleVectorSearchService
-> ArticleService
```

그래서 더 낮은 수준의 `ArticleVectorCandidateSearchService`를 새로 만들었다. 이 서비스는 query embedding과 Qdrant search까지만 담당하고, article response reload는 하지 않는다.

```txt
ArticleService
-> ArticlePublicSearchService
-> ArticleVectorCandidateSearchService
```

이렇게 하면서 내부 diagnostics endpoint인 `ArticleVectorSearchService`도 같은 candidate boundary를 재사용하도록 정리했다.

### 4. Public search orchestrator 추가

`ArticlePublicSearchService`는 public query search의 orchestration을 담당한다.

동작 mode는 다음 네 가지다.

| Mode | 조건 | 동작 |
| --- | --- | --- |
| `HYBRID` | keyword/vector 모두 성공 | RRF 결과 사용 |
| `KEYWORD_ONLY` | vector 실패, keyword 성공 | keyword 후보만 사용 |
| `VECTOR_ONLY` | keyword 실패, vector 성공 | vector 후보만 사용 |
| `POSTGRES_FALLBACK` | 둘 다 실패 | PostgreSQL field filtering 사용 |

성공했지만 후보가 빈 경우는 실패로 보지 않는다. 빈 검색 결과와 검색 인프라 장애는 다른 상태이기 때문이다.

또한 degraded mode에서도 `resultLimit`를 적용하도록 보완했다. Hybrid일 때만 limit가 걸리고 keyword-only/vector-only에서는 더 많은 결과가 나오는 것은 public API 관점에서 일관성이 떨어진다.

### 5. Mode-aware search metrics 확장

기존 metrics는 `fallback: Boolean`과 `elapsedMs` 중심이었다. Hybrid search에서는 이것만으로는 어떤 path가 사용됐는지 알 수 없다.

그래서 internal metrics를 다음 정보로 확장했다.

- search mode
- keyword/vector/fused candidate count
- stale candidate count
- keyword/vector failure flag
- bounded fallback reason code
- keyword elapsed time
- embedding elapsed time
- vector elapsed time
- fusion elapsed time
- article reload elapsed time
- total elapsed time

중요한 점은 raw query text를 저장하지 않는 것이다. 검색어 자체는 metrics에 남기지 않고 `queryLength`만 기록한다. fallback reason도 외부 exception message를 그대로 저장하지 않고 `KEYWORD_SEARCH_FAILED`, `QDRANT_SEARCH_FAILED` 같은 제한된 reason code로 남기도록 보완했다.

## 설계 고민

### 왜 score를 public API에 노출하지 않았는가?

Hybrid search를 붙이면 score를 응답에 넣고 싶어진다. 하지만 public API에 score를 노출하면 검색 알고리즘과 응답 계약이 강하게 묶인다.

현재 Sigak의 public article API는 article 목록을 반환한다. 사용자는 검색 결과를 필요로 하지, RRF score나 Qdrant similarity score를 직접 필요로 하지는 않는다. 점수는 튜닝 과정에서 내부적으로 관찰할 수 있으면 충분하다.

그래서 public response shape는 유지하고, 성능과 fallback 정보는 internal metrics endpoint로 분리했다.

### 왜 PostgreSQL reload를 유지했는가?

Elasticsearch와 Qdrant에는 article ID와 검색용 projection data가 들어간다. 하지만 최종 응답은 PostgreSQL에서 다시 읽는다.

이 방식은 한 단계 더 느릴 수 있다. 대신 다음 장점이 있다.

- 검색 projection이 stale해도 최종 API-ready article만 반환한다.
- article response schema는 PostgreSQL/JPA 모델 기준으로 안정적으로 유지된다.
- projection store를 지우고 다시 만들어도 public API의 source of truth가 흔들리지 않는다.

실제로 stale candidate ID가 들어와도 PostgreSQL reload 단계에서 제외하고, `staleCandidateCount`로 관측할 수 있게 했다.

### 왜 지금 RRF 튜닝은 하지 않았는가?

RRF의 `k`, keyword/vector weight, candidate limit은 검색 품질에 영향을 준다. 하지만 지금 바로 튜닝하면 기준이 부족하다.

현재 seed article은 5개뿐이고, query set도 작다. 이 상태에서 weight를 조정하면 실제 품질 개선보다 우연히 현재 데이터에 맞춘 값이 나올 가능성이 크다.

그래서 이번 작업에서는 tuning이 아니라 measurement boundary를 먼저 만들었다. 별도로 `docs/search-evaluation/queries.md`에 query set과 현재 결과를 남겨, 다음 변경에서 비교할 수 있게 했다.

## 트레이드오프

### RRF baseline vs 정교한 ranking model

정교한 ranking model이나 learning-to-rank를 도입하면 더 좋은 결과를 만들 수 있다. 하지만 지금 Sigak의 목표는 포트폴리오 MVP다. 검색 품질을 주장하기 전에 keyword/vector/hybrid baseline이 모두 재현 가능해야 한다.

RRF는 단순하지만 설명 가능하다. 서로 다른 검색 엔진의 score scale을 직접 맞추지 않아도 되고, 테스트도 명확하다. 대신 domain-specific relevance tuning은 부족하다. 이 부족함은 benchmark query set을 만든 뒤 다음 단계에서 다루는 편이 맞다.

### 장애 fallback vs 장애 노출

검색 projection이 실패해도 public API가 500으로 깨지지 않게 했다. 사용자 경험 측면에서는 좋은 선택이다.

하지만 fallback이 너무 조용하면 장애가 숨겨진다. 그래서 internal metrics에 mode와 failure flag를 남겼다.

```txt
사용자 API: 가능한 한 정상 응답 유지
internal metrics: 어떤 path가 실패했는지 명확히 기록
```

이 분리는 MVP에서 특히 중요하다. 데모 중 외부 인프라 일부가 내려가도 서비스는 설명 가능한 방식으로 동작해야 한다.

## 공학적 주제화

오늘 작업의 핵심 주제는 "기능을 붙이는 것"보다 "검색 시스템의 실패 경계와 관측 가능성을 설계하는 것"에 가깝다.

검색/RAG 시스템은 단일 DB 조회보다 실패 지점이 많다.

- embedding server가 실패할 수 있다.
- vector DB가 느리거나 내려갈 수 있다.
- keyword index가 stale할 수 있다.
- projection rebuild가 필요할 수 있다.
- 검색 품질이 query class마다 다르게 나타날 수 있다.

따라서 hybrid search를 구현할 때는 "결과를 합치는 알고리즘"만큼이나 "실패했을 때 어떤 mode로 degrade되는가", "어떤 metric으로 확인할 수 있는가", "public API 계약은 흔들리지 않는가"가 중요하다.

Sigak에서는 이 문제를 다음 방식으로 풀었다.

```txt
projection store는 빠른 후보 생성
PostgreSQL은 최종 응답 source of truth
public API는 안정적인 article response
internal metrics는 search mode와 실패 원인 관측
evaluation query set은 향후 튜닝 기준
```

이 구조는 이후 graph retrieval이나 benchmark dashboard로 확장하기 위한 기반이 된다.

## 다음 단계

바로 RRF weight를 튜닝하지는 않는다. 다음 순서는 검색 품질을 평가할 수 있는 기준을 먼저 늘리는 것이다.

1. `docs/search-evaluation/queries.md`의 query set을 늘린다.
2. keyword-only, vector-only, hybrid 결과를 같은 query set으로 비교한다.
3. top-1/top-3 relevance 같은 간단한 지표를 정한다.
4. 그 뒤에 `rrfK`, keyword/vector weight, candidate limit을 조정한다.
5. Neo4j graph projection과 graph-aware retrieval로 확장한다.

오늘의 구현으로 hybrid search는 "동작하는 기능"이 됐다. 다음 목표는 이것을 "측정하고 개선할 수 있는 검색 시스템"으로 만드는 것이다.
