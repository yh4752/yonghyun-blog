# 2026-06-03 개발 로그: 블로그 운영을 화면과 루틴으로 정리하기

## 요약

오늘은 블로그를 단순히 "글을 보여주는 사이트"에서 "여러 프로젝트의 글을 안전하게 운영하고, 발행한 글을 다시 학습하는 시스템"으로 확장하는 데 집중했다.

GitHub Actions 런타임 경고를 정리했고, 장기 로드맵을 세웠고, Blog Ops Dashboard와 Learning Ops Dashboard의 역할을 분리했다. Sigak 글을 발행하면서 태그 정책도 다시 정리했고, 프로젝트 상세 페이지에 글이 많아질 때를 대비해 페이지네이션 설계와 구현까지 이어졌다.

하루의 핵심은 CRUD를 바로 붙이는 것이 아니었다. 먼저 현재 원칙인 `source docs/blog -> validation -> sync -> PR -> deploy` 흐름을 유지하면서, 그 상태를 사람이 한눈에 보고 판단할 수 있는 운영 레이어를 만드는 것이었다.

## 오늘 완료한 일

### 1. GitHub Actions 런타임 경고를 정리했다

CI는 통과했지만 main CI 로그에 `Node.js 20 actions are deprecated` 경고가 남아 있었다.

처음에는 프로젝트의 Node 버전 문제처럼 보일 수 있었지만, 실제 원인은 `node-version: 22.x`가 아니었다. 프로젝트 명령을 실행하는 Node와 GitHub Action 자체가 사용하는 런타임은 다른 레이어였다.

그래서 `.github/workflows/ci.yml`에서 공식 액션 버전을 올리는 방식으로 접근했다.

```yaml
uses: actions/checkout@v6
uses: actions/setup-node@v6
```

이 작업은 별도 글로도 정리했다. 다만 하루 기록 관점에서는 "CI 로그의 작은 경고도 운영 대상이다"라는 감각을 얻은 작업에 가깝다.

### 2. 장기 블로그 로드맵을 정리했다

블로그를 계속 발전시키려면 당장 보이는 페이지보다 운영 루틴이 더 중요해졌다.

정리한 방향은 크게 세 가지였다.

- 공개 블로그는 포트폴리오와 기술 판단 기록으로 유지한다.
- 학습/면접 준비는 공개 글과 분리된 개인 루틴으로 추적한다.
- 글 생성, 발행, 비공개, 검증, PR 과정을 나중에 화면에서 다룰 수 있게 한다.

여기서 바로 CMS나 DB를 붙이지 않기로 했다. 현재 글의 source of truth는 GitHub와 각 프로젝트의 `docs/blog` 파일이다. 이 구조는 버전 이력과 PR 검토가 남는다는 장점이 있으므로, 먼저 이 흐름을 잘 보조하는 로컬 운영 도구를 만드는 쪽이 맞다고 봤다.

### 3. Learning Ops를 Blog Ops 안의 독립 탭으로 설계했다

학습/면접 준비는 글 발행과 다른 문제다.

글이 발행됐다고 해서 내가 그 글의 설계 판단을 면접에서 설명할 수 있는 것은 아니다. 특히 AI와 함께 만든 글은 더 그렇다. 글은 그럴듯하지만 내가 다시 설명하지 못하면 포트폴리오의 신뢰도가 떨어질 수 있다.

그래서 Learning Ops를 Blog Ops Dashboard 안의 독립 탭으로 두기로 했다.

```txt
Blog Ops Dashboard
├─ Content Ops
│  ├─ 글 생성
│  ├─ frontmatter 수정
│  ├─ draft 토글
│  ├─ validate / sync / PR
│
└─ Learning Ops
   ├─ 면접 질문 세트 상태
   ├─ 개인 답변 노트 상태
   ├─ 첫 답변 작성 여부
   ├─ 에이전트 리뷰 여부
   ├─ 면접 준비 완료 여부
   ├─ 다음 복습 후보
```

핵심은 공개 글과 개인 답변 노트를 분리하는 것이다. 질문 세트가 공개 글에 있는지는 보여줄 수 있지만, 사용자의 첫 답변이나 면접용 30-60초 답변은 public repository에 올리면 안 된다.

그래서 `.local/learning-progress.json` 같은 private progress manifest를 도입하는 방향으로 설계했다. 이 파일에는 답변 본문을 넣지 않고, 상태와 복습 일정, hash만 둔다.

### 4. Blog Ops Dashboard v1을 read-only inventory로 구현했다

사용자는 나중에 블로그에서 글 수정이나 비공개 전환 같은 작업까지 하고 싶어 했다. 하지만 v1에서 바로 CRUD를 넣으면 public site와 local admin tool의 경계가 흐려질 수 있었다.

그래서 첫 버전은 별도 로컬 Node Dashboard로 정했다.

```txt
npm run ops:dashboard
-> http://localhost:4317
```

v1의 역할은 글을 고치는 것이 아니라 상태를 읽는 것이다.

- source post와 published post 비교
- `draft`, `published`, `pending-sync`, `orphan-published`, `archived-note` 상태 계산
- 허용되지 않은 tag와 quick fix suggestion 표시
- 질문 세트와 개인 답변 노트 존재 여부 표시
- private note와 `.local/`이 `.gitignore`에 포함되어 있는지 확인
- 학습/면접 에이전트로 넘길 프롬프트 생성

이 구조는 나중에 자동 validate, sync, PR 생성으로 확장할 수 있다. 하지만 현재는 임의 shell command를 실행하지 않고 read-only inventory부터 시작한다.

### 5. Sigak 글 발행 과정에서 태그 정책을 보강했다

Sigak 글을 가져오는 과정에서 허용되지 않은 tag가 validation error로 잡혔다.

문제는 단순히 "허용 목록에 추가하면 된다"가 아니었다. 앞으로도 새 프로젝트가 들어오면 새로운 태그가 계속 생길 수 있고, 반대로 일회성 태그가 무분별하게 들어오면 태그 목록이 지저분해질 수 있다.

그래서 태그를 볼 때 다음 기준을 적용하기로 했다.

- 여러 글과 프로젝트에서 반복될 수 있는 durable topic인가?
- 독자가 글을 찾는 데 도움이 되는 reader-facing filter인가?
- 기존 tag의 동의어나 대소문자 차이인가?
- 한 글에서만 쓰이는 상황 설명인가?

이 기준으로 `Collection`, `Evaluation`, `Tooling`처럼 반복 가능성이 있는 태그는 허용하고, `Demo`처럼 상황에 가까운 태그는 다른 태그나 본문 설명으로 흡수하는 방향이 더 맞다고 봤다.

### 6. 프로젝트 상세 페이지 페이지네이션을 설계했다

Sigak 글이 늘어나면서 프로젝트 상세 페이지에 모든 글을 한 번에 보여주는 구조가 점점 부담스러워졌다.

그래서 프로젝트별 글 목록에 페이지네이션을 붙이는 설계를 정리했다.

```txt
/projects/sigak
/projects/sigak/2
/projects/sigak/3
```

첫 페이지 URL은 그대로 유지하고, 2페이지부터 숫자 path를 붙이는 방식이다. 기본 page size는 `8`로 두고, 나중에 프로젝트별 override를 둘 수 있게 `src/data/pagination.ts`로 분리하는 방향을 잡았다.

이 작업은 자정 이후 merge까지 이어졌지만, 문제 인식과 설계는 오늘의 블로그 운영 개선 흐름 안에 있었다.

## 설계 고민

### 왜 바로 CMS나 DB를 붙이지 않았는가?

글 수정, 비공개, 발행 같은 작업을 웹 화면에서 하고 싶은 욕구는 분명히 있다. 하지만 지금 블로그의 중요한 장점은 글이 GitHub 이력과 PR 리뷰 흐름 안에 남는다는 점이다.

처음부터 DB나 MinIO 같은 외부 저장소를 글의 source of truth로 만들면 아래 문제가 생긴다.

- 글 변경 이력이 Git diff로 보이지 않을 수 있다.
- PR 기반 검토와 branch protection 흐름이 약해질 수 있다.
- 개인 답변 노트 같은 private 데이터와 공개 글의 경계가 더 어려워질 수 있다.
- 현재 이미 잘 작동하는 `validate -> sync -> PR -> deploy` 흐름을 다시 설계해야 한다.

그래서 v1은 저장소를 바꾸는 것이 아니라, 현재 파일 기반 운영을 더 잘 보이게 하는 방향으로 잡았다.

### 왜 Learning Ops를 별도 앱이 아니라 Dashboard 안에 넣었는가?

Content Ops와 Learning Ops는 목적이 다르다. 하나는 글을 발행 가능한 상태로 만드는 일이고, 다른 하나는 발행한 글을 내가 설명 가능한 상태로 만드는 일이다.

하지만 둘은 같은 글 목록, 같은 project slug, 같은 draft/published 상태를 필요로 한다. 별도 앱으로 나누면 같은 inventory를 두 번 만들어야 한다.

그래서 UI에서는 탭을 분리하되, 데이터 기반은 공유하는 편이 낫다고 봤다.

```txt
같은 글 inventory
-> Content Ops는 발행 상태를 본다
-> Learning Ops는 이해/면접 상태를 본다
```

### 왜 read-only부터 시작했는가?

CRUD는 편하지만 위험하다. 특히 글 저장소가 파일이고, 발행 흐름이 PR 기반이라면 브라우저 버튼 하나로 파일을 고치는 순간 git 상태, source/published sync, draft 전환, validation, PR 경계가 한꺼번에 엮인다.

그래서 먼저 읽기 전용 inventory를 만들고, 어떤 상태와 경고를 보여줘야 하는지 검증하는 편이 맞다. 상태 모델이 안정된 뒤에야 "이 버튼이 실제로 무엇을 바꿔야 하는가"를 안전하게 정할 수 있다.

## 트레이드오프

### 파일 기반 운영 vs CMS

파일 기반 운영은 CLI와 PR이 필요하므로 번거롭다. 대신 글 변경 이력, 리뷰, CI 검증이 자연스럽게 남는다.

CMS는 편하지만, 지금 단계에서는 데이터 저장소, 인증, draft/published 모델, 배포 연동을 새로 설계해야 한다. 그래서 현재는 GitHub 기반 파일 운영을 유지하고, 그 위에 로컬 Dashboard를 얹는 선택을 했다.

### 자동화 vs 사람의 판단

Dashboard가 생기면 글 상태를 더 쉽게 볼 수 있다. 하지만 어떤 태그를 새로 허용할지, 어떤 글을 학습 대상으로 삼을지, 어떤 글을 포트폴리오 대표 글로 둘지는 여전히 사람이 판단해야 한다.

오늘의 자동화는 사람의 판단을 대체하는 것이 아니라, 판단하기 전에 놓치기 쉬운 상태를 보여주는 쪽에 가깝다.

## 기술 포인트

### publish status와 learning status를 분리했다

발행 상태는 파일 구조로 계산한다.

| 상태 | 의미 |
| --- | --- |
| `draft` | source post가 있고 `draft: true`다 |
| `published` | source post가 있고 `draft: false`이며 published post도 있다 |
| `pending-sync` | source post가 있고 `draft: false`지만 published post가 아직 없다 |
| `orphan-published` | published post는 있지만 source post가 없다 |
| `archived-note` | source/published post는 없지만 private note만 있다 |

학습 상태는 별도 흐름이다.

| 상태 | 의미 |
| --- | --- |
| `not-started` | 아직 학습 루틴을 적용하지 않은 글 |
| `questions-ready` | 공개 글에 질문 세트가 있음 |
| `first-answer-written` | 개인 노트에 첫 답변이 있음 |
| `reviewed` | 부족한 개념이나 근거가 보강됨 |
| `interview-ready` | 30-60초 답변으로 설명 가능한 상태 |
| `needs-revisit` | 시간이 지났거나 글/질문 변경으로 복습 필요 |

이 둘을 분리해야 "글은 발행됐지만 아직 면접 준비는 안 됐다" 같은 상태를 표현할 수 있다.

### private 데이터는 내용이 아니라 존재와 상태만 본다

Learning Ops에서 개인 답변 노트의 존재 여부는 필요하다. 하지만 답변 내용 자체를 Dashboard에 보여줄 필요는 없다.

그래서 private note는 파일 존재와 섹션 여부만 확인하고, progress manifest도 답변 본문 대신 상태, 복습 일정, hash만 저장하는 방향으로 설계했다.

이 경계는 중요하다. 공개 블로그 운영 도구가 개인 학습 기록까지 노출하면, 나중에 오픈소스화하기 어렵고 심리적으로도 솔직한 첫 답변을 남기기 어려워진다.

## 검증

오늘 작업의 검증은 여러 단계로 나뉘었다.

| 항목 | 확인한 것 | 상태 |
| --- | --- | --- |
| GitHub Actions 경고 제거 | PR과 main CI 로그에서 `deprecated`, `Node.js 20`, `punycode` 키워드 검색 | 별도 글에 검증 기록 남김 |
| Blog Ops 설계 | `docs/superpowers/specs/2026-06-03-blog-ops-dashboard-design.md`에 범위, 상태 모델, 로컬 실행 방식을 문서화 | 확인 |
| Learning Ops 설계 | `docs/learning-ops-dashboard.md`에 상태 전환, 질문 세트 판정, private manifest 정책을 정리 | 확인 |
| Blog Ops 구현 | `scripts/blog-ops-dashboard.mjs`, `scripts/blog-ops/*`, 관련 테스트가 main 이력에 포함됨 | 확인 |
| 프로젝트 페이지네이션 | `docs/superpowers/specs/2026-06-03-project-post-pagination-design.md`와 `scripts/project-pagination.test.mjs`로 설계와 기대 동작을 고정 | 확인 |

미검증으로 남긴 것도 있다.

- Blog Ops Dashboard에서 실제 수정, draft 전환, PR 생성은 아직 구현하지 않았다.
- Learning Ops는 개인 답변 노트를 자동으로 작성하지 않는다.
- GitHub Actions 액션 버전 업데이트 자동화는 아직 Dependabot/Renovate로 연결하지 않았다.

## 남은 문제

가장 큰 남은 문제는 Blog Ops Dashboard의 다음 단계다.

v1은 read-only inventory이므로 상태를 보여줄 수는 있지만, 아직 사용자의 작업을 줄여주지는 못한다. 이후에는 아래 순서가 필요하다.

1. validate/source validate 명령 실행 버튼
2. draft 전환과 frontmatter quick fix 적용
3. sync 실행과 diff preview
4. PR 생성 보조
5. production 배포 후 QA checklist 연결

또 하나는 글 형식의 경계다. 오늘처럼 하루 안에 CI 경고 정리, 운영 대시보드 설계, 태그 정책, 페이지네이션이 함께 진행되면 단일 deep-dive로 만들기 쉽다. 하지만 이 경우에는 dev-log가 먼저고, 큰 주제는 별도 글 후보로 분리하는 편이 더 낫다.

## 다음 단계

- Blog Ops Dashboard v1을 실제로 켜서 content/learning 상태가 기대대로 보이는지 확인한다.
- invalid tag suggestion과 quick fix suggestion을 실제 글에 적용 가능한 수준으로 다듬는다.
- Learning Ops에서 학습/면접 에이전트로 넘기는 프롬프트를 더 자연스럽게 만든다.
- 프로젝트 페이지네이션이 모바일과 production에서 어색하지 않은지 QA한다.
- 6/3에 진행한 작업 중 별도 글로 남길 주제를 고른다.

## 별도 글 후보

- `GitHub Actions 런타임 경고를 CI 로그에서 지우기`: 이미 별도 debugging 글로 작성했다.
- `Blog Ops Dashboard 설계`: 로컬 read-only dashboard를 먼저 선택한 이유를 deep-dive로 만들 수 있다.
- `Learning Ops Dashboard`: 발행 상태와 학습 상태를 분리한 이유를 학습형 글로 만들 수 있다.
- `태그 정책과 validation`: 태그 allow-list를 무작정 넓히지 않는 기준을 decision-note로 만들 수 있다.
- `프로젝트 글 페이지네이션`: 글이 늘어나는 프로젝트 상세 페이지를 어떻게 나누는지 architecture 글로 확장할 수 있다.
